# Completeness critique

A final reviewer read all nine summaries and searched for what a platform-security architect would still insist on. Gaps become backlog items; contradictions were resolved in the plan (one profile taxonomy, Agent Substrate as a watch item, OpenBao AWS engine as an external plugin, no MIG on A16, CSI-first FUSE, deny-queue-resume approvals).

## Gaps

### Audit logging of agent actions inside the pod (tool calls, file writes, MCP invocations, credential issuance) as a first-class, tamper-evident record — no dimension specifies what is logged, where, in what schema, or for how long.

Note: the session WebSearch budget was exhausted, so primary sources were fetched directly with WebFetch. Kubernetes auditing (https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/) logs only kube-apiserver requests (levels None/Metadata/Request/RequestResponse; log and webhook backends) and explicitly does not cover in-pod process activity, so the DE will see a Sandbox being created but never what Claude Code or Codex did inside it. OpenBao audit devices (https://openbao.org/docs/audit/, 2.4.x-2.6.x docs) record every API request/response with HMAC-SHA256-hashed strings, expose /sys/audit-hash for verification, and block requests if no audit device can write, which gives a reliable 'who received which credential' trail — but only for brokered credentials. For runtime activity, Falco's default rules (https://falco.org/docs/reference/rules/default-rules/) already ship 'Read sensitive file untrusted' (WARNING, stable), 'Read ssh information' (ERROR), 'Adding ssh keys to authorized_keys', 'Detect crypto miners using the Stratum protocol' and 'Known Cryptominer Process Executed' (CRITICAL) — directly relevant to an agent reading ~/.irods/.irodsA or ~/.ssh — but the page says nothing about gVisor support, so L2 pods may be blind. The OpenTelemetry GenAI semantic conventions have moved to https://github.com/open-telemetry/semantic-conventions-genai (agent spans, tool execution, MCP conventions; still in active development, 131 open issues), so a schema exists to adopt for per-tool-call tracing from agentgateway/ToolHive, but it is not yet stable. NIST SP 800-171 Rev 3 (May 2024, https://csrc.nist.gov/pubs/sp/800/171/r3/final) has a dedicated Audit and Accountability family; without an in-pod audit design the platform cannot claim coverage.

Suggested follow-up query: OpenTelemetry semantic-conventions-genai agent spans gen_ai.tool.name stability; Falco gVisor runsc support; agentgateway OTel MCP tool call tracing

### Data egress / DLP for research data — nothing covers what happens when an agent reads a restricted Data Store file and sends its contents to an LLM endpoint or a web tool (exfiltration through the allowed channel), nor indirect prompt injection from untrusted files in /data-store or shared collections.

OWASP's 'Top 10 for Agentic Applications for 2026' (https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/, published 2025-12-09, peer-reviewed by 100+ experts) is the current reference framework; the fetch returned only the cover page so ASI entries could not be quoted, but the agent-harness dimension already cites ASI03 for identity. All nine dimensions enforce egress by destination (domain allowlist, NetworkPolicy, proxy) — none inspects or classifies the payload. Since llm-api.cyverse.ai, api.anthropic.com and github.com are on every proposed L0/L1 allowlist, a compromised or prompt-injected agent can exfiltrate any file it can read to those hosts. UNM's guidance (mesa-carc dimension) permits only P-class data in AI tools, and CARC's Good Neighbor policy (https://carc.unm.edu/docs/getting-started/good-neighbor-policy/) prohibits HIPAA/PHI/PCI/FERPA/CUI data on CARC systems, so a design with no content-level control cannot support C/E-class data even at the strongest runtime tier. Cilium's toFQDNs/L7 docs could not be fetched (redirect only), so the L7 method/path capability for HTTPS remains unverified.

Suggested follow-up query: OWASP ASI Top 10 agentic applications 2026 ASI06 memory poisoning ASI data exfiltration tool output; indirect prompt injection coding agent file read mitigation; LLM gateway DLP redaction agentgateway prompt guard

### Multi-tenant GPU (and CPU) scheduling fairness, queueing and per-user quota — the gpu-local-llm dimension covers device sharing (MIG/MPS/time-slicing) but no dimension covers who gets the GPU when the pool is full, preemption of idle agent pods, or per-user limits, given that all analyses share the single vice-apps namespace.

Kubernetes ResourceQuota (https://kubernetes.io/docs/concepts/policy/resource-quotas/) can cap requests.nvidia.com/gpu and DRA device classes (e.g. examplegpu.deviceclass.resource.k8s.io/devices) and object counts, but it is namespace-scoped, not per-user, and rejects with HTTP 403 — so with every VICE analysis in vice-apps it cannot stop one user from taking every GPU. Kueue (https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/) provides ClusterQueue nominalQuota, borrowingLimit, lendingLimit (stable since v0.17), cohorts, and spec.preemption (reclaimWithinCohort, borrowWithinCohort, withinClusterQueue), and its plain-Pod integration (https://kueue.sigs.k8s.io/docs/tasks/run/plain_pods/, default-on since v0.16, label kueue.x-k8s.io/queue-name, managedJobsNamespaceSelector) can gate app-exposer-created pods without changing the DE — but Kueue does not recreate failed pods and excludes pods owned by other Kueue-managed resources, so the Deployment-based VICE model and agent-sandbox Sandbox CRD need explicit integration work. Long-running autonomous agent pods (problem c) plus warm pools would otherwise starve interactive GPU apps.

Suggested follow-up query: Kueue agent-sandbox Sandbox CRD integration; Kueue Deployment integration GPU preemption idle pods; per-user namespace tenancy JupyterHub vs shared namespace quotas

### Cost controls and budget enforcement across LLM spend, GPU-hours and pod runtime for autonomous agents — dimensions mention LiteLLM virtual keys and --max-budget-usd in passing but none defines who pays, per-user/per-course budgets, alerting, or what the DE does when a budget is exhausted mid-run.

LiteLLM (https://docs.litellm.ai/docs/proxy/users and https://docs.litellm.ai/docs/proxy/virtual_keys) supports max_budget and budget_duration at global, team, team-member (max_budget_in_team), internal-user, per-key, per-model and customer scopes; keys made with /key/generate accept duration, max_budget, budget_duration, models, metadata, tpm_limit, rpm_limit, team_id; exceeding a budget fails requests with ExceededBudget/ExceededTokenBudget (HTTP 401/429); soft budgets and budget fallbacks exist; /key/block and /key/unblock disable keys — but key rotation with grace periods and advanced audit logging are Enterprise-only, which matters for an all-OSS design and for whether AI Verde will expose these. Nothing equivalent exists for GPU-hours: ResourceQuota is namespace-scoped and Kueue quotas are capacity, not cost. A budget-exhausted agent mid-run must be handled by the harness (Claude --max-budget-usd, Goose GOOSE_MAX_TURNS) and surfaced in the DE, otherwise a 401 from the gateway becomes an opaque failure.

Suggested follow-up query: LiteLLM budget alerts webhook open source vs enterprise; OpenCost GPU cost allocation per pod Kubernetes; Claude Code max-budget-usd exit behavior stream-json

### Compliance mapping — which framework (NIST SP 800-171 Rev 3, UNM data classification P/C/E, CARC Good Neighbor, export control) the AI Sandbox security levels must satisfy, and specifically whether the proposed Apptainer/CARC variant of the MESA image violates CARC's no-unencrypted-passwords rule via ~/.irods/.irodsA.

NIST SP 800-171 Rev 3 (https://csrc.nist.gov/pubs/sp/800/171/r3/final, May 2024) defines 17 families including Access Control, Audit and Accountability, Identification and Authentication, Incident Response, System and Communications Protection, and Supply Chain Risk Management; no dimension maps the L0/L1/L2 tiers to these. CARC's Good Neighbor Use Policy (https://carc.unm.edu/docs/getting-started/good-neighbor-policy/) states 'HIPAA, PHI, PCI, FERPA, and Controlled Unclassified Information (CUI) data may not be stored on or transferred via CARC systems', 'No passwords — for CARC or any other machines — may be stored in unencrypted form on CARC file systems', and that export-controlled software needs written approval from UNM Export Control. The credential-brokering dimension confirms .irodsA is only reversibly obfuscated (keyed on uid), so the mesa-carc recommendation to ship an Apptainer-compatible MESA agent image using 'a CARC-approved secret file with 0600' would still put a decodable iRODS password on CARC filesystems, and agent binaries bundled from GitHub releases may need export-control review. CARC's own 'For AI agents' page (https://carc.unm.edu/docs/about/ai-agents/) is only guidance for LLMs consuming docs and contains no policy on running agents, so no institutional rule exists yet to design against.

Suggested follow-up query: NIST SP 800-171 r3 03.03 audit 03.13 boundary protection requirements list; UNM data classification P C E class AI tools policy; iRODS PAM password obfuscation .irodsA encrypted at rest

### Backup, undo and rollback of agent-made changes — to the workspace PVC, to git, and above all to the iRODS Data Store — including whether autonomous agents may ever hard-delete.

Claude Code checkpointing (https://code.claude.com/docs/en/checkpointing) keeps file snapshots for the 100 most recent checkpoints, deletes them after ~30 days (cleanupPeriodDays), and explicitly does not track files modified by bash commands (rm, mv, cp), edits by background subagents, external changes, or symlinked/hard-linked paths — so it is not a safety net for headless `claude -p` runs, and Codex/OpenCode/Goose have no equivalent in any dimension. On the Data Store side, iRODS irm (https://docs.irods.org/4.3.5/icommands/user/#irm) moves objects to /myZone/trash by default, while -f performs 'Immediate removal of data objects without putting them in trash', and irmtrash empties it; iRODS has no versioning (data_version in R_DATA_MAIN is 'no longer used', https://docs.irods.org/4.3.5/system_overview/data_objects/). The mesa-mcp toolset exposes ds_delete_file, ds_move_file, ds_write_file and ds_execute_rule, and the mesa-carc dimension only proposes denying ticket/ACL/rule tools — not delete/overwrite. The design needs a trash-only write policy for agents, forbidding -f/irmtrash and rule execution, plus git-worktree-per-job and PVC snapshots for rollback.

Suggested follow-up query: iRODS trash policy disable force delete for user PEP; Kubernetes VolumeSnapshot CSI iRODS; Codex CLI checkpoint undo; git worktree per agent job rollback pattern

### How approvals reach the human when they are away — mobile access, push notifications, timeout/expiry semantics and accessibility of the DE 'approval inbox' — and why Anthropic's own Remote Control cannot be the answer for VICE.

Claude Code Remote Control (https://code.claude.com/docs/en/remote-control) does let you 'Approve tool calls from your phone' with push notifications ('Push when actions required') and keeps permission prompts open until answered, but it requires a claude.ai Pro/Max/Team/Enterprise login ('API keys are not supported'), stores the session transcript on Anthropic servers, is unavailable to Zero-Data-Retention organizations, and refuses to work when ANTHROPIC_BASE_URL points at an LLM gateway other than api.anthropic.com — i.e. exactly the AI Verde/LiteLLM configuration every dimension recommends. Trusted Devices requires Team/Enterprise. So VICE must build its own approval channel (hooks/OpenCode endpoint into a DE service), and must decide expiry rules: Claude's forwarded dialogs default to a 5-minute expiry (dialogExpiry) while hook timeouts default to 600 s, and WCAG 2.2 (current version, published 2023-10-05, https://www.w3.org/WAI/standards-guidelines/wcag/) governs timing-adjustable UI for a university service — none of which any dimension addressed.

Suggested follow-up query: WCAG 2.2 success criterion 2.2.1 timing adjustable 2.2.6 timeouts; web push notifications PWA approval queue self-hosted; Matrix/Slack interactive approval buttons open source

### LLM provider data retention and transcript governance — which Claude Code/Codex login mode VICE users are in (consumer OAuth vs API key vs AI Verde), what retention applies to prompts that may contain research data, and whether session transcripts leave campus.

Anthropic's commercial retention article (https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-personal-data, current as of 2026-07-01) says API inputs/outputs are deleted within 30 days by default, Zero Data Retention is available only 'when you and we have agreed otherwise', flagged content may be kept up to 2 years and safety scores up to 7 years, and consumer Claude/Claude Code-with-consumer-login retention is governed by a different policy. The images bundle agents with their own OAuth tokens (Claude Code subscription, Codex, Antigravity), so a user who logs in with a personal account sends Data Store content under consumer terms, bypassing AI Verde entirely; Remote Control additionally stores transcripts on Anthropic servers. No dimension states the policy: which providers are allowed per security level, whether ANTHROPIC_BASE_URL/OPENAI_BASE_URL must be pinned to llm-api.cyverse.ai in managed settings, and where the DE persists transcripts for its own approval audit.

Suggested follow-up query: Claude Code managed settings force ANTHROPIC_BASE_URL disable OAuth login; OpenAI API data retention zero data retention eligibility; university LLM gateway data governance policy research data

### Admission-time policy enforcement engine and supply-chain gate — the image-build dimension says 'an admission policy should refuse unsigned images' and the runtime-isolation dimension wants an 'ai-sandbox' policy, but no dimension names the engine, nor considers mutating pods (adding securityContext/seccomp) without changing app-exposer.

Kyverno (https://kyverno.io/docs/introduction/, v1.19.0 current) provides validate, mutate, generate and cleanup policies in YAML/CEL, plus Verify Image rules supporting Sigstore and Notary signatures, which could enforce 'no NOPASSWD sudo images', 'Capabilities.Drop ALL', 'seccompProfile Localhost', 'runtimeClassName by security level', and cosign-signed harbor.cyverse.org images at admission — and mutate the existing vicebuild Deployment specs so hardening does not wait for app-exposer changes. Pod Security Admission alone (recommended by cyverse-vice) cannot verify signatures or require Localhost seccomp profiles. Without a named engine the security levels are documentation, not enforcement.

Suggested follow-up query: Kyverno verifyImages cosign keyless harbor policy; Kyverno mutate seccompProfile Localhost runtimeClassName by label; ValidatingAdmissionPolicy CEL hostUsers false require

### iRODS-specific limits of the ticket/CSI credential model — tickets cannot be used by the CSI FUSE mount, default ticket scope is dangerously broad, and the CSI driver's documented auth surface contradicts what the cyverse-vice dimension asserts.

The iRODS 4.3.5 ticket docs (https://docs.irods.org/4.3.5/icommands/tickets/) say 'By default a ticket can be used by anyone (and anonymous), from any host, and any number of times, and for all time (until deleted)'; restrictions are only via `mod` uses/write-file/write-byte/expire/add-remove user/group/host — so DE-minted agent tickets must always be constrained, and hosts are converted to IPs (pod egress IPs change). The cyverse/irods-csi-driver README (https://github.com/cyverse/irods-csi-driver) documents credentials only as user/password (secret via nodeStageSecretRef or plain text) with an optional clientuser proxy parameter and enforceProxyAccess, mountPathWhitelist, pathMappingJSON; it lists no ticket, PAM or OIDC support and does not document no_permission_check. Therefore the CSI mount will always carry a full proxy credential in the node DaemonSet, and tickets can only govern iRODS API/MCP access — the two paths need separate policy, and write-scoped tickets cannot be enforced on the FUSE mount at all.

Suggested follow-up query: irods-csi-driver no_permission_check volume attribute source; iRODS ticket restrictions metadata AVU rule execution 4.3; irods_client_icommands iticket add host CIDR

### How the DE / ai-sandboxes-ui exposes security levels to users and app authors — consent, default level per app, who may raise a level, and how the level is recorded on the analysis for audit.

docs.cyverse.org/vice and learn.cyverse.org could not be fetched (404 / DNS failure), and ai-sandboxes-ui is private, so no primary source describes the current user-facing model; the cyverse-vice dimension only proposes 'expose the level in ai-sandboxes-ui'. Every other dimension defines a different tier taxonomy (egress tiers, RuntimeClass tiers, data-class tiers, autonomy tiers), so without a UI/API contract (a field on the analysis or VICESpec, an admin-approved list of apps per level, and a visible badge) users cannot reason about what an agent may do with their data, and admins cannot audit which level a run used. NIST 800-171's Access Control and Planning families expect this to be documented.

Suggested follow-up query: cyverse ai-sandboxes-ui security level analysis field Terrain API; JupyterHub profile_list security tier consent UI pattern

### Incident response and kill-switch: revoking everything a user's agents hold, stopping all of a user's autonomous runs, and containing a compromised image or node — no dimension covers detection-to-revocation flow.

OpenBao's blocking audit semantics and lease model give revocation primitives, and Falco's default rules (https://falco.org/docs/reference/rules/default-rules/) provide detections such as 'Detect crypto miners using the Stratum protocol' (CRITICAL) and 'Read sensitive file untrusted', but nothing wires a Falco alert to LiteLLM /key/block (https://docs.litellm.ai/docs/proxy/virtual_keys), OpenBao lease revocation, iRODS ticket deletion, and app-exposer stopping the analysis. NIST SP 800-171 Rev 3 includes an Incident Response family. Autonomous agent pods that outlive the human session (problem c) increase blast radius, so a 'stop all my agents' action and an admin-wide kill switch must be first-class in the DE.

Suggested follow-up query: Falco talon response actions Kubernetes; OpenBao revoke leases by prefix role; LiteLLM key block API automation

## Contradictions between dimensions

- Security-level taxonomy is defined six different ways: cyverse-vice L0/L1/L2 = egress allowlists; k8s-agent-substrates L0 runc / L1 gvisor / L2 kata-qemu; runtime-isolation L1 runc+userns / L2 gVisor / L3 Kata; mesa-carc Level 0/1/2 = UNM data classes P/C/E; prior-art L0 assist (in-pod bwrap) / L1 background pod / L2 untrusted gVisor; gpu-local-llm standard/sandboxed/isolated. These are orthogonal axes (runtime, egress, data class, autonomy) and must be unified before any UI or admission policy is written.
- Substrate/kagent adoption: cyverse-vice recommends attaching a kagent/Agent Substrate or gVisor cluster as a vice-operator target; prior-art lists kagent + Agent Substrate in the 'all-OSS stack'; k8s-agent-substrates says 'track, but do not build on'; runtime-isolation and agent-harness-autonomy say 'do not adopt kagent or Agent Substrate' / 'adjacent, not foundational'. mesa-carc additionally reports that kagent main removed the AgentHarness CRD and OpenClaw backend on 2026-09-05, replacing them with Harness/AgentTemplate, while k8s-agent-substrates describes v0.10.0's CRD as SandboxAgent — three different names for the same layer.
- OpenBao AWS/STS engine: the credential-brokering summary states OpenBao 'does NOT ship an AWS/STS-style secrets engine, so S3 credentials for OSN cannot be brokered by OpenBao itself', but its own verdict documents official external plugins secrets-aws-v0.3.1 (2026-07-22) with iam_user/assumed_role/federation_token and sts_endpoint, loadable via plugin_auto_download; the remaining true gap is only Ceph-RGW/MinIO-specific STS (openbao#1504 open).
- gVisor for agent pods vs in-harness sandboxes: agent-harness-autonomy recommends `sandbox.enabled: true` + `sandbox.failIfUnavailable: true` in the agent image and falling back to `--dangerously-skip-permissions` 'only inside a gVisor/Kata pod', while runtime-isolation documents that bubblewrap inside gVisor has open bugs (#13438 RTM_NEWADDR, #14451 openat2), gVisor ignores pod seccomp/AppArmor and lacks Landlock, and gVisor cannot combine with hostUsers:false (#13303) — so failIfUnavailable would make Claude Code refuse to start in exactly the L2 pods where it is supposed to run unattended.
- Sandbox-router necessity: the k8s-agent-substrates summary says under gVisor/Kata 'the project's sandbox-router must be used as the single entry point', whereas its own verdict shows the router is optional (threat model lists it as 'Sandbox Router (Optional)', openclaw-gvisor example uses NodePort/LoadBalancer) and only CRI port-forward breaks; VICE's existing vice-proxy + HTTPRoute path would keep working.
- GPU sharing on A16: cyverse-vice recommends 'MIG/time-slicing on A16-class cards' for a shared vLLM tier, but gpu-local-llm establishes the A16 cannot MIG and that time-slicing gives 'zero memory/fault isolation'; runtime-isolation adds that gVisor nvproxy supports no MIG and no time-slicing. Only whole-sub-GPU allocation or MPS is consistent across dimensions.
- FUSE strategy: image-build recommends prototyping/forking meta-fuse-csi-plugin (dormant since 2024-10-23) with the FUSE client as a sidecar; runtime-isolation says do not plan on host-side libfuse servers over --pass-fd under gVisor and prefers node-side CSI; cyverse-vice observes that on CSI clusters the FUSE privilege already lives in the irods.csi.cyverse.org DaemonSet and the analysis pod needs no FUSE at all. The only unresolved FUSE need is OSN s3fs, which credential-brokering wants routed through a SigV4 re-signing proxy anyway.
- CSI authentication claims: cyverse-vice states the per-analysis PV uses volumeAttributes clientUser (proxy through de-irods) and no_permission_check=true, and mesa-carc's verdict repeats 'proxy clientUser'; the irods-csi-driver README fetched today documents user/password secrets, clientuser, enforceProxyAccess and mountPathWhitelist but no no_permission_check attribute, and mesa-carc's open question still asks what auth the driver uses — the attribute and its security meaning need verification against driver source, since 'no permission check' on a proxy-admin mount is the single largest privilege in the pod.
- Claude Code hook semantics inside agent-harness-autonomy: the summary/recommendation says PermissionRequest returns allow|deny|ask and to 'default deny on the 600 s timeout', but the verdict shows PermissionRequest returns a {behavior: allow|deny} object with no 'ask', and a timed-out http hook is discarded so the call falls through to the normal permission flow rather than denying — under interactive mode that means a prompt, under `-p --permission-prompts none` a denial; the approval-inbox design must not rely on timeout-as-deny.
- Launcher-dropped .irodsA: mesa-carc's summary says VICE's launcher writes ~/.irods/.irodsA into the pod, while its verdict and cyverse-vice both show app-exposer injects only IPLANT_USER/IPLANT_EXECUTION_ID/REDIRECT_URL and .irodsA appears only after iinit/cyverse-login; credential-brokering's 14-day password_max_time hardening therefore applies to the human-initiated login path, not to something the platform injects.
- Node baseline prerequisites are asserted but never verified: runtime-isolation and image-build make Kubernetes >=1.36, kernel >=6.3, containerd >=2.0 and idmap-capable volumes hard prerequisites (with image-build noting NFS is unsupported for hostUsers:false), gpu-local-llm pins >=1.36 for ImageVolume/DRA, yet every dimension lists the actual CyVerse/Jetstream2 cluster version, CNI, node OS and NVIDIA driver version as open questions — the whole L1 design depends on an unverified fact.
- Time-limited approvals: prior-art and agent-harness propose a DE approval inbox where 'the agent pod blocks' until the user answers later, but Claude Code's own remote dialogs expire after 5 minutes by default (dialogExpiry) and hook timeouts after 600 s, and OpenCode headless 'ask' hangs (issue #16367) — 'block indefinitely' is not a behavior any harness currently guarantees, so the inbox must implement deny-queue-resume via --resume/codex exec resume rather than long blocking.

## Strongest design signals

- Brain/hands split: keep the human's interactive VICE pod and run every autonomous agent job as a separate pod with its own UID, ServiceAccount, lifetime and credentials, sharing only the workspace volume (stated independently by all nine dimensions; kubernetes-sigs/agent-sandbox Sandbox v1beta1 or a plain Job/second analysis via Formation as the primitive).
- Credentials never live in the agent's filesystem or environment: a broker (OpenBao 2.6.x Kubernetes/JWT auth, leased and revocable) plus an egress proxy that injects real secrets only for allow-listed hosts (sentinel/mask pattern from Anthropic, Claude Code sandbox.credentials, OpenShell providers v2, agentgateway); non-HTTP credentials (iRODS password, SSH keys) are replaced by iRODS tickets, hosted OAuth MCP endpoints (mcp.cyverse.ai/mcp, de.cyverse.org/formation/mcp) and OpenBao SSH CA certificates.
- Immediate, substrate-independent fixes that every dimension agrees on: remove `NOPASSWD: ALL` sudo and the entry.sh copy of ~/.aws, ~/.ssh, .gitconfig from /data-store; harden the analysis container (AllowPrivilegeEscalation=false, Capabilities.Drop ALL, seccomp, PSA labels on vice-apps); run agents as a distinct non-sudo UID with 0700 human dotfiles; ship read-only managed settings (deny reads of ~/.irods, ~/.aws, ~/.ssh; CLAUDE_CODE_SUBPROCESS_ENV_SCRUB; disableBypassPermissionsMode).
- Egress is enforced at the pod/cluster boundary (default-deny NetworkPolicy already produced by vice-operator, plus FQDN/SNI allowlist proxy), never only per process — because Claude Code's bwrap sandbox, Codex's network proxy and GitHub's firewall all explicitly exclude MCP servers and hooks, and VICE bundles several MCP servers.
- LLM access goes through one gateway (AI Verde/LiteLLM, optionally agentgateway) with per-analysis short-lived virtual keys (duration, max_budget, models), and self-hosted vLLM/Ollama run as shared GPU-scheduled cluster services reachable only via that gateway; per-pod GPUs are reserved for whole-GPU science workloads, and A16-class cards cannot be MIG-partitioned.
- kubernetes-sigs/agent-sandbox (v1.0.1, 2026-09-03, RuntimeClass-delegated isolation, shutdownTime/shutdownPolicy, volumeClaimTemplates) is the consensus pod primitive; Agent Substrate (v0.0.x, 'not ready for production') and kagent (CRDs churning: SandboxAgent/AgentHarness/Harness) are watch items, and Daytona, E2B, microsandbox, Ona, Coder Tasks are dropped.
- gVisor is the consensus runtime for headless agent pods and Kata for VM-grade/GPU-passthrough, but with hard caveats repeated across dimensions: no hostUsers:false, no in-gVisor bubblewrap, no MIG/time-slicing under nvproxy, exact NVIDIA driver-version windows, KasmVNC/RStudio untested — hence a mandatory spike before assigning apps to levels.
- A node/cluster baseline is a prerequisite for the whole L1 design: Kubernetes >=1.36 (user namespaces GA, ImageVolume stable, DRA sub-features), kernel >=6.3, containerd >=2.0, a VICE-specific Localhost seccomp profile and AppArmor profile permitting mount/userns for bubblewrap, and Ubuntu 24.04's kernel.apparmor_restrict_unprivileged_userns handled.
- Human-in-the-loop becomes an asynchronous DE-owned approval service (Claude Code PermissionRequest/PreToolUse http hooks, OpenCode /session/:id/permissions endpoint; policy-only for Goose/Gemini/Antigravity), with every approval and denial logged with tool_name/tool_input — and, per this review, it must be homegrown because Anthropic Remote Control refuses to work behind an LLM gateway.
- Phased rollout with measurable gates recurs (CISA/OWASP-style): Phase 1 read-only/dontAsk jobs on hardened runc pods, Phase 2 workspace-write with approval inbox, Phase 3 broader autonomy only inside gVisor/Kata Sandboxes behind the egress proxy — with vice-toolkit's audit skill converging all seven images before securityContext enforcement.
