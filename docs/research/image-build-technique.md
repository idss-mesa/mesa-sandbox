# Image build technique (Bake, pinning, SBOM, non-root apps, native sidecars)

Dimension key: `image-build-technique`. Date: 2026-09-06.

## Summary

The building blocks for a rootless, sudo-free VICE image family now exist as GA Kubernetes features and mainstream build tooling. Native sidecars (initContainers with restartPolicy: Always) are stable since v1.33 and are the natural home for credential brokers, egress proxies, FUSE mounters and agent runners; user namespaces (hostUsers: false) went GA in v1.36 (April 2026) and make in-container UID 0 and namespaced CAP_SYS_ADMIN harmless to the node, but they demand kernel 6.3+, containerd 2.0+, and idmap-capable volume filesystems. FUSE without privileged remains the hardest problem: the only production-shaped design is meta-fuse-csi-plugin (FUSE process in a sidecar, /dev/fuse fd passed from a privileged CSI DaemonSet) but it has been dormant since Oct 2024; device plugins like nextflow-io/k8s-fuse-plugin only inject /dev/fuse and still leave the mount(2) privilege problem, and the moby PR relying on the kernel-4.18 unprivileged-FUSE-in-userns path was never merged. Every VICE app can run as a fixed non-root user: JupyterLab (docker-stacks jovyan 1000:100 with tini), code-server (run with -u uid:gid), ttyd, and KasmVNC (kasmtech core images use useradd -u 1000 kasm-user, USER 1000, no sudo; vncserver is a user-level service with ~/.kasmpasswd), and Open OnDemand proves RStudio Server needs no root when launched as rserver --server-user=$(whoami) --auth-none 0 --server-data-dir=/tmp/run, which is how VICE should replace rocker's root-only /init + s6 userconf script. On the build side, Docker Bake matrix/inherits/contexts with attest = [provenance mode=max, sbom], BuildKit cache mounts, Renovate docker:pinDigests plus regex custom managers for curl-fetched agent binaries, cosign keyless signing (with OpenBao KMS support) and SLSA-3 container provenance, gated by hadolint DL3002/dockle CIS-DI-0001/Trivy+Grype, give a reproducible hardened base. Industry agent sandboxes (Codex universal, Gitpod, Codespaces) all still run root or passwordless sudo; the strongest reference designs for VICE are Anthropic's cloud environment (credentials held by proxies outside the VM; CLI refuses --dangerously-skip-permissions as root) and Coder's Agent Firewall (nsjail/Landlock + HTTP allowlist proxy), both of which map cleanly onto a sidecar-per-agent pod layout.

## Fact-check verdicts on load-bearing claims

### [confirmed] Native sidecar containers are declared as initContainers with restartPolicy: Always, are stable since Kubernetes v1.33 (feature gate SidecarContainers enabled by default since v1.29 and locked in v1.33), start in order before app containers, are terminated only after the main container stops (in reverse order), and support startupProbe/readinessProbe/livenessProbe and their own resource requests.

**Evidence.** Every element of the claim checks out against the primary source and independent sources, as of 2026-09.

1) Declaration: kubernetes.io sidecar-containers page (last modified 2026-01-18): "you can specify a restartPolicy for containers listed in a Pod's initContainers field"; example YAML has `initContainers: - name: logshipper ... restartPolicy: Always` with the comment "Setting restartPolicy: Always makes this a sidecar container."

2) Version/status: Same page: "Feature state: Stable since Kubernetes v1.33 ... It was first available in the v1.28 release. You can no longer disable or opt out of this feature or behavior (it is locked); if you explicitly set a value for the associated feature gate SidecarContainers, Kubernetes ignores it." Independent confirmation from the feature-gates-removed reference table: `SidecarContainers false Alpha 1.28-1.28`, `true Beta 1.29-1.32`, `true Stable 1.33-`. Independent confirmation from the upstream CHANGELOG-1.29.md: "The SidecarContainers feature has graduated to beta and is enabled by default (#121579)"; CHANGELOG-1.33.md: "The SidecarContainers feature has graduated to GA. 'SidecarContainers' feature gate was locked to default value and will be removed in v1.36 (#129731)". The v1.33 release blog (2025-04-23) states "Sidecar containers graduate to stable in v1.33 ... KEP-753: Sidecar Containers led by SIG Node." KEP-753 README milestone table: Alpha 1.28, Beta 1.29, GA 1.33. Note: v1.33 also shipped a temporary `LegacySidecarContainers` gate (disabled by default, v1.33 only), which CHANGELOG-1.36.md reports as "completely removed (#131463)".

3) Startup ordering: docs: "they benefit from the same ordering and sequential guarantees as regular init containers"; "After a sidecar-style init container is running (the kubelet has set the started status ... to true), the kubelet then starts the next init container." KEP: "Regular containers should start in parallel after all regular init containers have completed and all restartable init containers have started." Nuance: the kubelet gates on 'started' (startupProbe success or postStart completion), not on readiness.

4) Termination: docs sidecar page: "the kubelet postpones terminating sidecar containers until the main application container has fully stopped. The sidecar containers are then shut down in the opposite order of their appearance in the Pod specification." Pod-lifecycle page "Pod shutdown and sidecar containers": "the kubelet will delay sending the TERM signal to these sidecar containers until the last main container has fully terminated. The sidecar containers will be terminated in the reverse order they are defined in the Pod spec." CHANGELOG-1.29: "Sidecar termination is now serialized and each sidecar container will receive a SIGTERM after all main containers and later starting sidecar containers have terminated (#120620)."

5) Probes: init-containers page: "init containers do not support lifecycle, livenessProbe, readinessProbe, or startupProbe whereas sidecar containers support all these probes to control their lifecycle." Sidecar page: "If a readinessProbe is specified for this init container, its result will be used to determine the ready state of the Pod." v1.33 blog: "sidecars can utilize probes (startup, readiness, liveness)". KEP-753: "All probes (startup, readiness, liveness)".

6) Resources: init-containers page: "Init containers support all the fields and features of app containers, including resource limits". Sidecar page has a "Resource sharing within containers" section; scheduling uses the 'effective' request/limit rules (highest init-container request vs. sum of app containers), and CHANGELOG-1.33 adds "support for in-place vertical scaling of Pods with sidecars (#128367)". KEP: sidecars "will be used for Pod QoS calculation as all other containers". So sidecars do carry their own requests/limits, but they are folded into the Pod's effective request via the init/sidecar accounting rules rather than simply summed independently.

License: not a code artifact; Kubernetes docs are CC BY 4.0 per page footer; Kubernetes itself is Apache-2.0 (not separately verified here). No CRD is involved; the only config surface is the `restartPolicy: Always` field on entries in `spec.initContainers`.

**Implication for VICE.** The primitive is safe to build on: on any cluster at v1.29+ native sidecars work by default, and on v1.33+ they cannot be disabled, so VICE's app-exposer/pod builder can emit credential-broker, egress-proxy, FUSE-mounter and agent-runner containers as `spec.initContainers` entries with `restartPolicy: Always` and no feature-gate dependency. Design notes from the verified behavior: (a) order sidecars in the list by dependency (e.g. broker -> proxy -> mounter) because the kubelet starts the next one only after the previous is 'started'; give each a startupProbe so 'started' means actually serving, since ordering does not wait for readiness; (b) a readinessProbe on a sidecar gates the Pod's Ready condition, so the DE's ingress/Service will not route to the IDE until, say, the FUSE mount or credential broker is healthy; (c) on stop, the kubelet only TERMs sidecars after the IDE container exits and does so in reverse order, so the FUSE mounter/broker stay up while the IDE flushes; a slow IDE shutdown delays sidecar teardown, so keep terminationGracePeriodSeconds in mind; (d) the sidecar requests are folded into the Pod's effective request, so they must be counted in VICE's per-analysis resource quotas; (e) confirm the CyVerse production cluster version is >= 1.29 (ideally >= 1.33) before relying on this; the v1.33 changelog also fixed named-port exposure from sidecars via Services (#128850), relevant if a proxy sidecar is the Service target.

### [confirmed] User namespaces (pod.spec.hostUsers: false) reached GA in Kubernetes v1.36; requirements are Linux 6.3+ (idmap mounts on tmpfs), containerd 2.0+ or CRI-O 1.25+, runc 1.2+/crun 1.9+, a 'kubelet' system user and getsubids on PATH; UID/GID 0-65535 are mapped, capabilities such as CAP_SYS_ADMIN are limited to the pod's user namespace, runAsUser/runAsGroup/fsGroup always mean container-side IDs, and it cannot be combined with hostNetwork/hostPID/hostIPC.

**Evidence.** Every element of the claim checks out against primary sources; only one nuance (hostNetwork) deserves a footnote.

GA status: The upstream v1.36.0 changelog (kubernetes/kubernetes CHANGELOG-1.36.md, "Changelog since v1.35.0") states "Graduated the `UserNamespacesSupport` feature gate to GA. (#136792, @rata)". The GitHub release v1.36.0 was published 2026-04-22T17:57Z. The docs feature-gate definition (UserNamespacesSupport.md in kubernetes/website) lists: alpha 1.28-1.29, beta default-false 1.30-1.32, beta default-true 1.33-1.35, stable+locked from 1.36. The docs page renders "Feature state: Stable since Kubernetes v1.36" and says the gate is locked and ignored if set. The GA blog post "Kubernetes v1.36: User Namespaces in Kubernetes are finally GA" has front-matter date 2026-04-23T10:35:00-08:00 and slug kubernetes-v1-36-userns-ga (URL https://kubernetes.io/blog/2026/04/23/kubernetes-v1-36-userns-ga/), matching the claimed April 23, 2026 date. The claim is still current as of 2026-09: a v1.37 blog post dated 2026-09-04 ("KubeletInUserNamespace (aka Rootless mode) Graduates to Beta") refers to pod user namespaces as "`hostUsers: false` with the `UserNamespacesSupport` feature gate, GA since v1.36" and explicitly distinguishes it from the separate rootless-kubelet feature.

Requirements (docs source user-namespaces.md, kubernetes/website main): "In practice this means you need at least Linux 6.3, as tmpfs started supporting idmap mounts in that version"; "crun version 1.9 or greater (it's recommend version 1.13+)"; "runc version 1.2 or greater"; "containerd: version 2.0 (and later) supports user namespaces for containers"; "CRI-O: version 1.25 (and later)"; "A user `kubelet` in the system (you cannot use any other username here)"; "The binary `getsubids` installed (part of shadow-utils) and in the PATH for the kubelet binary"; plus subordinate UID/GID configuration for the kubelet user and idmap-mount support on the filesystem backing /var/lib/kubelet/pods/. Independent confirmation: containerd's own docs/user-namespaces/README.md lists for "Kubernetes 1.27 and greater": Linux 6.3 or greater, containerd 2.0 or greater, runc 1.2 or greater, crun 1.9 or greater, and "all the file-systems used by the volumes in the pod need kernel-support for idmap mounts" (btrfs, ext4, xfs, fat, tmpfs, overlayfs listed). It also warns that with containerd 1.6 or older, hostUsers: false is silently ignored.

UID/GID range: docs: "By default, the valid UIDs/GIDs when this feature is enabled is the range 0-65535. This applies to files and processes (runAsUser, runAsGroup, etc.)"; files outside the range appear as the overflow ID (usually 65534) and cannot be modified. KEP-127 README: "The mapping length will be 65536, mapping the range 0-65535 to the pod." The kubelet assigns host IDs above 0-65535.

Capabilities: docs: "`CAP_SYS_ADMIN` is limited to the pod's user namespace and invalid outside of it"; "`CAP_SYS_MODULE` does not have any effect if granted to a pod using user namespaces". KEP-127 goal: "Allow pods to have capabilities (e.g. CAP_SYS_ADMIN) that are only valid in the pod (not valid in the host)."

runAsUser semantics: docs: "The runAsUser, runAsGroup, fsGroup, etc. fields in the pod.spec always refer to the user inside the container. These users will be used for volume mounts ... therefore the host UID/GID will not have any effect on writes/reads from volumes the pod can mount," including hostPath.

Host namespaces: docs "Limitations" section: "if you set `hostUsers: false` then you are not allowed to set any of: hostNetwork: true, hostIPC: true, hostPID: true." Also: "No container can use `volumeDevices` (raw block volumes)". NUANCE: the v1.36 changelog adds a `UserNamespacesHostNetwork` runtime handler tied to the `UserNamespacesHostNetworkSupport` feature gate (docs list it as alpha, default false, from 1.35) which "only takes effect when the container runtime's UserNamespacesHostNetwork runtime handler returns true and the NodeDeclaredFeatures feature gate is enabled"; when enabled, "pods are allowed to use both hostNetwork and User Namespaces simultaneously". So the hostNetwork exclusion is the default behavior but is being relaxed via an alpha gate; hostPID/hostIPC remain excluded.

License: not applicable to the claim (Kubernetes docs are CC BY 4.0 per the site footer; no license assertion was made in the claim). The docs' example failure message shows what happens on an unsupported filesystem: "failed to set MOUNT_ATTR_IDMAP on ${your mount path} invalid argument (maybe the filesystem used doesn't support idmap mounts on this kernel?)".

**Implication for VICE.** The claim holds, so VICE can plan on hostUsers: false as a GA, gate-locked feature on any v1.36+ cluster (and it remains current at v1.37). Practical consequences: (1) Node audit is mandatory: kernel >= 6.3, containerd 2.x (containerd 1.6 silently ignores hostUsers: false; 1.7 works only with older limitations), runc >= 1.2 or crun >= 1.9 (1.13+ recommended), a system user literally named 'kubelet' with /etc/subuid and /etc/subgid entries, and getsubids in the kubelet's PATH. (2) Volume filesystems are the biggest risk: every volume the pod mounts, plus the filesystem under /var/lib/kubelet/pods, must support idmap mounts; docs list btrfs/ext4/xfs/fat/tmpfs/overlayfs. NFS, iRODS FUSE mounts, and CSI drivers used by VICE are not listed and must be tested; an unsupported filesystem makes the pod fail with a MOUNT_ATTR_IDMAP 'invalid argument' error rather than degrade gracefully. (3) Because runAsUser/fsGroup and volume writes use container-side IDs, the chown-home-volume workaround becomes unnecessary only for IDs in 0-65535; files owned by IDs outside that range show up as the overflow ID (65534) and are read-only, so VICE should confirm all research-user UIDs on shared volumes fall inside that range or extend the range via the documented kubelet knob. (4) CAP_SYS_ADMIN is confined to the pod's userns, which supports the idea of allowing FUSE inside the pod without host exposure, but whether FUSE actually mounts inside a userns pod still depends on /dev/fuse access and the runtime, which this check did not verify. (5) Pods with hostUsers: false cannot use hostNetwork/hostPID/hostIPC or raw block volumeDevices; the hostNetwork exclusion is only relaxable via the alpha UserNamespacesHostNetworkSupport gate plus runtime support, so do not depend on it. (6) Under Pod Security Standards, hostUsers: false pods may set any capabilities.add at the baseline level, which is useful if VICE runs under baseline PSS.

### [partially_true] meta-fuse-csi-plugin (pfnet-research) mounts any FUSE implementation without privileged:true or CAP_SYS_ADMIN by having a privileged CSI DaemonSet open /dev/fuse and pass the fd over a Unix socket ('fuse-starter') or via a modified 'fusermount3-proxy'; the FUSE process must run as a restartable init (sidecar) container, minimum Kubernetes v1.30, and it supports mountpoint-s3, goofys, s3fs, ros3fs, gcsfuse and sshfs. The repo's last push was 2024-10-23 (97 stars, Apache-2.0).

**Corrected claim.** meta-fuse-csi-plugin (pfnet-research, Apache-2.0, forked from gcs-fuse-csi-driver) lets a user pod mount FUSE filesystems without privileged:true or CAP_SYS_ADMIN: a privileged CSI driver DaemonSet (holding CAP_SYS_ADMIN) opens /dev/fuse and performs mount(2), then passes the fd over a Unix Domain Socket to the pod, either via 'fuse-starter' (cmd/fuse_starter; for FUSE impls that accept an fd such as /dev/fd/X) or via 'fusermount3-proxy' (cmd/fusermount3-proxy; a drop-in fusermount3 that proxies the mount to the driver, located through env var FUSERMOUNT3PROXY_FDPASSING_SOCKPATH). ## Findings

### Native sidecar containers are declared as initContainers with restartPolicy: Always, are stable since Kubernetes v1.33 (feature gate SidecarContainers enabled by default since v1.29 and locked in v1.33), start in order before app containers, are terminated only after the main container stops (in reverse order), and support startupProbe/readinessProbe/livenessProbe and their own resource requests.

- Confidence: high (load-bearing); source: <https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/> (current docs, fetched 2026-09-06)
- Evidence: 'Sidecar containers are declared in the initContainers field with restartPolicy: Always'; 'Stable since Kubernetes v1.33'; 'Kubelet postpones terminating sidecar containers until the main application container has fully stopped'; 'If a readinessProbe is specified for a sidecar init container, its result determines the Pod's ready state'.
- Relevance to VICE: This is the pod-level primitive for splitting today's monolithic VICE container: credential broker, egress proxy, FUSE mounter and each autonomous agent runner can be a native sidecar that starts before the user's IDE and outlives it, with probes gating readiness.

### User namespaces (pod.spec.hostUsers: false) reached GA in Kubernetes v1.36; requirements are Linux 6.3+ (idmap mounts on tmpfs), containerd 2.0+ or CRI-O 1.25+, runc 1.2+/crun 1.9+, a 'kubelet' system user and getsubids on PATH; UID/GID 0-65535 are mapped, capabilities such as CAP_SYS_ADMIN are limited to the pod's user namespace, runAsUser/runAsGroup/fsGroup always mean container-side IDs, and it cannot be combined with hostNetwork/hostPID/hostIPC.

- Confidence: high (load-bearing); source: <https://kubernetes.io/docs/concepts/workloads/pods/user-namespaces/> (2026-04-23 (GA blog) / current docs)
- Evidence: 'Stable since Kubernetes v1.36'; 'Minimum: Linux 6.3 (required for idmap mount support in tmpfs)'; 'containerd: version 2.0+; CRI-O: version 1.25+'; 'CAP_SYS_ADMIN: Limited to pod's user namespace; invalid outside it'; 'All filesystems used in pod volumes must support idmap mounts'. GA blog dated April 23, 2026.
- Relevance to VICE: Lets VICE keep in-image UID 0 or namespaced CAP_SYS_ADMIN (e.g., for FUSE) without exposing the node, and removes the need to chown home volumes. It forces a node prerequisite audit (kernel >= 6.3, containerd 2.x, idmap-capable CSI/NFS/iRODS volume filesystems) before it can be relied on.

### Mounting FUSE filesystems inside an unprivileged container is not enabled by default even though the kernel allows it inside a user namespace: moby PR #41880 ('Allow mounting FUSE filesystems without CAP_SYS_ADMIN or AppArmor/SecComp custom profiles') states that 'Kernel 4.18 enabled safe unprivileged FUSE mounts within a user namespace' but was never merged because default seccomp/AppArmor profiles block mount/umount/unshare; a custom seccomp profile (and namespaced CAP_SYS_ADMIN under hostUsers: false) is still required.

- Confidence: medium (load-bearing); source: <https://github.com/moby/moby/pull/41880> (opened 2021, still open at fetch 2026-09-06)
- Evidence: PR title quoted above; 'Not merged. The PR remains open'; AppArmor change 'Permits mount operations with fstype fuse and fuse.*'; SecComp change 'Adds whitelist entries for mount, umount, and unshare syscalls'.
- Relevance to VICE: Running s3fs/irods-fuse directly in the user container on a hostUsers:false pod is plausible only with a custom seccomp profile allowing mount and with CAP_SYS_ADMIN added inside the userns; that combination fails the Restricted Pod Security Standard, so a sidecar/CSI design is safer.

### meta-fuse-csi-plugin (pfnet-research) mounts any FUSE implementation without privileged:true or CAP_SYS_ADMIN by having a privileged CSI DaemonSet open /dev/fuse and pass the fd over a Unix socket ('fuse-starter') or via a modified 'fusermount3-proxy'; the FUSE process must run as a restartable init (sidecar) container, minimum Kubernetes v1.30, and it supports mountpoint-s3, goofys, s3fs, ros3fs, gcsfuse and sshfs. ### Scanner roles: hadolint (v2.15.1, 2026-07-31, GPL-3.0) lints Dockerfiles with rules such as DL3002 'Last user should not be root', DL3006/DL3007 (pin tags, no latest), DL3008 (pin apt versions) and runs ShellCheck on RUN lines; dockle (v0.4.15, 2025-01-06, Apache-2.0) audits built images against CIS-DI-0001 'Create a user for the container', CIS-DI-0008 setuid/setgid files, CIS-DI-0010 credentials in env/files, with goodwithtech/dockle-action; Trivy emits CycloneDX/SPDX SBOMs ('trivy image --format cyclonedx') and rescans them ('trivy sbom'); Grype is a faster vuln-only second opinion that shares a Syft SBOM.

- Confidence: high; source: <https://github.com/hadolint/hadolint> (releases 2026-07-31 (hadolint), 2025-01-06 (dockle))
- Evidence: hadolint README rule texts; dockle README checkpoint IDs; Trivy doc commands; comparison articles: 'Grype is consistently 30-40% faster for pure vulnerability scanning', 'running Trivy and Grype together widens CVE coverage'.
- Relevance to VICE: DL3002 and CIS-DI-0001/0008 directly test the no-root/no-setuid invariant (a sudo binary is setuid and would trip CIS-DI-0008), making the hardening rule machine-checkable in CI.

### Dev Container Features are OCI-distributed folders (devcontainer-feature.json + install.sh) whose install.sh 'executes as the root user during container image building', receive _REMOTE_USER/_CONTAINER_USER and option env vars, are ordered by dependsOn/installsAfter, and each becomes a separate image layer; the Codespaces 'universal' image is composed this way (common-utils, node, python, conda, docker-in-docker, etc.) with remoteUser/containerUser 'codespace', userUid 1000, userGid 1000, and Anthropic publishes ghcr.io/anthropics/devcontainer-features/claude-code:1.0.

- Confidence: high; source: <https://containers.dev/implementors/features/> (fetched 2026-09-06)
- Evidence: containers.dev spec quotes; universal devcontainer.json: remoteUser codespace, userUid 1000; Claude docs: '"ghcr.io/anthropics/devcontainer-features/claude-code:1.0": {}'.
- Relevance to VICE: Features are a viable composition unit for the VICE family (one feature per agent CLI/MCP server, run via devcontainer CLI build in Bake), but because install.sh runs as root at build time only, they are compatible with a final USER 1000 and no runtime sudo.

### Apptainer runs every OCI image as the calling user, ignores the Dockerfile USER instruction, mounts the image read-only (use --writable-tmpfs), binds $HOME, /tmp, /etc/passwd and $PWD by default, and its docs advise installing software to /usr or /opt rather than /root or a user home and testing with docker run --read-only.

- Confidence: high; source: <https://apptainer.org/docs/user/main/docker_and_oci.html> (current docs, fetched 2026-09-06)
- Evidence: 'Apptainer always runs as the calling user. The USER instruction in Dockerfiles is ignored'; 'Install software to system locations (/usr, /opt) rather than /root or user home directories'; default binds list includes /etc/passwd.
- Relevance to VICE: A VICE image that is UID-agnostic, installs everything under /opt or /usr, and tolerates a read-only root filesystem will also run unchanged on UNM CARC HPC under Apptainer, which the MESA collaboration needs.

### Commercial agent images still run as root or with passwordless sudo: openai/codex-universal is Ubuntu 24.04 with sudo installed and no USER instruction; Gitpod's base is buildpack-deps:jammy@sha256 with 'useradd -l -u 33333 -G sudo -md /home/gitpod' and '%sudo ALL=NOPASSWD:ALL'; Codespaces' universal image runs as codespace uid 1000. Anthropic's cloud environment gives each session a fresh Ubuntu 24.04 x86_64 VM where setup scripts 'run as root', holds the GitHub token in a proxy outside the VM ('your token never enters the container'), attaches stored API credentials via an agent proxy after requests leave the VM, and offers network levels None/Trusted/Custom; Claude Code 'refuses to start with [--dangerously-skip-permissions] when running as root', and its reference devcontainer needs NET_ADMIN/NET_RAW only for init-firewall.sh with remoteUser node.

- Confidence: high; source: <https://code.claude.com/docs/en/cloud-environments> (fetched 2026-09-06)
- Evidence: codex-universal Dockerfile: 'does not include a USER instruction ... sudo is installed'; Gitpod Dockerfile lines quoted; cloud-environments doc: 'Scripts run as root on Ubuntu 24.04', 'The key never reaches Claude, the commands it runs, or the session's environment variables'; sandbox doc quote on root refusal.
- Relevance to VICE: The credential-proxy pattern (secrets attached outside the agent's trust boundary) is the design VICE should copy with a sidecar broker fronting iRODS/OSN/AI Verde keys, and the root-refusal means the agent runner container must be non-root anyway.

### Coder's Agent Firewall (formerly Agent Boundaries; binary coder/boundary v0.10.0, 2026-07-07, MIT) is a process-level firewall for any terminal-based agent using an nsjail (Linux namespaces) or landjail (Landlock V4) jail plus an HTTP proxy on port 8080, configured by ~/.config/coder_boundary/config.yaml allowlist rules (domain=, method=, path=); Coder's docs place it under AI Governance in the Premium license, and it is installed into the workspace image or at startup.

- Confidence: medium; source: <https://coder.com/docs/ai-coder/agent-boundary> (docs reference Coder v2.37; release 2026-07-07)
- Evidence: 'process-level firewall that restricts and audits what autonomous programs, such as AI agents, can access'; 'nsjail: Uses Linux namespaces with network namespace isolation (default)'; 'landjail: Uses Landlock V4'; 'Part of AI Governance, included with Coder's Premium license'; gh: license MIT, v0.10.0.
- Relevance to VICE: The boundary binary itself is MIT and could wrap each agent inside a VICE agent sidecar (userns + Landlock need no root when hostUsers:false), independent of the Coder product license; needs legal review of the docs' Premium framing versus the repo license.

### Zero-to-JupyterHub's default hardening adds a privileged initContainer that runs iptables to block the cloud metadata endpoint 169.254.169.254 (singleuser.cloudMetadata.blockWithIptables), prefers a NetworkPolicy instead when a CNI supports it, restricts user-pod egress to hub/proxy by default, and gives user pods no Kubernetes API credentials; 2i2c and Pangeo discussions show container securityContext for singleuser pods (runAsNonRoot, allowPrivilegeEscalation: false) is set via KubeSpawner.

- Confidence: medium; source: <https://z2jh.jupyter.org/en/stable/administrator/security.html> (stable docs, fetched 2026-09-06)
- Evidence: 'an initContainer is added to the user pods' with elevated privileges for iptables; 'By default, user pods cannot access Kubernetes API credentials'; forum: 'runAsNonRoot: true, allowPrivilegeEscalation: false, and privileged: false in the container security context'.
- Relevance to VICE: VICE's app-exposer should mirror this: no service-account token automount in user pods, NetworkPolicy-based metadata block, and an egress proxy sidecar rather than a privileged iptables init container.

### Jupyter AI v3.2.0 treats agents and models as 'personas', connects external agents via the Agent Client Protocol (ACP) including Claude, exposes JupyterLab operations as MCP tools through a Jupyter MCP server, and lets users register custom MCP servers in .jupyter/mcp_settings.json.

- Confidence: medium; source: <https://jupyter-ai.readthedocs.io/en/latest/users/index.html> (v3.2.0 docs, fetched 2026-09-06)
- Evidence: 'A persona is the integration point for an agent or model; it is not the model itself'; 'Jupyter MCP server exposes notebook and JupyterLab operations as MCP tools'; 'configure custom MCP servers in .jupyter/mcp_settings.json'.
- Relevance to VICE: The JupyterLab family member can host agents through ACP personas talking to an agent sidecar over localhost, so the agent process (and its OAuth tokens) need not live in the notebook container's UID.

## Recommendations

- Adopt one hardened base image (Ubuntu 24.04) with a fixed identity 'user' UID 1000 / GID 100 (matching docker-stacks jovyan and Kasm kasm-user so existing VICE volumes stay compatible), no sudo package, final USER 1000, ENTRYPOINT tini, everything installed under /opt or /usr, and a docker-stacks-style passwd-append shim for arbitrary UIDs; enforce with hadolint DL3002 and dockle CIS-DI-0001/CIS-DI-0008 in CI.
- Rebuild the RStudio member on the OOD recipe instead of rocker's /init: install rstudio-server via rocker's install scripts but launch 'rserver --server-user=$(whoami) --auth-none 1 --www-port 8787 --server-data-dir=/tmp/run --database-config-file=<user-writable>' as UID 1000 behind the DE auth proxy; drop init_userconf.sh, s6 and ROOT=true entirely.
- Build the KasmVNC desktop from the kasmtech workspaces-core pattern (useradd -u 1000, USER 1000, vncserver with ~/.vnc/kasmvnc.yaml and ~/.kasmpasswd) rather than lsiobase/kasmvnc, which is root+s6+passwordless sudo by design; keep DRI3 via /dev/dri device requests only.
- Move every privileged boot step out of the image into pod spec: fsGroup: 100 with fsGroupChangePolicy: OnRootMismatch for home/iRODS volumes, NetworkPolicy for metadata blocking, and native sidecars (initContainers + restartPolicy: Always) for (a) a credential-broker that holds iRODS/OSN/AI Verde/Anthropic keys and exposes them only as short-lived tokens or an HTTP proxy that injects headers (copying Anthropic's agent-proxy model), (b) an egress allowlist proxy, and (c) one agent-runner sidecar per autonomous job running as a different UID than the human, sharing only the project volume.
- Enable hostUsers: false on the VICE node pool once nodes are on kernel >= 6.3 and containerd 2.x, and verify idmap support for the iRODS CSI/NFS volume classes; treat this as the prerequisite for any in-pod FUSE and for Sysbox if agent-side Docker builds are ever needed.
- For s3fs/OSN and iRODS FUSE, prototype meta-fuse-csi-plugin (fork it under cyverse) with the FUSE client as a sidecar and a startupProbe on the mountpoint; keep nextflow-io/k8s-fuse-plugin + userns + a mount-allowing seccomp profile as plan B, and prefer a non-FUSE path (irods CSI driver, rclone/mountpoint via sidecar) for the human container so it stays Restricted-PSS compliant.
- Express the family as a single docker-bake.hcl: target base -> matrix over app = [jupyterlab, rstudio, code-server, kasmvnc, cli] x accel = [cpu, cuda] using contexts = { base = 'target:base' }, shared attest = ['type=provenance,mode=max','type=sbom'], registry cache-from/cache-to, and RUN --mount=type=cache for apt/pip/uv; add agent CLIs and MCP servers as digest-pinned COPY --from tool images or Dev Container Features rather than curl|sh.
- Wire Renovate with docker:pinDigests plus a regex customManager driven by '# renovate: datasource=github-releases depName=...' comments on every ARG that names a downloaded binary (ttyd, code-server, KasmVNC deb, Claude Code, Codex, OpenCode, Goose); require Trivy and Grype gates, cosign keyless signing (OpenBao as KMS if you want org-held keys), and SLSA-3 provenance via slsa-github-generator; have app-exposer or an admission policy refuse unsigned images.
- Run each agent as a non-root user in its own sidecar with a Landlock/nsjail wrapper (coder/boundary is MIT) or bubblewrap, with agent OAuth/config dirs on a per-agent emptyDir rather than the human's $HOME; this also satisfies Claude Code's refusal to run bypass mode as root and lets long autonomous jobs continue while the human's IDE container restarts.
- Keep images Apptainer-clean (no runtime writes to the image, no USER dependence, ldconfig at build) so the same OCI artifacts run on UNM CARC for MESA, and add 'docker run --read-only -u 65534' as a CI smoke test.

## Open questions

- What kernel, containerd version and volume filesystems (iRODS CSI, NFS, Ceph) do the current CyVerse VICE nodes run, and do they support idmap mounts required by hostUsers: false?
- Does the iRODS FUSE client (irods-fuse / irods-vfs-client) work with meta-fuse-csi-plugin's fusermount3-proxy, or must VICE rely on a non-FUSE iRODS CSI/rclone path?
- Will CyVerse maintain a fork of meta-fuse-csi-plugin given no upstream activity since October 2024?
- Can rserver --auth-none behind the DE's proxy satisfy CyVerse's session-security expectations, or is a PAM helper (as OOD uses with --auth-pam-helper-path) required?
- Is coder/boundary's MIT repo license sufficient to use it independently of Coder's Premium 'AI Governance' packaging?
- Does the DE's app-exposer already support initContainers with restartPolicy: Always, per-container securityContext, fsGroup and extended resources (nextflow.io/fuse, nvidia.com/gpu) in generated pod specs?
- How should per-agent UIDs map onto a shared project volume: fsGroup with setgid directories, or ACLs, given Apptainer/HPC reuse of the same home layout?
