# Kubernetes agent substrates (agent-sandbox, Agent Substrate, kagent, OpenShell, ToolHive)

Dimension key: `k8s-agent-substrates`. Date: 2026-09-06.

## Summary

The two candidates the team named are different layers, not competitors. "Agent Sandbox" (kubernetes-sigs/agent-sandbox, SIG Apps, Apache-2.0, v1.0.1 released 2026-09-03, ~3.75k stars) is a CRD-level pod primitive: Sandbox (agents.x-k8s.io/v1beta1) plus SandboxTemplate/SandboxClaim/SandboxWarmPool (extensions.agents.x-k8s.io/v1beta1), with isolation delegated to runtimeClassName (gvisor or kata-qemu), stable hostname, volumeClaimTemplates, shutdownTime TTLs, and a Go sandbox-router that now does browser path-based routing with session-cookie auth. That maps almost one-to-one onto VICE's existing "one pod per analysis" model and is the safest thing to adopt first. "Agent Substrate" (github.com/agent-substrate/substrate, Google-originated, v0.0.x, self-described "not ready for production use") is a separate high-density actor/worker multiplexing layer (WorkerPool CRD, ActorTemplate, gVisor or Kata+Cloud Hypervisor sandbox classes, snapshots to S3/GCS, PostgreSQL control plane) that kagent's SandboxAgent CRD targets; it is a watch item, not a 2026 deployment target. kagent (CNCF Sandbox, v0.10.0 on 2026-09-04, kagent.dev/v1alpha2: Agent, ModelConfig, ModelProviderConfig, RemoteMCPServer, SandboxAgent; ToolServer removed in favor of kmcp/MCPServer) gives declarative agents, requireApproval/ask_user human-in-the-loop, OIDC via oauth2-proxy, and a "claude ACP sandbox target", but it is a DevOps-agent framework rather than a per-user IDE sandbox. The most direct answer to VICE problem (a), credentials readable by every agent, is NVIDIA OpenShell (Apache-2.0, alpha, v0.0.116): its Kubernetes driver is built on top of the agent-sandbox CRDs, its "providers v2" replaces every credential in the agent environment with an opaque placeholder that a sandbox-side proxy resolves only for allow-listed host/port/path, policies are Landlock-enforced filesystem rules plus default-deny per-binary network rules with MCP-aware matching, and GPUs map to nvidia.com/gpu; the caveat is its Helm chart is explicitly "do not use in production". For MCP hosting with secrets, Stacklok ToolHive's operator (toolhive.stacklok.dev/v1beta1 MCPServer etc., v0.46.0) with Vault-Agent-Injector-style injection and OIDC/Cedar authz is the most mature open option, with agentgateway (now an AAIF/Linux Foundation project, v1.5.0) as the LLM/MCP/A2A gateway. GPU support is the load-bearing constraint: Agent Sandbox itself is GPU-agnostic (plain pod resources), gVisor needs runsc --nvproxy, Agent Substrate only allows nvidia.com/gpu on gvisor-class WorkerPools, and Kata needs VFIO passthrough; keep vLLM/Ollama as shared cluster services behind a gateway rather than inside sandboxes. Peers to skip for VICE: Daytona (went closed-source June 2026), E2B infra (Firecracker on Nomad/Terraform, GCP-first, no Kubernetes), microsandbox (libkrun, no Kubernetes), Ona/Gitpod (acquired by OpenAI June 2026, managed service), Coder Tasks (removed from v2.37). OpenSandbox (Apache-2.0, 15k stars, Kubernetes operator with gVisor/Kata/Firecracker, egress sidecar with Credential Vault) is a credible alternative sandbox platform but is API-server-centric rather than CRD-centric and its egress sidecar has a documented incompatibility with gVisor.

### [partially_true] Agent Sandbox delegates isolation entirely to Kubernetes RuntimeClass: setting spec.podTemplate.spec.runtimeClassName to gvisor or kata-qemu is the whole configuration; direct kubectl port-forward does not work under gVisor/Kata so the project's sandbox-router must be used as the single entry point.

**Corrected claim.** Agent Sandbox (kubernetes-sigs, SIG Apps, Apache-2.0; v1.0.0 released 2026-08-28, v1.0.1 on 2026-09-03; API agents.x-k8s.io/v1beta1 is now the only served version) delegates container-escape isolation to a secure runtime selected via the standard spec.podTemplate.spec.runtimeClassName field (docs show `gvisor` and `kata-qemu`; the AKS example uses `kata-vm-isolation`), and the docs do say a workload can be hardened "by adding this single field to the pod spec". But the RuntimeClass is not the whole story: the RuntimeClass/runtime must already be installed on nodes (gVisor node setup; Kata needs nested virtualization or a Kata-capable node pool), and when sandboxes are created via a SandboxTemplate the controller adds its own controls by default: a Managed NetworkPolicy (`networkPolicyManagement: Managed` is the default) that allows ingress only from the Sandbox Router and egress only to the public Internet (blocking RFC1918 and metadata endpoints), `automountServiceAccountToken` defaulted to false, and filtering of system labels. `kubectl port-forward` directly to the pod genuinely fails under Kata (kubelet dials 127.0.0.1 in the host-side netns; Kata has never implemented CRI port-forward, canonical issue #1693 open since 2018 and reconfirmed by a maintainer on 2026-07-10) and under gVisor's default netstack (the listener lives in the userspace network stack, nothing is bound in the host netns). However, the sandbox-router is NOT mandatory: the project's own threat model lists "Sandbox Router (Optional)", the openclaw-gvisor example exposes gVisor sandboxes via a NodePort/LoadBalancer Service plus an IAP tunnel instead of the router, and the Kata AKS example offers `kubectl exec` as an alternative. What breaks is specifically the port-forward (CRI streaming) path, not Service/pod-IP reverse proxying; the router simply becomes the only permitted ingress if you keep the default Managed NetworkPolicy.

Also note the CRDs are v1beta1 (v1alpha1 removed in 1.0.0), and upgrades from <0.5.0 require a migration path.

## Recommendations

- Adopt kubernetes-sigs/agent-sandbox (agents.x-k8s.io/v1beta1) as the pod primitive for 'AI Sandboxes': have the DE's app-exposer/VICE launcher create one Sandbox per analysis (or a SandboxClaim against a per-app SandboxTemplate) instead of a raw Deployment; map VICE time limits to spec.shutdownTime/shutdownPolicy: Delete, the user's home to volumeClaimTemplates, and evaluate FUSE CSI for iRODS mounts. Keep the existing one-pod-per-user model; nothing about the DE's app catalog needs to change.
- Express 'security levels' as three SandboxTemplates that differ only in podTemplate.spec.runtimeClassName: L0 runc (today's behavior, GPU as-is), L1 gvisor (enable runsc --nvproxy on GPU node pools so nvidia.com/gpu still works), L2 kata-qemu (strongest boundary, no GPU unless VFIO passthrough via the NVIDIA GPU Operator kata mode). Because port-forward-style access breaks under gVisor/Kata, front analyses with the Go sandbox-router in --path-routing-prefix mode with session-cookie auth and scoped tokens, and wire the DE's Keycloak login to mint those tokens.
- Layer NVIDIA OpenShell on top of Agent Sandbox for credential isolation and policy (problems a and b): run each bundled agent (Claude Code, Codex, OpenCode) as an OpenShell sandbox whose Kubernetes driver reuses the same agent-sandbox CRDs; register AI Verde (llm-api.cyverse.ai), Anthropic/OpenAI/Gemini, GitHub and OSN S3 keys as 'providers v2' so the agent sees only placeholders bound to those hosts; ship per-app policy presets (Landlock filesystem_policy limiting reads to the project directory, network_policies with MCP tool-name matching for iRODS/mesa/formation MCP). Treat this as a 2026 pilot, not GA, because the Helm chart is labelled experimental; keep the Agent Sandbox layer independent so OpenShell can be swapped.
- Move the three MCP servers (iRODS Data Store, mesa-mcp, formation-mcp) out of the user pod into Stacklok ToolHive MCPServer resources (toolhive.stacklok.dev/v1beta1) with oidcConfigRef bound to the DE's OIDC provider, Cedar authzConfig per tool, permissionProfile 'network', and secrets injected via the Vault-Agent-Injector annotation path pointed at OpenBao; agents then reach tools over streamable-http with the user's identity rather than a shared iRODS password on disk. Verify OpenBao's injector honors the vault.hashicorp.com annotations before committing.
- Put agentgateway (AAIF/Linux Foundation, v1.5.x) in front of all LLM and MCP traffic as the single choke point: unified OpenAI-compatible route to AI Verde, Anthropic, OpenAI and Gemini with per-user JWT auth, CEL RBAC on MCP tools, rate/spend limits and OTel; agents get a short-lived gateway token instead of provider keys, and Claude Code Router/Goose/Antigravity can be pointed at the gateway with no code changes.
- For long-running autonomous jobs (problem c), separate 'human pod' from 'agent worker': launch a second SandboxClaim from the same SandboxTemplate sharing the user's data volume (needs an RWX StorageClass or iRODS/S3 as the shared substrate) and run the agent there via the Anthropic Managed Agents 'ant beta:worker run' pattern (automountServiceAccountToken: false, non-root, read-only rootfs, gVisor); the human's JupyterLab/RStudio/VS Code session keeps running independently and the DE can show both as linked analyses.
- Track, but do not build on, Agent Substrate and kagent SandboxAgent for 'AI Sandboxes v2': they deliver the hibernation/oversubscription VICE needs for idle agents (and a claude ACP sandbox target), but Substrate is v0.0.x with alpha APIs, needs PostgreSQL + S3/GCS + a DaemonSet, and GPUs only work on the gvisor class. Revisit when Substrate publishes a versioned API guarantee; join #substrate-users on CNCF Slack now.
- Use kagent's requireApproval/ask_user pattern (or OpenShell's policy.local approval flow) as the design for human-in-the-loop gates on destructive MCP tools (iRODS delete/move, DE analysis stop, S3 writes), surfaced in the DE UI rather than in a separate kagent dashboard.
- Keep self-hosted vLLM/Ollama as shared, GPU-scheduled cluster services (not per-sandbox) behind agentgateway; only L0/L1 sandboxes should request nvidia.com/gpu directly, and only for user science workloads. Borrow NemoClaw's local-inference privacy-routing idea for UNM CARC / DGX resources.
- Drop Daytona (closed-source), E2B infra (Nomad/GCP), microsandbox (no Kubernetes), Ona (OpenAI-owned managed service) and Coder Tasks (removed in v2.37) from consideration. As an interim hardening for today's runc pods, the MIT-licensed coder/boundary CLI can wrap agents with a domain/path allow-list inside existing VICE images, accepting that it is HTTP-only and needs CAP_NET_ADMIN.

## Open questions

- Does OpenBao's Kubernetes injector honor the vault.hashicorp.com/agent-inject-* annotations that ToolHive's Vault integration and OpenShell's 'HashiCorp Vault' credential backend rely on, or will VICE need a bao-agent sidecar/CSI path instead?
- Has anyone run kubernetes-sigs/agent-sandbox with gVisor + runsc --nvproxy on NVIDIA nodes in production (the docs are silent on GPU); which CUDA/driver versions does nvproxy support for vLLM/Ollama and the VICE GPU apps?
- Is Kata GPU passthrough (NVIDIA GPU Operator sandboxWorkloads/kata mode, VFIO) feasible on CyVerse's and CARC's node hardware, or is L2 (Kata) a CPU-only security level?
- How should the human pod and an autonomous agent sandbox share the user's working directory: RWX PVC, iRODS FUSE under gVisor (FUSE CSI compatibility with runsc), or S3/OSN as the only shared substrate?
- OpenShell's credential placeholders are rewritten at an HTTP proxy; what is the equivalent for the native iRODS protocol (~/.irods/.irodsA) and SSH keys — an iRODS HTTP API/MCP front-end, or SPIFFE-based short-lived iRODS tickets?
- When will OpenShell's Kubernetes driver and Helm chart lose the 'experimental, do not use in production' label, and which agent-sandbox API version will it pin (it currently accepts v1beta1 or v1alpha1)?
- Can the agent-sandbox sandbox-router's scoped-token/session-cookie auth be integrated with the DE's existing Keycloak OIDC session and the current per-analysis ingress, or does VICE keep its own proxy and only use the router in-cluster?
- Which of VICE's bundled agents (Goose, Google Antigravity CLI, Claude Code Router, the 'ant' CLI) have OpenShell adapters; Claude Code, OpenCode and Codex are listed but the others are not.
- Will Agent Substrate be donated to CNCF or SIG Apps (it already uses CNCF Slack), and when will it commit to versioned APIs so kagent SandboxAgent becomes a safe target?
- Does agentgateway's MCP authorization model (CEL RBAC) support per-user delegated identity down to the MCP server (token exchange with RFC 8707 resource indicators as kagent v0.10 does), so iRODS permissions are enforced as the human user rather than a service account?
