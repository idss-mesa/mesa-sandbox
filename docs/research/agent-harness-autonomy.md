# Agent harness autonomy and approvals (Claude Code, Codex, OpenCode, Goose, Antigravity)

Dimension key: `agent-harness-autonomy`. Date: 2026-09-06.

## Summary

Every harness VICE bundles now has a documented non-interactive mode, but they differ sharply in how much of the "unattended + still safe" problem they solve in-harness. Claude Code is the most complete: `claude -p` with `--permission-mode dontAsk|auto`, `--permission-prompts none`, `--allowedTools`, `--max-turns`/`--max-budget-usd`, resumable sessions (`--resume`, SIGTERM leaves the turn resumable), an OS-enforced Bash sandbox (bubblewrap+socat on Linux, with `sandbox.network.allowedDomains` and `sandbox.credentials` deny/mask), `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` to strip credentials from Bash/hooks/MCP subprocesses, and `PreToolUse`/`PermissionRequest` hooks that can be `type: "http"` so a DE-hosted approval service can answer permission requests asynchronously. Codex CLI has an equally explicit model (`sandbox_mode` × `approval_policy`, `codex exec` defaults to read-only, bwrap+seccomp on Linux, `[features.network_proxy]` domain allowlist) but no hook mechanism for remote approval; OpenCode exposes permission decisions over its `opencode serve` HTTP API (`POST /session/:id/permissions/:permissionID`) which is a natural approval-queue integration point, though headless "ask" currently hangs (issue #16367). Goose (`GOOSE_MODE=auto|approve|smart_approve|chat`, `goose run`, `goose schedule --cron`), Gemini CLI (`--approval-mode yolo|auto_edit|default`, container sandbox auto-enabled with yolo) and Antigravity CLI (`agy -p`, soft-deny in headless, `permissions.allow` with `command(...)`/`unsandboxed(...)` rules) all support unattended runs only via pre-declared allow/deny policy; none has a remote-approval hook, so on VICE they should run in locked-down policy mode inside a pod-level sandbox. The strongest architectural pattern across Anthropic (Claude Code on the web / self-hosted environments, Managed Agents self-hosted sandboxes with vault credential substitution at egress), OpenAI (Codex cloud: secrets removed before agent phase, agent-phase internet off by default) and the OWASP/CISA guidance is identical: run the agent as a separate identity in a separate isolated execution unit that shares only the workspace, hold credentials outside the sandbox and inject them at the network egress proxy, allowlist egress, and route anything not pre-approved to an async human checkpoint. For VICE this maps cleanly onto: human interactive pod + separate agent pod/Job (Kubernetes SIG `agent-sandbox` `Sandbox` CRD, v1beta1, Apache-2.0, gVisor/Kata via RuntimeClass) sharing the user's workspace PVC; a DE "approval inbox" service reached by Claude Code HTTP hooks and the OpenCode permissions endpoint; managed-settings.json baked into the images to forbid `bypassPermissions` and pin the sandbox/credential policy; and OpenBao-issued short-lived per-job credentials (iRODS tickets, scoped S3/LLM-gateway tokens) instead of the user's long-lived files. kagent is a Kubernetes-native framework for building ADK service agents (Agent/ToolServer/ModelConfig CRDs) rather than a runtime for coding-CLI harnesses, and Google's "Agent Substrate" (announced 2026-05-20) is a brand-new control plane built on agent-sandbox that is too early to depend on.

## Fact-check verdicts on load-bearing claims

### [confirmed] Claude Code has six permission modes — `default` (Manual), `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions` — selected with `--permission-mode`; `--dangerously-skip-permissions` is equivalent to `--permission-mode bypassPermissions`, is documented for 'Isolated containers and VMs only', refuses to start as root on Linux/macOS, and `dontAsk` is the documented mode for 'Locked-down CI and scripts' where anything not matched by `permissions.allow` rules, the read-only command set, or a PreToolUse hook allow is auto-denied.

**Evidence.** Verified against the primary docs (code.claude.com, fetched 2026-09-06) plus two independent primary sources: the anthropics/claude-code CHANGELOG.md on GitHub and the npm registry. Every element of the claim checks out; only minor refinements apply.

1. Six modes / flag values. The permission-modes page table lists exactly `default` ("Reads only" / "Reviewing every action yourself, sensitive work"), `acceptEdits`, `plan`, `auto` ("Everything, with background safety checks" / "Long tasks, reducing prompt fatigue"), `dontAsk` ("Only pre-approved tools" / "Locked-down CI and scripts"), `bypassPermissions` ("Everything" / "Isolated containers and VMs only"). The CLI reference says `--permission-mode` "Accepts `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`, or `manual` as an alias for `default`" — the `manual` alias requires v2.1.200+, so the flag accepts 7 strings but there are still six modes. `--permission-mode` "Overrides `defaultMode` from settings files."

2. `--dangerously-skip-permissions`. CLI reference: "Skip permission prompts. Equivalent to `--permission-mode bypassPermissions`." Permission-modes page: "The `--dangerously-skip-permissions` flag is equivalent." Warning box: "Only use this mode in isolated environments like containers, VMs, or dev containers without internet access". Recipe table: "Run fully unattended inside a container | `claude -p "<prompt>" --dangerously-skip-permissions` | Required: a container, VM, or the sandbox runtime; on Linux and macOS, run it as a non-root user". Also: "You can't enter `bypassPermissions` from a session you started without it enabled" and it is refused under `--restricted` (v2.1.248+).

3. Root refusal. Permission-modes page: "On Linux and macOS, Claude Code refuses to start in this mode when running as root or under `sudo`: `--dangerously-skip-permissions cannot be used with root/sudo privileges for security reasons`. The check is skipped automatically inside a recognized sandbox." Independently confirmed by the devcontainer page ("The CLI rejects this flag when launched as root, so confirm `remoteUser` is set to a non-root account") and sandbox-environments page ("On Linux and macOS, Claude Code refuses to start with this flag when running as root").

4. `dontAsk`. Permission-modes page: "If you set `dontAsk` mode, Claude Code auto-denies every tool call that would otherwise prompt you. Claude runs only actions matching your `permissions.allow` rules, read-only Bash commands, and calls approved by a PreToolUse hook. Use this mode for CI pipelines or restricted environments". Example: `claude -p "run the test suite" --permission-mode dontAsk --allowedTools "Bash(npm test)" "Read"`. Additional denials the claim omits: explicit `ask` rules are denied rather than prompted; `AskUserQuestion`, MCP tools marked `_meta["anthropic/requiresUserInteraction"]` (v2.1.199+) and org-`ask` connector tools are denied even when an allow rule matches; `rm`/`rmdir` on critical paths (e.g. `rm -rf /`, `rm -rf ~`) are denied even with an allow rule or hook allow. `dontAsk` "never appears in the [Shift+Tab] cycle; set it with `--permission-mode dontAsk`". The headless page independently repeats: "`dontAsk`: Claude Code denies anything not in your `permissions.allow` rules or the read-only command set, which is useful for locked-down CI runs." Read-only set (permissions page): `ls`, `cat`, `echo`, `pwd`, `head`, `tail`, `grep`, `find`, `wc`, `which`, `diff`, `stat`, `du`, `cd`, read-only `git`; not configurable.

5. Deny rules. "Deny rules block in every mode, including `bypassPermissions`... Allow rules have no effect in `bypassPermissions`." Repeated in settings-reference under `permissions.defaultMode`.

6. `permissions.defaultMode` scoping. Settings-reference: "`auto` and `bypassPermissions` don't take effect from project or local settings, so set them in `~/.claude/settings.json` instead. Before v2.1.257, `bypassPermissions` took effect from any file." CHANGELOG 2.1.257 independently: "Changed `defaultMode: "bypassPermissions"` in `.claude/settings.json` or `.claude/settings.local.json` to be ignored, like `"auto"`; set it in user or managed settings, or pass `--permission-mode`". Managed settings can also set `permissions.disableBypassPermissionsMode: "disable"` and `permissions.disableAutoMode: "disable"`.

7. Status/version currency. No beta/preview label on any mode; `auto` is GA and is the built-in starting mode on Pro/Max/Team (requires v2.1.228+ on macOS/Linux/WSL, v2.1.233+ on Windows; for `-p` the built-in start is Manual). Auto mode requires a supported model (Sonnet 5, Opus 4.7+, Fable on Bedrock/Vertex/Foundry). npm `@anthropic-ai/claude-code` latest = 2.1.263 (license field: "SEE LICENSE IN README.md", i.e. proprietary Anthropic terms, not OSS); CHANGELOG top entry is 2.1.263. Newer relevant flag: CHANGELOG 2.1.259 added `--permission-prompts none` "for unattended headless hosts: anything that would prompt is denied automatically while the active permission mode (including auto mode) keeps deciding"; headless docs show `claude -p "..." --permission-mode auto --permission-prompts none`. In a `-p` bypassPermissions run, "the few calls that would still prompt are denied instead".

**Implication for VICE.** The proposed launcher policy is sound and matches current (v2.1.263) documentation. Refinements for VICE: (1) Tightly scoped jobs: `claude -p ... --permission-mode dontAsk --allowedTools "Bash(<cmd> *)" "Read" ...`; note dontAsk also silently denies `AskUserQuestion`, `ask` rules, and MCP tools flagged `requiresUserInteraction`, so mesa-mcp/formation-mcp/iRODS tools must be explicitly allow-listed (`mcp__<server>__<tool>`) and must not set that meta flag if they are meant to run unattended. (2) Broader autonomy: prefer `--permission-mode auto --permission-prompts none` (2.1.259+) so residual prompts are denied rather than hanging the job; auto requires a supported model and suspends broad allow rules like `Bash(*)`. (3) `bypassPermissions`: only in a gVisor/Kata pod as a non-root user; the CLI hard-refuses it as root/sudo on Linux (the check is skipped only inside a "recognized sandbox" such as Anthropic's own sandbox runtime, so do not rely on gVisor being recognized — run as UID != 0). Since VICE images run agents as the same Unix user, put `permissions.deny` rules (which apply in every mode, including bypass) and `permissions.disableBypassPermissionsMode`/`disableAutoMode` in a managed-settings file baked into the image, not in project `.claude/settings.json` (which cannot set `auto`/`bypassPermissions` since v2.1.257 and can be edited by the agent itself). Pin the Claude Code version in the image (>=2.1.259 for `--permission-prompts none`).

### [partially_true] Claude Code hooks provide the async-approval integration surface: PreToolUse returns hookSpecificOutput.permissionDecision = allow|deny|ask (can also rewrite updatedInput), PermissionRequest returns hookSpecificOutput.decision = allow|deny|ask (exit code 2 is NOT honored there), Notification fires with notification_type permission_prompt/idle_prompt/agent_needs_input, and Stop can return continueLoop: true. Hooks can be command, http, mcp_tool, prompt, or agent; HTTP hooks POST the event JSON to a URL that must match the allowedHttpHookUrls allowlist, with headers interpolated from allowedEnvVars. Default timeout is 600 s and a timed-out command/http hook does not block — the call falls through to the normal permission flow.

**Corrected claim.** Claude Code hooks (docs current as of 2026-09; changelog head v2.1.263) support five handler types: command, http, mcp_tool, prompt, agent. PreToolUse returns hookSpecificOutput.permissionDecision with FOUR values: "allow" | "deny" | "ask" | "defer" (plus permissionDecisionReason, updatedInput, additionalContext); "defer" exits the process with stop_reason "tool_deferred" so the tool can be resumed later (single-tool-call turns only). PermissionRequest does NOT return a string decision: it returns hookSpecificOutput.decision as an OBJECT {behavior: "allow"|"deny", updatedInput?, updatedPermissions?, message?, interrupt?} — there is no "ask" behavior; to fall back to the user prompt the hook simply returns no decision object. Exit code 2 is not honored on PermissionRequest (stderr discarded; only the decision object grants/denies). Notification hooks receive notification_type, which has 12 values including permission_prompt (fires only after the prompt has waited ~6 s with no typing, and is suppressed if a PermissionRequest hook answers sooner), idle_prompt (~60 s after Claude finishes), and agent_needs_input (requires v2.1.198+). Stop hooks have NO continueLoop field: they prevent stopping with top-level {"decision":"block","reason":"..."} or exit 2, or continue softly with hookSpecificOutput.additionalContext; both are subject to the stop_hook_active input and an 8-consecutive-continuation cap. HTTP hooks POST the event JSON (Content-Type: application/json) to url, with headers interpolated only from variables listed in the hook's allowedEnvVars (empty string for unlisted); allowedHttpHookUrls is OPTIONAL — default unset means any URL is allowed; when defined at any settings level the URL must match the merged wildcard allowlist (empty array blocks all). A separate httpHookAllowedEnvVars setting caps which env vars any HTTP hook may interpolate. Default timeout is 600 s for command/http/mcp_tool (lowered to 30 s on UserPromptSubmit/PreModelSwitch/PostModelSwitch and 10 s on MessageDisplay), 30 s for prompt, 60 s for agent. **Implication for VICE.** The overall design (DE approval inbox via an http hook) is sound, but three concrete details in the claim would break an implementation. (a) The PermissionRequest response the DE endpoint must return is {"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"|"deny","message":"...","updatedInput":{...},"updatedPermissions":[...]}}} — not decision:"allow". There is no "ask": if the DE wants to hand the decision back to the local TUI prompt it must return no decision object (or exit 0 with no JSON). The interrupt:true field on deny lets the DE hard-stop the agent. (b) Stop hooks must return {"decision":"block","reason":"..."} (or hookSpecificOutput.additionalContext) rather than continueLoop, and Claude Code caps this at 8 consecutive forced continuations — a "keep working until DE says done" loop cannot be unbounded. (c) Timeout semantics are as claimed for PreToolUse (fall-through, not a gate), and the doc says the same for "most events", so a long-poll DE endpoint must answer within the hook's timeout (default 600 s, settable per hook) or the request falls to the local permission flow; in dontAsk mode / headless that flow auto-denies, which is the safe default the plan already anticipates — but in default mode a timed-out hook results in a local TUI prompt that a remote user may never see, so set explicit timeouts and prefer dontAsk for unattended pods. Additional useful primitives the claim missed: PreToolUse permissionDecision:"defer" cleanly exits a headless (-p) run with stop_reason "tool_deferred" and a resumable transcript — a better fit than long-polling for approvals that may take hours, at the cost of a single-tool-call-per-turn restriction; the Notification permission_prompt type is a 6-second-delayed fallback and is suppressed if the PermissionRequest hook answers, so use PermissionRequest (not Notification) as the primary trigger and permission_prompt/agent_needs_input only for "still waiting" nudges. For hardening on shared-user VICE pods, set allowedHttpHookUrls to the DE endpoint pattern and httpHookAllowedEnvVars to the DE token variable in managed settings (both apply to hooks from every source), and consider allowManagedHooksOnly so a user-level or project-level settings file cannot add a competing PermissionRequest hook that auto-allows. Note that Agent SDK callback hooks have stricter fail-closed timeout behavior than command/http hooks, so if the DE ever wraps agents via the SDK instead of the CLI, the timeout semantics invert.

### [confirmed] The Claude Agent SDK evaluates permissions in a fixed order — hooks → deny rules → ask rules → permission mode → allow rules → `canUseTool` callback — and `canUseTool` is the programmatic approval prompt; `allowedTools` does not constrain `bypassPermissions`; subagents inherit the parent's mode and cannot override `bypassPermissions`/`acceptEdits`/`auto`; TypeScript `permissionPrompts: 'none'` skips the callback and lets a `PermissionRequest` hook decide, else denies.

**Evidence.** Every element of the claim is confirmed by the primary source and by at least one independent artifact, current as of 2026-09-06.

1. Evaluation order. The SDK permissions page (code.claude.com/docs/en/agent-sdk/permissions, fetched 2026-09-06) lists six ordered steps under "How permissions are evaluated": Hooks, Deny rules, Ask rules, Permission mode, Allow rules, canUseTool callback, and its diagram alt-text says "six-step permission evaluation flow ... hooks, deny rules, ask rules, permission mode, allow rules, and canUseTool". Independent corroboration from the standalone Claude Code permissions reference (code.claude.com/docs/en/permissions): "Rules are evaluated in order: deny, then ask, then allow"; "PreToolUse hooks run before the permission prompt"; "Hook decisions don't bypass permission rules. Claude Code evaluates deny and ask rules regardless of what a PreToolUse hook returns"; "A blocking hook also takes precedence over allow rules."

2. canUseTool as the programmatic prompt. Python reference (code.claude.com/docs/en/agent-sdk/python): "The callback is the SDK replacement for the interactive permission prompt: it's invoked only when the permission evaluation flow resolves to a prompt." TypeScript reference: canUseTool is "invoked only when the permission flow falls through to a prompt. Not invoked for calls auto-approved by allowedTools, allow rules, or permissionMode." The TS SDK emits a Node warning with code CLAUDE_SDK_CAN_USE_TOOL_SHADOWED when canUseTool is paired with bypassPermissions or bare allowedTools entries.

3. allowedTools does not constrain bypassPermissions. Verbatim on the primary page: "`allowed_tools` does not constrain `bypassPermissions`... Setting `allowed_tools=["Read"]` alongside `permission_mode="bypassPermissions"` still approves every tool, including `Bash`, `Write`, and `Edit`. If you need `bypassPermissions` but want specific tools blocked, use `disallowed_tools`." Also: "For a locked-down agent, pair `allowedTools` with `permissionMode: "dontAsk"`." The shipped TS type file (cdn.jsdelivr.net/npm/@anthropic-ai/claude-agent-sdk@0.3.263/sdk.d.ts) confirms bypassPermissions "requires allowDangerouslySkipPermissions" and the PermissionMode union is exactly 'default' | 'acceptEdits' | 'bypassPermissions' | 'plan' | 'dontAsk' | 'auto' (line 2317). Python PermissionMode Literal lists the same six values.

4. Subagent inheritance. Verbatim: "Subagents inherit the parent session's permission mode. An AgentDefinition's permissionMode can override it, except when the parent uses bypassPermissions, acceptEdits, or auto: those modes apply to every subagent and can't be overridden per subagent. Claude Code also ignores a definition's permissionMode: "bypassPermissions" when bypass mode is disabled by permissions.disableBypassPermissionsMode". The subagents page and sdk.d.ts (line 91) confirm AgentDefinition has a permissionMode?: PermissionMode field.

5. permissionPrompts: 'none'. Primary page: "In the TypeScript SDK, if you set permissionPrompts: 'none', your callback isn't called at this step. A PermissionRequest hook still gets a chance to decide, and if it doesn't, Claude Code denies the call. The option requires Claude Code v2.1.259 or later." TS reference table: permissionPrompts is 'host' | 'none', default 'host', "Requires Claude Code v2.1.259 or later." Independent: sdk.d.ts line 1859 declares permissionPrompts?: 'host' | 'none' with JSDoc "'none': nobody — the permission mode (including auto mode's classifier), rules and hooks still decide, and anything that would otherwise prompt is denied immediately ... canUseTool is never called." TS CHANGELOG 0.3.259: "Added permissionPrompts: 'none' option to auto-deny permission prompts in sessions with nobody to answer them, without disabling auto mode's classifier." The Python reference has no permission_prompts option, so the "TypeScript" qualifier is accurate. The hooks reference confirms PermissionRequest fires "when a tool call needs a permission decision" and returns hookSpecificOutput.decision "allow" | "deny" (exit code 2 is not honored for that event).

Version/status/license (as of 2026-09-06): TS SDK latest on npm is 0.3.263 (parity with Claude Code v2.1.263); version tracks the bundled Claude Code version ("SDK v0.3.191 bundles Claude Code v2.1.191"). Python SDK latest is 0.2.152 (pyproject.toml), bundling CLI 2.1.259, license MIT. The npm package license field reads "SEE LICENSE IN README.md"; I could not extract a license section from the npm README, so the TS license text is not verified here. No beta label appears on any of these features; permissionPrompts is a GA option gated only by a minimum version.

Nuances the claim omits (not errors, but material): (a) a hook "allow" does not skip deny/ask rules; (b) explicit ask rules, AskUserQuestion, MCP tools with _meta["anthropic/requiresUserInteraction"] (needs Claude Code v2.1.199+), org-"ask" connector tools, and rm/rmdir on critical paths still reach canUseTool even under bypassPermissions or a matching allow rule; (c) in dontAsk mode the callback step is skipped and the call is denied; (d) plan mode routes file edits and (v2.1.212+) shell write commands to canUseTool regardless of allow rules; (e) a bare-name deny like "Bash" removes the tool from context before evaluation, only scoped denies like Bash(rm *) are checked at the deny step.

**Implication for VICE.** The claim holds, so the design reasoning is sound, with four refinements for a DE agent-runner service. (1) The context statement that "deny rules and hooks are the only controls that survive bypassPermissions" is slightly incomplete: explicit ask rules in settings.json also survive and route to canUseTool even in bypassPermissions, as do critical-path rm/rmdir, AskUserQuestion, MCP tools that set _meta["anthropic/requiresUserInteraction"] (Claude Code v2.1.199+), and org-level "ask" connector tools. So the DE can force iRODS/mesa-mcp/formation-mcp destructive tools (e.g. ds_delete_file, ds_modify_access) into the approval queue with ask rules or the requiresUserInteraction annotation on its own MCP servers, without giving up bypass mode elsewhere. (2) canUseTool only sees calls that fall through; any bare allowedTools entry (e.g. "Read") short-circuits it, and the TS SDK warns (CLAUDE_SDK_CAN_USE_TOOL_SHADOWED). If the DE wants every call to hit its queue, use a PreToolUse hook (runs first, applies even in bypassPermissions) rather than the callback; PreToolUse can also return permissionDecision "defer", which ends the query so it can be resumed later, a natural fit for an out-of-band approval queue with long timeouts. (3) Because subagents inherit bypassPermissions/acceptEdits/auto and cannot be narrowed per AgentDefinition, a VICE runner must not use bypassPermissions if any subagent needs tighter controls; set permissions.disableBypassPermissionsMode in managed settings to make subagent bypass definitions inert. (4) permissionPrompts: 'none' (TS SDK >= 0.3.259 / Claude Code >= 2.1.259) is TS-only; the Python SDK (0.2.152, MIT) has no equivalent, so a Python-based runner must rely on dontAsk mode or an absent callback to get deny-by-default. Versions checked as of 2026-09-06: TS SDK 0.3.263, Python SDK 0.2.152; none of these features is marked beta.

### Claude Code has six permission modes — `default` (Manual), `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions` — selected with `--permission-mode`; `--dangerously-skip-permissions` is equivalent to `--permission-mode bypassPermissions`, is documented for 'Isolated containers and VMs only', refuses to start as root on Linux/macOS, and `dontAsk` is the documented mode for 'Locked-down CI and scripts' where anything not matched by `permissions.allow` rules, the read-only command set, or a PreToolUse hook allow is auto-denied.

- Confidence: high (load-bearing); source: <https://code.claude.com/docs/en/permission-modes> (2026 (live docs, fetched 2026-09-06; references v2.1.257))
- Evidence: Table: `dontAsk` — 'Only pre-approved tools' — 'Locked-down CI and scripts'; `bypassPermissions` — 'Everything' — 'Isolated containers and VMs only'. 'Run fully unattended inside a container: `claude -p "<prompt>" --dangerously-skip-permissions` ... Required: a container, VM, or the sandbox runtime; on Linux and macOS, run it as a non-root user'. - Relevance to VICE: Defines the exact flags for VICE's agent-job launcher: use `--permission-mode dontAsk` + `--allowedTools` for tightly scoped jobs, `--permission-mode auto` for broader autonomy, and only ever `bypassPermissions` inside a gVisor/Kata pod as a non-root user with no sudo.

### Headless Claude Code (`claude -p`) supports `--bare` (skips hooks/MCP/plugins/CLAUDE.md discovery and never reads OAuth/keychain; needs `ANTHROPIC_API_KEY` or an `apiKeyHelper` via `--settings`), `--allowedTools`, `--output-format json|stream-json`, `--json-schema`, `--max-turns`, `--max-budget-usd`, `--continue`/`--resume <session_id>`/`--fork-session`, and `--permission-prompts none` (v2.1.259+) which denies anything that would prompt unless a `PermissionRequest` hook allows it; SIGTERM exits 143 leaving the turn unfinished and `--resume` continues that turn.

- Confidence: high (load-bearing); source: <https://code.claude.com/docs/en/headless> (2026 (live docs; references v2.1.259/v2.1.261))
- Evidence: 'Pass `--permission-prompts none` when nobody is available to answer permission prompts ... 'In bare mode, Claude Code never reads OAuth credentials or the system keychain.' '`--bare` is the recommended mode for scripted and SDK calls'.
- Relevance to VICE: Gives VICE a durable, budget-capped, resumable job primitive: run `claude -p --bare --permission-mode auto --permission-prompts none --max-budget-usd N --output-format stream-json` inside a K8s Job; a pod eviction (SIGTERM) is recoverable with `--resume` as long as `CLAUDE_CONFIG_DIR` lives on the workspace PVC.

### Claude Code hooks provide the async-approval integration surface: `PreToolUse` returns `hookSpecificOutput.permissionDecision` = allow|deny|ask (can also rewrite `updatedInput`), `PermissionRequest` returns `hookSpecificOutput.decision` = allow|deny|ask (exit code 2 is NOT honored there), `Notification` fires with `notification_type` `permission_prompt`/`idle_prompt`/`agent_needs_input`, and `Stop` can return `continueLoop: true`. Hooks can be `command`, `http`, `mcp_tool`, `prompt`, or `agent`; HTTP hooks POST the event JSON to a URL that must match the `allowedHttpHookUrls` allowlist, with headers interpolated from `allowedEnvVars`. Default timeout is 600 s and a timed-out command/http hook does not block — the call falls through to the normal permission flow.

- Confidence: high (load-bearing); source: <https://code.claude.com/docs/en/hooks> (2026 (live docs))
- Evidence: PermissionRequest: 'Exit code 2 has no blocking effect on `PermissionRequest` — denials must come through the `decision` field in `hookSpecificOutput`'. HTTP hooks: 'Event JSON sent as POST body ... URL validation: Must match `allowedHttpHookUrls` if that allowlist is defined in settings'. 'Timed-out `command`, `http`, or `mcp_tool` hooks don't block; call continues through normal permission flow'. Example: `{"type":"http","url":"http://localhost:8080/hooks/pre-tool-use","timeout":30,"headers":{"Authorization":"Bearer $MY_TOKEN"},"allowedEnvVars":["MY_TOKEN"]}`.
- Relevance to VICE: This is how the DE can host an approval inbox: a `PermissionRequest` (or `PreToolUse`) `http` hook posts to a DE endpoint which long-polls the user's decision (Slack/Matrix/DE UI) and returns `{decision: allow|deny}`; `Notification` hooks push 'agent needs input' events to the DE; `Stop` hooks can report completion. The 600 s ceiling and fall-through-on-timeout semantics must be designed around (deny on timeout in `dontAsk`/`--permission-prompts none`).

### The Claude Agent SDK evaluates permissions in a fixed order — hooks → deny rules → ask rules → permission mode → allow rules → `canUseTool` callback — and `canUseTool` is the programmatic approval prompt; `allowedTools` does not constrain `bypassPermissions`; subagents inherit the parent's mode and cannot override `bypassPermissions`/`acceptEdits`/`auto`; TypeScript `permissionPrompts: 'none'` skips the callback and lets a `PermissionRequest` hook decide, else denies.

- Confidence: high (load-bearing); source: <https://code.claude.com/docs/en/agent-sdk/permissions> (2026 (live docs; references v2.1.259))
- Evidence: '`allowed_tools` does not constrain `bypassPermissions` ... Setting `allowed_tools=["Read"]` alongside `permission_mode="bypassPermissions"` still approves every tool'. 'For a locked-down agent, pair `allowedTools` with `permissionMode: "dontAsk"`'. 'Subagents inherit the parent session's permission mode ... except when the parent uses `bypassPermissions`, `acceptEdits`, or `auto`: those modes apply to every subagent and can't be overridden'.
- Relevance to VICE: If the DE builds its own agent-runner service (rather than shelling out to `claude -p`), the SDK's `canUseTool` callback is the cleanest place to implement an async approval queue with full control over timeouts; the ordering rules mean deny rules and hooks are the only controls that survive `bypassPermissions`.

### `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` strips Anthropic/cloud-provider credentials, any variable Claude Code recognizes as a credential, and credentials embedded in registry URLs from the environment of Bash commands, hooks, and MCP stdio servers, while the parent process keeps them; on Linux it also runs Bash subprocesses in an isolated PID namespace so `/proc` cannot leak host process environments. A companion `CLAUDE_CODE_SCRIPT_CAPS` JSON limits per-script invocation counts when scrub is set.

- Confidence: high (load-bearing); source: <https://code.claude.com/docs/en/env-vars> (2026 (live docs))
- Evidence: 'Set to `1` to strip credentials from subprocess environments (Bash tool, hooks, MCP stdio servers) ... - Relevance to VICE: Directly addresses VICE problem (a): set this in the image's managed settings `env` block so the AI Verde/Anthropic key given to Claude Code is not visible to shell commands, hooks or the iRODS/mesa/formation MCP servers. ## Recommendations

- Split the human session from the agent job: keep the existing VICE interactive pod (JupyterLab/RStudio/VS Code/KasmVNC/ttyd) for the person and launch each autonomous run as a separate pod — a kubernetes-sigs `agent-sandbox` `Sandbox` (stable identity, PVC, pause/resume, gVisor/Kata RuntimeClass) or, as a first step, a plain K8s Job — that mounts the same workspace PVC (read-write) but NOT `~/.irods`, `~/.aws`, `~/.ssh`, or agent OAuth caches. Run it as a non-root UID with no sudo and its own ServiceAccount; the DE already owns the Job/Pod API so this is an extension of the current launcher, not a new substrate.
- Standardize the unattended launch lines per harness and bake them into the images: Claude Code `claude -p --bare --permission-mode auto|dontAsk --permission-prompts none --allowedTools ... --max-turns N --max-budget-usd X --output-format stream-json` (fall back to `--dangerously-skip-permissions` only inside a gVisor/Kata pod); Codex `codex exec -s workspace-write -a never --json -o out.md` with `[sandbox_workspace_write] network_access=true` and a `[features.network_proxy]` domain allowlist; OpenCode `opencode run --agent <name>` with a complete `permission` map (never `ask` until issue #16367 is fixed); Goose `GOOSE_MODE=auto goose run --recipe job.yaml --max-turns N --no-session`; Gemini `gemini -p ... --approval-mode auto_edit|yolo` with `GEMINI_SANDBOX=false`; Antigravity `agy -p ... --output-format stream-json` relying on soft-deny plus `permissions.allow` rules.
- Build a DE 'approval inbox' service and wire it to the two harnesses that expose an approval API: Claude Code via `PermissionRequest` (and `PreToolUse`) `http` hooks in managed settings (pin the URL with `allowedHttpHookUrls`, pass a per-job token via `allowedEnvVars`, default deny on the 600 s timeout), and OpenCode via `opencode serve` + `/event` + `POST /session/:id/permissions/:permissionID`. Fan decisions out to the DE web UI, Slack, and Matrix; use Claude `Notification` (`permission_prompt`, `idle_prompt`, `agent_needs_input`) and `Stop` hooks to update job status. For Goose/Gemini/agy, which have no approval channel, restrict unattended jobs to pre-declared allow/deny policy and a smaller egress allowlist.
- Ship a read-only `managed-settings.json` in every Claude-capable VICE image: `permissions.disableBypassPermissionsMode: "disable"` in the interactive image, `permissions.deny` for `Read(~/.irods/**)`, `Read(~/.aws/**)`, `Read(~/.ssh/**)`, `sandbox.enabled: true`, `sandbox.failIfUnavailable: true` (agent image), `sandbox.network.allowedDomains` limited to `llm-api.cyverse.ai`, `api.anthropic.com`, `data.cyverse.org`/iRODS hosts, GitHub, package registries, `sandbox.network.allowManagedDomainsOnly: true`, `sandbox.credentials.files` deny entries, `allowManagedPermissionRulesOnly: true`, `allowedHttpHookUrls` = DE endpoint, and `env: {CLAUDE_CODE_SUBPROCESS_ENV_SCRUB: "1"}`. Validate bubblewrap under the VICE pod securityContext (unprivileged user namespaces / AppArmor `kernel.apparmor_restrict_unprivileged_userns`) and set `sandbox.enableWeakerNestedSandbox` where needed.
- Move credentials out of the home directory and into per-job, short-lived, scoped secrets issued by OpenBao: an init container (Codex-cloud style setup phase) obtains an iRODS ticket or short-lived .irodsA, a scoped OSN S3 STS-style key, a per-job AI Verde token, and a GitHub App installation token, writes them to a tmpfs consumed only by an egress proxy sidecar, then the agent phase starts with no secrets in env or home. Use Claude Code `apiKeyHelper` (with `CLAUDE_CODE_API_KEY_HELPER_TTL_MS`) or `ANTHROPIC_BASE_URL` → AI Verde to avoid static Anthropic keys, and copy the Managed Agents/Claude Code `mask` pattern (placeholder in sandbox, real value injected at the proxy for allowed hosts) for tokens tools must send verbatim.
- Give each agent job its own identity and audit trail (OWASP ASI03 / CISA guidance): a per-job Kubernetes ServiceAccount bound to an OpenBao role, NetworkPolicy allowing only the egress proxy, and a DE-side log of every approval decision (who/what/when) with the `tool_name`/`tool_input` payload from the hook; forbid agent-to-agent credential sharing by never mounting one harness's OAuth cache (`~/.claude`, `~/.codex`, `~/.config/goose`, `~/.gemini`) into another's pod.
- Make durability a property of the workspace, not the terminal: keep `CLAUDE_CONFIG_DIR` (or `~/.claude/projects`), Codex session rollouts, and Goose session files on the workspace PVC so an evicted job resumes with `claude -p --resume <id>`, `codex exec resume <id>`, or `goose run --resume`; handle SIGTERM (Claude exits 143 and resumes the unfinished turn) with a preStop that sends SIGINT first; cap runaway jobs with `--max-turns`/`--max-budget-usd`/`GOOSE_MAX_TURNS`. Inside a single interactive pod, `claude --bg` / `claude agents` and `--worktree --tmux` are acceptable interim tools but do not survive pod restarts.
- Keep the DE as the control plane and treat kagent and Agent Substrate as adjacent, not foundational: use kagent (Apache-2.0, CNCF) only if the team wants declarative ADK service agents around formation-mcp/mesa-mcp; track Agent Substrate (announced 2026-05-20) but do not build on it yet. For self-hosted vLLM/Ollama GPU inference, run it as a separate GPU-scheduled service reachable only through the egress proxy allowlist (OpenAI-compatible endpoint via AI Verde or Claude Code Router as a sidecar), rather than granting agent pods GPUs directly, until the gVisor/Kata GPU story is validated.
- Phase the rollout per CISA/OWASP guidance: Phase 1 read-only analysis jobs (`dontAsk` + allowlist, Codex `read-only`, Goose `chat`/`smart_approve`), Phase 2 workspace-write with git worktrees and DE approval inbox for pushes/data-store writes (`permissions.ask` rules such as `Bash(git push *)`, iRODS write tools marked ask), Phase 3 broader autonomy (`auto` mode / `-a never`) only inside gVisor/Kata `Sandbox` pods with egress proxy; instrument denials (`permission_denials` in Claude stream-json, agy stderr notices, OpenCode events) to tune policy.

## Open questions

- Does bubblewrap (Claude Code sandbox, Codex bwrap, agy namespaces) work under VICE's current PodSecurity/securityContext and node AppArmor settings, or must pods be relaxed / `sandbox.enableWeakerNestedSandbox` used? Needs a cluster test.
- Is a 600 s (default) HTTP hook wait acceptable for async human approval, or should the DE hook return `deny` immediately, queue the request, and re-run the tool via `--resume` once approved? Whether hooks support longer per-hook `timeout` values in practice should be verified.
- OpenCode issue #16367 (headless `ask` hangs under `serve`/`attach`) showed no maintainer fix as of the fetched page; is there a newer release that relays permission events so a DE broker can answer them reliably?
- Gemini CLI's behaviour when a tool needs confirmation in headless `-p` mode without `--yolo` is not documented on the headless page; does it deny, hang, or exit?
- gVisor (runsc) / Kata GPU passthrough support and its interaction with NVIDIA device plugins was not verified in primary sources; VICE's ad-hoc vLLM/Ollama GPU pods may need to stay outside the sandboxed RuntimeClass.
- Claude Managed Agents self-hosted sandboxes do not yet support `environment_variable` vault credentials; if VICE ever used the hosted control plane, how would iRODS/S3 secrets be injected?
- Claude Code self-hosted environments require claude.ai Team/Enterprise seats and Anthropic's control plane; is any CyVerse user population licensed for it, or is the design reference the only value?
- Are the Codex `[features.network_proxy]` domain allowlist and Claude `sandbox.network.allowedDomains` enforced for MCP stdio servers (iRODS/mesa/formation) — the Claude docs say MCP servers run unconstrained, so per-pod NetworkPolicy remains mandatory; confirm the same for Codex.
- NIST COSAiS SP 800-53 overlays and the Cyber AI Profile (IR 8596) are still drafts; which framework will CyVerse/UNM CARC security require the AI Sandbox design to map to?
- How should Goose recipes and Claude/Codex sessions record provenance of data-store writes (iRODS AVUs, mesa-mcp DataCite metadata) so approval decisions and agent actions are auditable in the DE?
