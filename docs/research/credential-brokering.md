# Credential brokering (OpenBao, iRODS tickets, OSN, LiteLLM keys, GitHub App tokens, proxies)

Dimension key: `credential-brokering`. Date: 2026-09-06.

## Summary

The clean all-open-source pattern for VICE is "agents never hold the user's long-lived secret": a trusted broker (OpenBao 2.6.x, MPL-2.0, latest v2.6.2 on 2026-08-18) issues short-lived, leased, revocable credentials to a per-analysis Kubernetes ServiceAccount, and a trusted egress proxy (agentgateway, Apache-2.0) injects the few secrets that cannot be made short-lived, so the agent process only ever sees a sentinel value or a scoped token. This is exactly the architecture Anthropic documents for Claude Code on the web (Oct 2025) and "How we contain Claude" (May 2026): credentials stay outside the sandbox, a proxy verifies each git/API request and attaches the real token. OpenBao gives VICE Kubernetes auth (TokenReview, bound_service_account_names/namespaces), JWT/OIDC auth against Keycloak with CEL claim validation, response wrapping, an SSH CA that signs 30-minute user certificates, a Kubernetes secrets engine that mints TTL-bound SA tokens, Transit, namespaces (2.3+, sealed namespaces in 2.6), and mandatory audit devices; it does NOT ship an AWS/STS-style secrets engine (only Cubbyhole, Databases, Identity, KV, Kubernetes, LDAP, PKI, RabbitMQ, SSH, TOTP, Transit), so S3 credentials for OSN cannot be brokered by OpenBao itself. For iRODS, tickets (iticket create read/write + mod uses/write-file/write-byte/expire/add host) are the right agent credential; the PAM path stores a TTL-limited but reversibly-obfuscated password in ~/.irods/.irodsA (default password_max_time 1209600 s = 14 days), so it must be kept out of the agent's uid. OSN's own docs describe only static per-bucket read-only/read-write keys distributed through a CILogon portal, with no STS or presigned-URL feature and no self-service revocation ("contact support to regenerate"), so OSN keys must sit behind a SigV4-re-signing proxy until OSN exposes RGW STS (Ceph RGW supports AssumeRoleWithWebIdentity with rgw_s3_auth_use_sts and rgw_sts_key). LLM access should be per-analysis LiteLLM virtual keys (/key/generate with duration, max_budget, models, tpm/rpm) if AI Verde is LiteLLM (MIT core). GitHub access should be GitHub App installation tokens (1 h, scoped by repositories/permissions) delivered through a git credential helper. MinIO is archived (repo archived, last push 2026-04-24) and should not be a new dependency; Bitwarden Secrets Manager is Enterprise-only for self-host with a proprietary SDK license; Infisical is MIT-core with proprietary ee/ features. Keycloak 26.2+ standard token exchange (RFC 8693, internal-internal only) plus the 26.5 JWT-authorization-grant/identity-chaining preview cover the "MCP server acting as the user" case.

For VICE: give each analysis pod its own ServiceAccount (e.g. vice-<analysis-id>) and create an OpenBao kubernetes-auth role with bound_service_account_names=<that SA> and bound_service_account_namespaces=<vice namespace> (or bound_service_account_namespace_selector for label-based matching) plus token_ttl (prefer token_ttl over the deprecated ttl). Run OpenBao inside the cluster with token_reviewer_jwt and kubernetes_ca_cert omitted and disable_local_ca_jwt=false so it uses its own rotating projected SA token for TokenReview; grant OpenBao's SA the system:auth-delegator ClusterRole. Set audience on the role and use a projected serviceAccountToken volume with a matching audience so the pod token cannot be replayed against the kube-apiserver. Prefer kubernetes auth over the JWT/OIDC route for VICE because TokenReview lets Kubernetes revoke access immediately when the analysis pod is deleted, whereas JWT auth would honor the token until expiry; use JWT/OIDC only if OpenBao runs outside the cluster and cannot reach TokenReview. Note the role's OpenBao token TTL and the pod token TTL are independent: keep both short and let the agent re-login.

### [confirmed] OpenBao response wrapping returns a single-use wrapping token (via the X-Vault-Wrap-TTL header) whose cubbyhole holds the real response; sys/wrapping/unwrap, sys/wrapping/lookup and sys/wrapping/rewrap manage it, providing in-transit protection, interception detection and an independent TTL.

**Evidence.** Primary source (openbao.org concepts doc, published for OpenBao 2.6.x; the underlying response-wrapping.mdx last touched 2025-10-30) states the client triggers wrapping with the X-Vault-Wrap-TTL header (integer seconds or 15s/20m/25h durations; CLI uses -wrap-ttl), that "A new single-use token is generated with the TTL supplied by the client" and "the original serialized response is stored in the single-use token's cubbyhole", lists the four sys/wrapping operations (lookup, unwrap, rewrap, wrap), and gives the three benefits: cover ("a reference to such a secret" crosses the wire), malfeasance detection ("only a single party can ever unwrap the token"), and a wrapper TTL independent of (and typically much shorter than) the wrapped secret's lifetime. Independent confirmation from OpenBao source on main (fetched 2026-09-06): api/client.go defines WrapTTLHeaderName = "X-Vault-Wrap-TTL" and WrapFormatHeaderName = "X-Vault-Wrap-Format" (OpenBao has NOT renamed these to an X-BAO-* header); internal/http/logical.go parses "X-Vault-Wrap-TTL"; internal/vault/wrapping.go's wrapInCubbyhole creates the token with NumUses: 1 and writes the response at Path "cubbyhole/response"; internal/vault/logical_system_paths.go registers Pattern "wrapping/wrap$", "wrapping/unwrap$", "wrapping/lookup$", "wrapping/rewrap$" bound to handleWrappingWrap/Unwrap/Lookup/Rewrap, with "wrapping/lookup" in the Unauthenticated list (lookup accepts both POST/update and GET/read). The in-repo API docs (website/content/docs/api/system/wrapping-{unwrap,lookup,rewrap,wrap}.mdx) confirm: POST /sys/wrapping/unwrap (wrapping token as X-Vault-Token or as `token` param, never both, otherwise the token is consumed without returning the value); POST /sys/wrapping/lookup returns creation_path, creation_time, creation_ttl; POST /sys/wrapping/rewrap issues a new token with the same creation TTL and "The old token will be invalidated"; reading cubbyhole/response directly is deprecated with a warning in request_handling.go. Upstream HashiCorp Vault docs describe the identical mechanism, as expected for a fork. Versioning: latest OpenBao release is v2.6.2 (2026-08-18, not prerelease; 2.6.0 GA 2026-07-14); response wrapping is a long-standing GA feature inherited from Vault, not beta. License: MPL-2.0 (LICENSE file and GitHub license metadata). Minor precision notes: the docs word interception detection as "only a single party can ever unwrap the token" (i.e., the legitimate consumer will get an error if someone else already unwrapped it), and the OpenBao docs do not use the exact phrase "interception detection", but the meaning matches. The published API doc URLs of the form openbao.org/api-docs/system/wrapping-*/ returned empty content to the fetcher; the canonical in-repo source is website/content/docs/api/system/.

**Implication for VICE.** The proposed pattern is sound and current on OpenBao 2.6.x: the DE launcher can request any OpenBao response (e.g., a token or KV read) with X-Vault-Wrap-TTL set to a short window (say 60-300s), inject only the wrapping token into the pod (env var or mounted file), and have the in-pod bootstrap call POST /sys/wrapping/unwrap using the wrapping token as X-Vault-Token (no separate auth needed). Because the wrapping token has NumUses=1, if the bootstrap's unwrap fails, the token was either already consumed (possible interception) or expired, which is an actionable signal; sys/wrapping/lookup is unauthenticated, so a pre-flight check can confirm creation_path (guard against a substituted token) and creation_ttl before unwrapping. Design cautions grounded in the docs: never pass the wrapping token both as X-Vault-Token and as the `token` body param (it will be consumed with no value returned); do not read cubbyhole/response directly (deprecated); if the pod might start slowly relative to the wrap TTL, the launcher can use sys/wrapping/rewrap to rotate the token and refresh its TTL before handing it over. Header names remain X-Vault-Wrap-TTL / X-Vault-Token in OpenBao (no X-BAO-* rename), so existing Vault client libraries work. OpenBao is MPL-2.0, which suits CyVerse's open-source stack.

## Recommendations

- Adopt the credential-type matrix: iRODS -> DE-minted per-analysis iRODS tickets (iticket create write on the analysis output collection; mod expire=<analysis end>, add host=<pod egress IP>, write-byte/uses caps) plus, for API access, an iRODS HTTP API bearer token obtained via Keycloak token exchange (timeout_in_seconds ~3600); OSN S3 -> keys held only in OpenBao KV and injected/re-signed by an egress proxy, with an explicit request to OSN for Ceph RGW AssumeRoleWithWebIdentity; SSH -> OpenBao SSH CA certificates (ttl 30m, valid_principals) delivered by the Agent sidecar, with CARC/CyVerse hosts trusting the CA; Git/GitHub -> CyVerse GitHub App installation tokens (1 h, repositories+permissions scoped) via a broker-backed git credential helper; LLM (AI Verde) -> per-analysis LiteLLM virtual key (duration = job time limit, max_budget, models, metadata{analysis_id,user}) blocked on termination; direct Anthropic/OpenAI/Gemini keys and agent OAuth tokens -> never in the pod, injected by the proxy; Kubernetes API -> OpenBao Kubernetes secrets engine SA tokens with token_max_ttl; MCP servers -> hosted outside the agent pod (ToolHive/agentgateway) receiving the user's downscoped Keycloak token.
- Give every VICE analysis its own Kubernetes ServiceAccount and an OpenBao role bound via bound_service_account_names/bound_service_account_namespaces (ttl minutes, renewable by the openbao.org/agent-inject sidecar); put user-owned material in an OpenBao namespace per user or project, with CyVerse and MESA/CARC as separate top-level namespaces; enable the HTTP audit device to stream every credential issuance into the DE analysis record.
- Deploy OpenBao 2.6.x (not HashiCorp Vault) with these mounts: auth/kubernetes, auth/jwt (Keycloak, CEL bound claims on the DE user/analysis), ssh-client-signer (CA), kubernetes secrets engine, transit (to encrypt DE-side stored user secrets such as OSN keys), pki (to issue the egress proxy's TLS-interception CA); do not plan on an AWS engine, it does not exist in OpenBao.
- Insert a per-pod (sidecar) or per-namespace agentgateway as the only egress path for agents: LLM routes to llm-api.cyverse.ai/api.anthropic.com with llm.models[].auth injected keys, an MCP route with backendAuth oauthTokenExchange to Keycloak, a GitHub route with a broker-minted installation token, and an S3 route that re-signs SigV4 with the real OSN key; expose only sentinel values (e.g., ANTHROPIC_API_KEY=sk-ant-dummy, AWS_ACCESS_KEY_ID=sentinel) inside the container, exactly as Anthropic's Claude Code on the web and the Claude Code mask/injectHosts design do.
- Fix the same-uid problem immediately, independent of the broker: run each agent (Claude Code, Codex, OpenCode, Goose, Antigravity, ant) as a dedicated non-sudo uid (e.g., 'agent') distinct from the human's uid, keep ~/.irods/.irodsA, ~/.aws, ~/.ssh and ~/.config/gh in the human's home with 0600, and share only an ssh-agent socket (ssh-add -t, -c) and a git credential helper socket into the agent uid; because .irodsA obfuscation is keyed on os.getuid(), this alone stops trivial decoding by agents.
- Harden the iRODS PAM path for the human session: lower password_max_time from the 1209600 s default toward the VICE session length, set password_extend_lifetime to 0 for VICE-launched sessions, have the DE call iinit --ttl with the analysis time limit, and upgrade Data Store to 4.3.5 to get the ticket write-file limit fix (#2720); prefer pam_interactive with TLS enforced.
- Ship Claude Code managed settings in cyverse-vice images now (sandbox.credentials envVars/files mode 'mask' with injectHosts for api.github.com, api.anthropic.com, llm-api.cyverse.ai; network.allowedDomains; strictAllowlist; awsPairs for OSN) as a stopgap for Claude Code specifically, while the pod-level gateway covers the other agents.
- For long autonomous runs (problem c), launch the agent in a separate kubernetes-sigs/agent-sandbox Sandbox pod with its own SA/OpenBao role and its own leased credentials, so the human's interactive VICE session and the agent's job have independent lifetimes; leases renew via the OpenBao Agent sidecar and are revoked by the DE when the job ends, giving 'revocable' without touching the human's session.
- Use Keycloak 26.2+ standard token exchange (same realm) for MCP servers acting as the user (formation-mcp against the DE API, iRODS HTTP API with the user_claim plugin), enabling the 'Standard token exchange' switch on the gateway client only; track the 26.5 JWT-authorization-grant/identity-chaining preview for CyVerse<->MESA/CARC cross-domain calls rather than building on deprecated V1 exchange.
- Open a formal dialogue with OSN: request confirmation of the RGW backend, enablement of rgw_s3_auth_use_sts with an OIDC provider for CILogon/ACCESS, and self-service key rotation; until then, treat OSN keys as non-revocable long-lived secrets that live only in OpenBao and the proxy.
- Exclude MinIO (archived), Bitwarden Secrets Manager (Enterprise-only self-host, proprietary SDK) and Infisical ee/ features from the design; keep External Secrets Operator only for platform-level Kubernetes Secrets, never for per-user agent credentials.
