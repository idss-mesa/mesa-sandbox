# Prior art: platforms that combine interactive workspaces with autonomous agents

Dimension key: `prior-art-platforms`. Date: 2026-09-06.

## Summary

Across every 2025-2026 platform examined, the same reference architecture recurs: (1) a "brain/hands" split where the LLM loop and orchestration run outside the execution environment and only tool calls enter it (Anthropic Managed Agents, Coder Agents, Anthropic self-hosted runners, Coder Agent Relay); (2) one disposable isolation unit per task (VM at Anthropic/Cursor/Jules/Docker Sandboxes, container+gVisor at Managed Agents and Codex, gVisor/Kata pods via the kubernetes-sigs agent-sandbox CRD, Landlock+seccomp+netns at NVIDIA OpenShell, bubblewrap on the host for Claude Code's built-in sandbox); (3) default-deny egress through a proxy that lives OUTSIDE the sandbox and enforces a domain (and increasingly method/path) allowlist; (4) credentials that never enter the sandbox: the sandbox sees a sentinel or scoped credential and the proxy swaps in the real secret on the way out (Anthropic's GitHub proxy and API-credential "agent proxy", Claude Code's sandbox.credentials mask+injectHosts+SigV4 re-sign, Managed Agents' vault credential proxy for MCP, OpenShell's inference gateway); (5) asynchronous human-in-the-loop where the session persists server-side and unanswered questions wait for the user to return (Claude Code on the web, Coder Agents chat persistence in the control plane); and (6) MCP servers treated as separate governed workloads (ToolHive operator, Managed Agents allow_mcp_servers) because per-process firewalls like GitHub Copilot's explicitly do not cover MCP. What is open source: Anthropic sandbox-runtime (Apache-2.0, bwrap/Seatbelt + HTTP/SOCKS proxy), Coder boundary (MIT) and httpjail (CC0), NVIDIA OpenShell (Apache-2.0, experimental Helm chart, GPU passthrough), kubernetes-sigs/agent-sandbox (Apache-2.0, v1beta1, gVisor/Kata RuntimeClass, pause/resume, warm pools), kagent + Agent Substrate (Apache-2.0, CNCF sandbox, gVisor snapshot/restore), ToolHive (Apache-2.0). What is proprietary or no longer self-hostable: Anthropic's hosted VMs and proxies, Codex cloud, Jules, Cursor, Devin, GitHub Copilot's Actions runner, Coder's Agent Firewall audit streaming (Premium), Modal, and Daytona (closed-sourced June 2026); E2B infra is open but Nomad-based, not Kubernetes. For VICE the copyable mechanisms are Anthropic's scoped-credential git proxy plus sentinel/inject credential masking, Coder Boundary's default-deny method+domain+path rules, and agent-sandbox as the Kubernetes CRD for per-agent gVisor pods with stable identity and pause/resume for long jobs while the human's interactive pod stays untouched.

## Fact-check verdicts on load-bearing claims

### [confirmed] Claude Code on the web keeps GitHub credentials outside the session VM: the git client inside the sandbox uses a scoped credential that a dedicated proxy verifies and swaps for the real token; pushes are restricted to the session's current branch, API requests are repo-scoped, and GraphQL is restricted to a pinned set of operations.

**Evidence.** PRIMARY SOURCE (fetched 2026-09-06, code.claude.com/docs/en/cloud-environments, section "GitHub proxy"): every element of the claim appears verbatim. "In Anthropic-hosted environments, all GitHub operations go through a dedicated proxy that keeps your real GitHub credentials outside the session's VM, independent of the environment's access level." Bullets: "Git credentials: the git client inside the VM uses a scoped credential, which the proxy verifies and swaps for your actual GitHub token." "Push protection: git push works only against the session's current working branch; cloning, fetching, and PR operations work normally." "Repository scope: GitHub API and release-asset requests reach only repositories attached to the session, so a setup script that downloads release assets from an unattached repository gets a 403." "GraphQL restrictions: the proxy serves only a pinned set of GraphQL operations for pull-request workflows. The proxy rejects everything else on the GraphQL endpoint with a 403 that says `This GraphQL query is not enabled for this session`... a `GH_TOKEN` you set gets the same 403. Claude can't reach GitHub APIs that exist only in GraphQL, such as Projects v2." The same page documents that when no token is set, `GH_TOKEN`/`GITHUB_TOKEN` read as the placeholder string `proxy-injected` inside the VM and "the proxy substitutes your real credentials on outbound GitHub requests."

SECOND ANTHROPIC PAGE (code.claude.com/docs/en/claude-code-on-the-web, "Security and isolation", fetched 2026-09-06): "Credential protection: in Anthropic-hosted environments, git credentials and signing keys stay outside the sandbox, and a proxy authenticates on the session's behalf with scoped credentials." Status note on the same page: "Claude Code on the web is in research preview for Pro, Max, and Team users, and for Enterprise users with premium seats or Chat + Claude Code seats." Important scoping caveat from the same page: "With either method, a cloud session can access any repository the connecting GitHub account can see... App installation... is not a session-level access control." I.e., the real token behind the proxy is the user's full GitHub OAuth/App token; repo/branch restriction is enforced by proxy policy, not by a narrowly-minted GitHub token.

SELF-HOSTED DOC (code.claude.com/docs/en/self-hosted-environments-deploy, "Configure git", fetched 2026-09-06; self-hosted environments are "in public beta on Team and Enterprise plans"): exposes the proxy's actual configuration names. Runner flag `--use-anthropic-git-proxy` or env `CLAUDE_RUNNER_USE_GIT_PROXY=1` makes the runner "clone through Anthropic's git proxy, authenticated with the session's own short-lived token. For ordinary user sessions, the proxy uses the GitHub or GitHub Enterprise OAuth token stored for the session creator; for bot and agent sessions, it uses your organization's GitHub App installation token... This is the same auth path Anthropic-hosted environments use." Requirements: `--capacity 1` ("the proxy URL is per-session") and git >= 2.32; proxy URL points at `api.anthropic.com`. Other flags named: `--configure-git`, `--git-host-rewrite <from>=<to>`, `--git-ssh-rewrite <host>`. Hardening guidance: "mint a short-lived, least-scoped token per session from your wrapper script, using the session creator's identity decoded from the session JWT. Pair it with an ephemeral per-session container."

LAUNCH BLOG (claude.com/blog/claude-code-on-the-web, published 2025-10-20, updated 2025-11-12): only states "Git interactions are handled through a secure proxy service that ensures Claude can only access authorized repositories" and that changes are limited to the working branch; the detailed branch/GraphQL rules are documented only in the docs pages above.

INDEPENDENT FIELD REPORTS (anthropics/claude-code issue tracker, via gh api): Issue #76417 (2026-07-10, closed) reproduces the exact 403 text "This GraphQL query is not enabled for this session — only the pinned set of PR-review operations is served. Use REST via `gh api repos/{owner}/{repo}/...` instead." and independently observes REST identity substitution: `gh api user` returned the proxy's identity even with an invalid dummy `GH_TOKEN`. The reporter found even a PR `reviewThreads` query blocked, so the "pinned set" is narrow (possibly only Anthropic's own built-in PR tools), narrower than the wording implies. Issue #76248 (2026-07-10, open) reproduces repo scoping at the git layer: "remote: access denied by the git proxy: <owner>/<repo> is not in this session's authorized repository set, so the proxy will not inject a credential for it" and REST "GitHub access to this repository is not enabled for this session"; reporter observed env flags `CCR_TEST_GITPROXY=1`, `CCR_AGENT_PROXY_ENABLED=1`, `CCR_UPSTREAM_PROXY_ENABLED=1`, and that user-supplied PATs are overridden (GitHub never sees them). Issue #88198 (2026-08-20) independently reports `GH_TOKEN` being ignored for api.github.com.

WHAT I COULD NOT INDEPENDENTLY VERIFY: the branch-level (as opposed to repo-level) push restriction is asserted only by Anthropic docs; no third-party report tests pushing to a non-current branch. Also, the proxy is proprietary Anthropic infrastructure — no source, no license, no version number, no Kubernetes CRD; the only operator-facing surface is the self-hosted runner flags above. Status as of 2026-09-06: Claude Code on the web = research preview (not GA); self-hosted environments = public beta (Team/Enterprise). The docs pages are undated but were fetched live today and reference Claude Code v2.1.223/v2.1.224, so they are current.

**Implication for VICE.** The pattern is real and current, so it is a sound model for VICE, but copy the architecture, not the assumed token semantics. Key design facts to carry over: (1) The in-sandbox "scoped credential" is effectively a per-session placeholder/short-lived session token (docs: `GH_TOKEN` reads as the literal string `proxy-injected`); the real GitHub credential is the user's full OAuth token or a GitHub App installation token held only by the proxy. Repo and branch restrictions are proxy-side policy, not GitHub-side token scoping, so the proxy is the security boundary and must be hardened accordingly. (2) The proxy is per-session (`--capacity 1` requirement, per-session proxy URL), which maps cleanly to one proxy sidecar or per-analysis proxy pod outside the VICE user container, keyed by the analysis ID. (3) Anthropic's own operator guidance for self-hosted runners is exactly the VICE situation: mint a short-lived, least-scoped token per session from a wrapper script using the session creator's identity from a session JWT, pair with an ephemeral container, and never bake credentials into the image. VICE can implement that with OpenBao issuing a per-analysis GitHub App installation token (or fine-grained PAT) to the proxy pod, with the DE's Keycloak identity as the session JWT. (4) Enforce: push only to the analysis's working branch; REST/git limited to an "attached repository set" the user chose at launch; block or allowlist GraphQL. (5) Known UX/operational pitfalls from field reports that VICE should design around: user-supplied PATs get silently overridden (identity confusion for automation), setup scripts fetching release assets from unattached repos get 403, and a too-narrow GraphQL allowlist breaks Projects v2 and even PR review-thread queries; give users a clear "add repo to session" affordance and a documented REST fallback. (6) Anthropic's proxy is proprietary with no license or open code; VICE would need to build its own (e.g., a git-credential-helper plus an HTTP forward proxy or Envoy ext_authz filter that swaps the placeholder for the OpenBao-issued token and applies repo/branch/operation policy). The same shape also works for non-GitHub HTTP credentials: the docs describe a separate "agent proxy" that attaches stored API keys to requests for listed hosts after they leave the VM, which is the analog for iRODS/DE-API tokens.

### [confirmed] Anthropic's cloud environments offer four network access levels (None, Trusted, Full, Custom) enforced by an HTTP/HTTPS security proxy outside the VM, and 'API credentials' are attached by an agent proxy to requests for listed hosts after the request leaves the VM, so the key never appears in the session's env vars or files.

**Evidence.** PRIMARY SOURCE (fetched 2026-09-06, code.claude.com/docs/en/cloud-environments; page is served no-cache, no explicit last-modified date): The "Access levels" table lists exactly four levels: None ("No outbound network access through the session's network"), Trusted ("Allowlisted domains only: package registries, GitHub, cloud SDKs"), Full ("Any domain"), Custom ("Your own allowlist, optionally including the defaults"). Trusted is the default. The "Security proxy" section says: "Cloud sessions in Anthropic-hosted environments run behind an HTTP/HTTPS network proxy for security and abuse prevention purposes ... All outbound internet traffic from an Anthropic-hosted session passes through this proxy" (malicious-request protection, rate limiting, content filtering, DNS-level audit trail of hostnames). The "Add API credentials" section reads verbatim as quoted in the original evidence: "Anthropic's agent proxy adds the key to requests for the hosts you list, after each request leaves the session's VM. The key never reaches Claude, the commands it runs, or the session's environment variables," and the verification step says "the key doesn't appear in the session's environment variables or in any file."

INDEPENDENT CORROBORATION: (1) code.claude.com/docs/en/claude-code-on-the-web "Security and isolation" section: "API credentials: in Anthropic-hosted environments on Pro and Max plans, keys you add to a cloud environment stay outside the sandbox the same way, attached to matching requests after they leave the session." (2) anthropics/claude-code GitHub issue #87378 (2026-08-17, open): a user in a Trusted-level cloud sandbox reports that "the local agent-proxy re-terminates TLS using CN = CCR Upstream Proxy CA (staging), O = Anthropic", with HTTPS_PROXY=http://127.0.0.1:<port> and a CA bundle under /root/.ccr/ — confirming the agent proxy exists and works via TLS interception, which is how header injection is possible. (3) anthropics/claude-code CHANGELOG v2.1.187: "Fixed Claude Code Remote sessions taking ~2.7s longer to start after the agent proxy CA system-trust install was added."

IMPORTANT CAVEATS the claim glosses over: (a) Status: Claude Code on the web / cloud environments are in "research preview" (Pro, Max, Team, Enterprise premium seats); self-hosted environments are "public beta" (Team/Enterprise). (b) API credentials are Pro and Max only — "They aren't available on Team or Enterprise plans yet", not on self-hosted environments, and cannot be saved if the org uses customer-managed encryption keys. (c) There are three distinct proxies, not one: the security proxy (all egress), a separate GitHub proxy (swaps a scoped git credential for the real token; GH_TOKEN reads as the placeholder "proxy-injected"), and the agent proxy (API credentials). (d) The agent proxy never attaches credentials to GitHub, api.anthropic.com, or public package registries (registry.npmjs.org, jsr.io, npm.jsr.io, pypi.org, files.pythonhosted.org, index.crates.io, proxy.golang.org), nor to setup-script requests (the proxy connects only after the setup script runs). (e) Credential hosts, GitHub, MCP connectors, and the Anthropic API bypass the access-level allowlist entirely (Anthropic API reachable even at None, which docs note "may allow data to exit the VM"). (f) The doc says the security proxy sits "behind" the session and requests "leave the session's VM" before the key is added; issue #87378 shows the first hop is a local 127.0.0.1 proxy with a MITM CA inside the VM, so "outside the VM" is accurate for where the credential is held but the enforcement chain starts in-VM. (g) Header format is configurable: default header Authorization with prefix Bearer; can be changed to e.g. X-Api-Key with no prefix. (h) Custom allowlist supports "*." wildcard subdomains and an "Also include default list of common package managers" toggle; no org-level allowlist push exists. (i) Known rough edge: the MITM CA lacked X.509v3 extensions, breaking Python 3.13+ strict verification (issue #87378).

**Implication for VICE.** The taxonomy and injection model are real and current as of 2026-09, so VICE can borrow them, but with design lessons: (1) Model it as three separable proxies — an egress policy proxy (None/Trusted/Full/Custom, implementable with Kubernetes NetworkPolicy plus an HTTP CONNECT/egress proxy such as Envoy/Squid), a git-credential proxy (scoped placeholder token swapped for the real one), and a host-matched credential-injection proxy for AI Verde/Anthropic/OpenAI/Gemini/OSN S3 keys. (2) Header injection over HTTPS requires TLS interception with a per-pod CA installed into the container trust store (SSL_CERT_FILE, java truststore, etc.); Anthropic's own rollout hit CA-extension bugs with Python 3.13 strict verification and Bun proxy incompatibility, so VICE should generate a conformant CA (basicConstraints, keyUsage) and test each bundled agent/SDK. (3) Anthropic deliberately excludes package registries and its own API from the injection path and lets credential hosts bypass the allowlist; VICE should decide explicitly whether credential hosts bypass the egress level. (4) Note Anthropic ships this only for Pro/Max, not Team/Enterprise or self-hosted — there is no Anthropic-provided self-hosted equivalent, so VICE must build its own; self-hosted docs recommend default-deny egress and blocking the cloud metadata endpoint in-container, both directly applicable to VICE pods. (5) Setup-script phase runs before the proxy is live, an ordering VICE must mirror (init containers vs. main container).

Independent source 1, Claude Code doc "Choose a sandbox environment" (code.claude.com/docs/en/sandbox-environments; docs.anthropic.com URL 301-redirects there): comparison table lists "Sandboxed Bash tool: Bash commands and their child processes" vs "Sandbox runtime: The whole Claude Code process, including file tools, MCP servers, and hooks"; text: "The sandboxed Bash tool ... restricts only Bash commands. **Implication for VICE.** The substance of the claim holds and supports the VICE design conclusion, with two refinements. (1) Provenance: cite the MCP/hooks-unconstrained statement to the Claude Code "Choose a sandbox environment" doc, not the README, and cite the repo at github.com/anthropics/sandbox-runtime (the anthropic-experimental URL redirects). (2) Practical consequence for VICE pods: Kubernetes pods running as unprivileged containers normally cannot give bwrap capability-bearing user namespaces or a fresh /proc mount, so in-pod srt/Bash sandboxing will typically require enableWeakerNestedSandbox=true, which Anthropic itself says "considerably weakens security and should only be used when additional isolation is otherwise enforced" -- i.e. Anthropic's own guidance is that the outer container/pod must be the real boundary. Additionally, the seccomp Unix-socket filter is optional and silently degrades to "sockets unrestricted" when unavailable, and a session with write access to ~/.claude or .mcp.json can persist MCP servers/hooks that run unsandboxed on next launch. This confirms that bwrap in-pod is at most a Level-0 convenience control; network egress restrictions for irods, mesa-mcp, and formation-mcp must be enforced via NetworkPolicy/pod-level controls, and config-path write protection (denyWrite on ~/.claude, .mcp.json, .claude/hooks) matters if agents run as the same Unix user as the MCP servers. Note the runtime is beta (v0.0.75, format may change), so do not pin operational policy to its config schema.

## Recommendations

- Adopt the brain/hands split as VICE's core design: keep the human's interactive VICE pod as the 'workbench', and run every autonomous agent job in a separate agent-sandbox Sandbox (agents.x-k8s.io/v1beta1) pod in the same namespace, sharing the user's workspace via a RWX PVC or a per-job clone, so a long job continues (and can be paused/resumed, TTL-reaped, or pulled from a SandboxWarmPool) regardless of whether the human's session is open. This mirrors Anthropic's per-session VM/container and Coder Agents' control-plane loop.
- Copy Anthropic's credential model literally: no user secret is ever mounted into an agent pod. Instead deploy a per-namespace 'agent egress proxy' sidecar/pod (built from anthropic-experimental/sandbox-runtime's proxy or coder/boundary + httpjail) that is the only egress permitted by NetworkPolicy; it terminates TLS, enforces a domain/method/path allowlist, and swaps per-session sentinels for real values fetched from OpenBao (GitHub token, AI Verde key at llm-api.cyverse.ai, Anthropic/OpenAI/Gemini keys, OSN S3 keys with SigV4 re-signing exactly as Claude Code's sandbox.credentials mask/injectHosts/awsPairs does). Git should get a scoped credential with repo scope and push-to-current-branch-only enforcement, as in Anthropic's GitHub proxy.
- For non-HTTP credentials that a proxy cannot rewrite (iRODS native protocol password in ~/.irods/.irodsA, SSH keys), do not expose them to agent pods at all: give agents iRODS access through the irods MCP server run as a ToolHive MCPServer pod with credentials injected from OpenBao, using short-lived iRODS tickets scoped to the job's collections; treat SSH/GitHub via the proxy; the human's interactive pod keeps its normal credentials.
- Define VICE security levels that map onto vendor-proven tiers: L0 'assist' = agent runs in the human's pod under sandbox-runtime/bwrap with denyRead on ~/.irods, ~/.aws, ~/.ssh and env scrubbing (requires enabling unprivileged userns on VICE node images, or accepting enableWeakerNestedSandbox); L1 'background' = separate runc pod, non-root distinct UID, no sudo, default-deny NetworkPolicy, egress only via the credential proxy, network mode 'Trusted' (package registries + GitHub) or 'Custom'; L2 'untrusted' = same pod under gVisor or Kata RuntimeClass via agent-sandbox with read-only HTTP (GET/HEAD/OPTIONS, per Codex/Devin 'limited' mode) and setup-then-offline networking. Make L1 the default for autonomous runs and refuse --dangerously-skip-permissions outside L1/L2, matching Anthropic's own guidance.
- Implement approvals as an asynchronous queue in the DE, not a terminal prompt: the proxy and the harness's permission hooks post 'needs approval' events (new domain, git push, destructive command) to a DE endpoint; the agent pod blocks, the user answers from the DE UI or mobile later, and the session transcript persists in DE storage (as Anthropic cloud sessions and Coder chat persistence do). Use OpenShell-style hot-reloadable network policy so approving a domain updates the proxy allowlist without restarting the pod.
- Route all LLM traffic through an inference gateway (OpenShell's inference.local pattern / Coder AI Gateway pattern): agents get a per-session token that the gateway exchanges for the real AI Verde or vendor key, giving per-user audit and rate limiting and letting self-hosted vLLM/Ollama on GPU nodes be reached only through the gateway rather than from sandboxes directly. Schedule vLLM/Ollama as normal GPU Deployments; only the gateway, not agent sandboxes, needs GPU-node network access.
- Enforce egress at the pod network boundary (NetworkPolicy + proxy), not per process: GitHub Copilot's firewall explicitly excludes MCP servers, and Claude's bwrap sandbox excludes MCP servers and hooks; VICE bundles several MCP servers, so only a pod-level boundary covers them.
- Prefer agent-sandbox + gVisor/Kata + ToolHive + sandbox-runtime/boundary + OpenBao as the all-OSS stack; evaluate NVIDIA OpenShell's Helm chart as an alternative packaged policy engine but note its env-var credential injection is weaker than proxy-side injection. Do not build on Daytona (closed June 2026), E2B (Nomad), or Modal (hosted).
- Support multiple harnesses by making the sandbox image, not the harness, the unit of policy: one base image with Claude Code, Codex, OpenCode, Goose etc. launched non-root as a separate 'agent' UID, each harness configured to use the proxy (HTTPS_PROXY / sandbox settings / OpenShell provider), so credential isolation does not depend on any one vendor's features.
- Verify the two operational prerequisites early on CyVerse nodes: (a) unprivileged user namespaces and/or gVisor or Kata RuntimeClass availability on VICE node pools, and (b) whether boundary's nsjail (CAP_NET_ADMIN) or landjail (kernel 6.7+) is usable in unprivileged pods; if neither, rely on NetworkPolicy + proxy sidecar rather than in-pod jails.
