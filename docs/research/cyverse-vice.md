# CyVerse VICE runtime today (app-exposer, CSI, GPU, egress, AI Sandboxes UI)

Dimension key: `cyverse-vice`. Date: 2026-09-06.

## Summary

Today a VICE analysis becomes a single-replica Kubernetes Deployment in the `vice-apps` namespace, built by app-exposer's `vicebuild` package and (in multi-cluster mode) applied by `vice-operator`. The pod runs one init container (porklock `working-dir-init` on CSI clusters, or `input-files-init` staging otherwise), a `vice-proxy` sidecar that does Keycloak OIDC login and an allowed-users check, an optional porklock file-transfer sidecar, and the `analysis` container. The pod-level securityContext pins RunAsUser/RunAsGroup/FSGroup to the tool's UID and disables the service-account token, but the analysis container drops no capabilities, sets no seccomp profile, and leaves AllowPrivilegeEscalation at its default, which is exactly why the images' `NOPASSWD: ALL` sudo still works. The Data Store reaches the pod as a CSI PersistentVolume (`irods.csi.cyverse.org`, storage class `irods-sc`, client `irodsfuse`) mounted at `/data-store` with a per-analysis `path_mapping_json`, `clientUser` (proxy auth through the `de-irods` admin account), and `no_permission_check=true`; the FUSE privilege lives entirely in the node DaemonSet (privileged, SYS_ADMIN, hostNetwork, Bidirectional mounts), not in the analysis pod. GPU requests become `nvidia.com/gpu` (or `amd.com/gpu`) with requests==limits, node affinity on `gpu=true` and `nvidia.com/gpu.product`, and a `gpu=true:NoSchedule` toleration. Egress is governed by vice-operator NetworkPolicies (namespace default-deny plus a per-analysis egress policy that can be switched to internet-off with explicit CIDR/pod exceptions), which is a ready-made lever for sandbox "security levels". Routing is Gateway API HTTPRoutes through Traefik on `<subdomain>.<frontend-base>` hostnames; ingress-nginx is being retired. On the AI side, Formation is now a hosted, stateless MCP server at `/formation/mcp` using OAuth 2.1 PKCE against Keycloak and forwarding the user's own token to Terrain; the Data Store MCP lives at `mcp.cyverse.ai/mcp` (OAuth, public client `mcp-client`) and `mcp-public.cyverse.ai/mcp` (anonymous); AI Verde is a LiteLLM proxy over vLLM with per-course/team API keys obtained self-service from chat.cyverse.ai. "AI Sandboxes" already exists as `cyverse-de/ai-sandboxes-ui` (private, "AI2S", Next.js, Keycloak, proxies Terrain, shipped in de-releases v2026.05.05) plus a Keycloak `ai-sandbox-authenticator` for university-IdP account linking, i.e. it is a launcher front-end over the same VICE runtime, not a new isolation runtime. The team's own `js2-substrate` design (kagent on Agent Substrate on k3s, gVisor actors) is explicitly unbuilt and untested as of 2026-09-02.

**Implication for VICE.** The mechanism the VICE design relies on is real and current in app-exposer: the Data Store mount is a statically provisioned PV whose only per-user attribute is `clientUser` (proxy auth; the proxy credentials sit in the driver's global secret, not in the pod), and `path_mapping_json` already carries per-entry `read_only`, `create_dir`, and `ignore_not_exist_error` flags plus the driver enforces a `mountPathWhitelist`. So a narrower or read-only mapping for an agent container could be produced by changing only the mapping list app-exposer builds (inputs are already read_only; output, home, and /<zone>/home/shared are read-write today) without any new component. Two corrections to the stated rationale: (1) `no_permission_check=true` does not disable iRODS ACLs. Per irodsfs's own code comment, it only skips the FUSE-side permission/mode computation and reports 0700; the iRODS server still checks permissions on every operation, so an agent cannot exceed the submitting user's iRODS ACLs via this flag, but it also means FUSE mode bits give no useful signal to sandboxing tools that inspect file permissions. (2) Because the VICE container runs as the tool UID and the mount is given `uid`/`gid` equal to that UID, any process in the pod (including AI agents running as the same Unix user) has the same read-write reach to /data-store as the human user; separating agent scope therefore has to happen at the mapping/PV level (a second PV/PVC with a read-only or narrower mapping mounted into an agent sidecar) or via a different clientUser, not via Unix permissions inside the pod. Watch-item: irodsfs main (2026-09-04) has dropped the `no_permission_check` option and added a `readonly` config; if irods-csi-driver upgrades past its pinned irodsfs v0.12.3, app-exposer's `"no_permission_check":"true"` attribute may start being rejected or ignored, so any scoping design should not depend on that flag.

- Evidence: learning.cyverse.org/ai/mcp/general/: Streamable-HTTP `https://mcp.cyverse.ai/mcp`, `https://mcp-public.cyverse.ai/mcp`, SSE deprecated with `Authorization: Basic <base64 username:password>`; aiverde-datastore-mcp-server README: "When prompted for OAuth: Client ID `mcp-client`, Client Secret `<empty>`"; idss-mesa/cli README: "`irods-auth` points at the authenticated endpoint, which uses CyVerse's pre-registered OAuth client (`mcp-client`)".

### AI Verde is built on LiteLLM as the OpenAI-compatible proxy in front of vLLM-served open models on a GPU cluster (with Jetstream2, AWS and Azure) and commercial providers, with CILogon federated login, API keys for user access control, per-group/course budgets, and a Weaviate RAG store; it has been in pilot since May 2024. The public API endpoint is https://llm-api.cyverse.ai (models via GET /v1/models with a Bearer key). Keys are obtained self-service in chat.cyverse.ai under a course/team's Details -> API Key tab, i.e. keys are scoped per course/team rather than documented as per-user LiteLLM virtual keys. Claude Code is supported through Claude Code Router pointed at https://llm-api.cyverse.ai/v1/chat/completions; Codex is not usable because AI Verde does not serve the Responses API.

- Confidence: high (load-bearing); source: <https://arxiv.org/html/2502.09651v1> (arXiv Feb 2025; docs 2025-2026)
- Evidence: arXiv 2502.09651: "vLLM to persistently load LLM in a GPU cluster", "LiteLLM as an LLM proxy" providing an "OpenAI-compliant API access point", CILogon login, "API Keys" with per-group budgets; aiverde-docs api-token page: select course/team, "Details", "API Key" tab; claude-code-router page: base URL `https://llm-api.cyverse.ai/v1/chat/completions`, provider `ai-verde`; idss-mesa/cli README: "Codex — not wired to AI Verde: Codex dropped Chat Completions support and AI Verde does not serve the Responses API."
- Relevance to VICE: LiteLLM natively supports virtual keys with budgets, expirations and per-key model lists, so per-analysis short-lived keys minted at launch are feasible if AI Verde exposes key-generation to CyVerse; today the key in ~/.config/aiverde/env is a long-lived course/team key shared by every agent in the pod.

- Confidence: medium; source: <https://github.com/cyverse-de/app-exposer/blob/main/configs/default.yml> (repo pushed 2026-09-03; DE news Fall 2024)

- Relevance to VICE: Long autonomous agent runs (problem c) are bounded by the analysis planned_end_date, and the pod is a Deployment, so an agent that must outlive the interactive session needs either a second analysis (Formation `launch_app_and_wait`) or the Argo batch path rather than the same pod.

- Confidence: medium (load-bearing); source: <https://github.com/cyverse-de/app-exposer/blob/main/batch/batch.go> (repo pushed 2026-09-03)

- Relevance to VICE: Argo batch is the existing 'uninterrupted autonomous job' substrate with GPU support; also, the iRODS admin properties (porklock-config secret) are outside the analysis container even on non-CSI clusters, so the main leak today is user-brought credentials, not platform ones.

## Recommendations

- Harden the analysis container in vicebuild/deployments.go: set AllowPrivilegeEscalation=false, Capabilities.Drop=[ALL], SeccompProfile RuntimeDefault, and add PodSecurity admission labels to vice-apps (pod-security.kubernetes.io/enforce=restricted, warn/audit first). The CSI mount, vice-proxy and porklock containers are already compatible (UID pinned, no host devices), so the only breakage is image-side sudo usage; treat that as the forcing function to remove `NOPASSWD: ALL` from cyverse-vice/vscode and idss-mesa/cli.
- Give agents their own identity inside the pod: add an optional `agent` container to VICESpec/vicebuild (native sidecar via initContainers with restartPolicy Always, or a second main container) running as a different UID/GID than the human, with a separate home on the working-dir PVC and a narrower `path_mapping_json` CSI PV (read-only inputs, one writable output collection) instead of the whole /data-store home. This removes shared-home credential exposure without leaving the existing pod model.
- Stop copying secrets at startup: remove the `cp -r /data-store/iplant/home/$IPLANT_USER/{.aws,.ssh,.gitconfig}` blocks from the entry.sh of every VICE image and replace them with an OpenBao workflow: app-exposer (or vice-operator) mints a short-lived, per-analysis OpenBao token via Keycloak JWT/OIDC auth (the user's token is already validated by vice-proxy and forwarded by Formation), mounts it only in the human's container (or an agent-broker sidecar), and agents obtain credentials through a broker (e.g. an MCP tool) rather than files in ~/.
- Drop the iRODS password from pods entirely: on CSI clusters the analysis already reads /data-store with no credential, so point in-pod MCP servers (irods-mcp-server, mesa-mcp) at the CSI mount or at the hosted OAuth endpoints (mcp.cyverse.ai/mcp, de.cyverse.org/formation/mcp) and remove `cyverse-login`/~/.irods/.irodsA; where write access outside the mapping is needed, use iRODS tickets minted per analysis rather than the password.
- Turn the existing vice-operator NetworkPolicy machinery into per-analysis 'security levels': move DisableInternet, AllowedCIDRs and PodExceptions from operator flags into VICESpec so buildAnalysisEgressPolicy can emit L0 (Keycloak + llm-api.cyverse.ai + mcp.cyverse.ai + formation only), L1 (plus Harbor/PyPI/CRAN mirrors), and L2 (internet) policies chosen per tool/app; expose the level in ai-sandboxes-ui.
- For per-user LLM credentials, negotiate with the AI Verde team to expose LiteLLM virtual-key generation (LiteLLM key generate with max_budget, duration, models) to app-exposer so each analysis gets a short-lived key injected as OPENAI_API_KEY/ANTHROPIC-compatible env in the agent container and revoked at expiry; until then keep the course/team key only in the human's container.
- For uninterrupted autonomous jobs, do not extend the interactive pod; instead have the interactive session launch a second analysis via Formation `launch_app_and_wait` (headless agent tool, same CSI mapping, its own planned_end_date) or submit an Argo batch job through the existing batch builder (which already supports GPUs); record the parent analysis id as a label so ai-sandboxes-ui can show parent/child runs.
- For self-hosted LLMs, run vLLM as a shared platform Deployment on the GPU node pool (nvidia.com/gpu with nvidia.com/gpu.product affinity, MIG/time-slicing on A16-class cards) fronted by AI Verde's LiteLLM, and reach it from analyses via the L0 egress exception; stop starting Ollama per session inside JupyterLab GPU apps.
- Attach any kagent/Agent Substrate or gVisor-based cluster as a vice-operator target rather than a separate control plane: app-exposer's operator scheduling, GPU model mapping and HTTPRoute transforms already handle heterogeneous clusters, and the team's js2-substrate data-residency analysis argues for limiting that target to public-data or headless agents.
- Encode the new image rules in cyverse-vice/vice-toolkit's audit skill (no NOPASSWD sudo, no secret copying from /data-store, separate agent user, MCP configs pointing at OAuth endpoints) so all seven images (vscode, cli, jupyterlab-*, rstudio-*, kasm-ubuntu) converge before the securityContext change is enforced.

## Open questions

- Is `vice.use_csi_driver` actually true in the production app-exposer/vice-operator config? The sample configs default to false while docs.cyverse.org describes CSI-mounted homes for VICE; the porklock (non-CSI) path changes which containers and secrets exist in the pod.
- Does /dev/fuse exist in production analysis pods? The VICE builder mounts no host devices, yet the images run `sudo s3fs` for OSN buckets; if those mounts fail silently, the OSN credential exposure is real but the mount is not.
- Are PodSecurity admission labels, LimitRanges or ResourceQuotas applied to vice-apps today? The public docs do not mention them.
- Will the AI Verde operators expose LiteLLM key-generation (virtual keys with budgets/expiry) to CyVerse services, and does llm-api.cyverse.ai serve an Anthropic-compatible Messages endpoint for native Claude Code use?
- What exactly does 'AI2S' expand to, and is the ai-sandboxes-ui intended to launch only existing VICE apps or a new sandbox app type in Terrain?
- How does the KasmVNC image (idss-mesa/kasm, private) handle sudo, and does the desktop stack require capabilities that a `restricted` profile would break?
- Which Keycloak client does vice-proxy use in production (the operator comments reference a `vice-users` client) and how are admin entitlement claims mapped?
- Does the DE tool schema (container_devices, container_volumes with host_path) apply to VICE at all, or only to the Argo batch path, when planning GPU device or scratch mounts for agents?
- What is the actual GPU node inventory and labelling (gpu=true, nvidia.com/gpu.product values) on the production and Jetstream2 clusters, and are MIG/time-slicing enabled?
