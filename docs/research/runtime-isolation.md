# Runtime isolation (user namespaces, seccomp/AppArmor, bubblewrap, gVisor, Kata, FUSE)

Dimension key: `runtime-isolation`. Date: 2026-09-06.

## Summary

For VICE the decisive facts are: (1) Kubernetes user namespaces (`hostUsers: false`) went GA in v1.36 (April 2026), need kernel >=6.3 and containerd >=2.0/CRI-O >=1.25, and make capabilities such as CAP_SYS_ADMIN pod-local, which is exactly what is needed to let bubblewrap-based agent sandboxes (Claude Code, Codex, Anthropic srt) and FUSE mounts run inside an unprivileged pod. (2) However, bubblewrap does NOT work under the containerd `RuntimeDefault` seccomp profile at all: the profile only allows `unshare`/`mount`/`setns` when CAP_SYS_ADMIN is present, blocks `clone(CLONE_NEWUSER)` via an argument mask, returns ENOSYS for `clone3`, and never allows `pivot_root` (which bwrap requires), so VICE must ship a `Localhost` seccomp profile (still allowed by PSS `restricted`) plus an AppArmor profile that permits `mount` and `userns`; otherwise agents fall back to Claude Code's weaker `enableWeakerNestedSandbox` mode, and on Ubuntu 24.04 nodes `kernel.apparmor_restrict_unprivileged_userns` must also be handled. (3) gVisor is the best fit for headless autonomous-agent pods and does run CUDA workloads including vLLM-class LLM serving via `--nvproxy` on T4/L4/A100/H100 (CUDA only; no MIG, no DRM/modeset, strict driver-version window), but today gVisor cannot be combined with `hostUsers: false` (kubelet rejects it, gVisor issue #13303, open), ignores pod seccomp/AppArmor, lacks Landlock, and has open bugs running bubblewrap inside it (RTM_NEWADDR, openat2), so nested agent sandboxes inside gVisor are fragile in 2026. (4) FUSE (s3fs/iRODS) works in gVisor only via an in-sandbox daemon on `/dev/fuse` or a raw-protocol external server (`--pass-fd`), and in plain pods needs `/dev/fuse` + CAP_SYS_ADMIN (safe under userns) or a CSI fd-passing driver like meta-fuse-csi-plugin. (5) Kata gives VM-strength isolation with systemd/Docker-in-pod and single-GPU VFIO passthrough (NVIDIA GPU Operator support is Technology Preview, no MIG/vGPU/multi-GPU) but has no user-namespace support and no checkpoint/restore; Firecracker (standalone, Kata, or E2B) has no GPU device model. (6) Sysbox is the pragmatic middle for KasmVNC/systemd/Docker workloads but loses NVIDIA container-runtime GPU access. (7) Among agent substrates, kubernetes-sigs/agent-sandbox (v1.0.1, Sept 2026, Sandbox/SandboxTemplate/SandboxClaim/SandboxWarmPool CRDs over RuntimeClass) is the mature, vendor-neutral choice; Google's Agent Substrate is explicitly early/aspirational; kagent is an ops-agent framework, not an isolation substrate. Recommended VICE design: keep the human interactive image on runc + userns + hardened profiles, run autonomous agents in separate gVisor (or Kata for GPU/Docker) sandbox pods that share the user's PVC, enforce egress at the cluster level (Cilium FQDN policy or Squid SNI allowlist) rather than trusting per-tool proxies, and use Claude Code/Codex credential deny/mask settings as defense in depth.

## Fact-check verdicts on load-bearing claims

### [confirmed] Kubernetes user namespaces (`pod.spec.hostUsers: false`) reached GA in Kubernetes v1.36 (April 2026); they were enabled by default (beta) in v1.33 (April 2025). Requirements: Linux kernel >= 6.3 (idmap mounts incl. tmpfs), containerd >= 2.0 or CRI-O >= 1.25, runc >= 1.2 or crun >= 1.9 (1.13+ recommended); the filesystem under /var/lib/kubelet/pods must support idmap mounts; a `kubelet` system user and `getsubids` (shadow-utils) on the node.

**Evidence.** Every element of the claim is corroborated by primary sources plus independent runtime sources; I could not refute any part.

The node stack floor is as stated: kernel >= 6.3, containerd >= 2.0 (or CRI-O >= 1.25), runc >= 1.2 or crun >= 1.13 (recommended), idmap-capable filesystem (ext4/xfs/btrfs/overlayfs) under /var/lib/kubelet/pods and for every pod volume, plus a `kubelet` system user with subordinate ID ranges and `getsubids` in the kubelet PATH. ### [partially_true] With `hostUsers: false`, capabilities granted to the pod (e.g. CAP_SYS_ADMIN, CAP_NET_ADMIN) are scoped to the pod's user namespace and are not valid on the host; KEP-127 explicitly lists 'CAP_SYS_ADMIN to mount a FUSE filesystem' as a target user story. The KEP also warns that a userns pod without any seccomp profile 'has access to the unshare syscall, allowing a user to create a user namespace in the pod, and gain the full set of capabilities within a user namespace'. hostNetwork: true is incompatible with hostUsers: false.

**Corrected claim.** With `hostUsers: false` (KEP-127, feature gate `UserNamespacesSupport`: alpha v1.25, beta v1.30, beta-on-by-default v1.33, GA/locked v1.36), capabilities granted to the pod are limited to the pod's user namespace and 'mostly invalid out of it' (CAP_SYS_ADMIN 'invalid outside of it'; CAP_SYS_MODULE has no effect at all). KEP-127 Story 1 names 'CAP_SYS_ADMIN to mount a FUSE filesystem or CAP_NET_ADMIN to setup a VPN', and its PSS section notes a pod without a seccomp profile has access to `unshare` and can gain full capabilities inside a nested user namespace. hostNetwork/hostPID/hostIPC: true (and container volumeDevices) are rejected by API validation when hostUsers is false -- BUT since v1.35 a separate alpha feature gate `UserNamespacesHostNetworkSupport` (KEP-5607, default false, still alpha in v1.36) lifts the hostNetwork restriction when enabled. Requirements: Linux >= 6.3 (idmap mounts on tmpfs), containerd >= 2.0 or CRI-O >= 1.25, runc >= 1.2 or crun >= 1.9.

**Evidence.** PRIMARY (KEP-127 README, kubernetes/enhancements master, kep.yaml stage: stable, latest-milestone v1.36, milestones alpha v1.25 / beta v1.35 / stable v1.36 per kep.yaml -- note kube_features.go shows the gate actually went beta at 1.30 and default-on at 1.33): Goals: 'Allow pods to have capabilities (e.g. CAP_SYS_ADMIN) that are only valid in the pod (not valid in the host).' **Implication for VICE.** The core mechanism VICE wants is sound and now GA: on a cluster at v1.36+ (or v1.33-1.35 with the default-on beta gate) with Linux >= 6.3 nodes and containerd 2.0+/runc 1.2+ (or CRI-O 1.25+/crun), VICE can set hostUsers: false and add CAP_SYS_ADMIN for FUSE (e.g. iRODS FUSE) or bubblewrap without that capability meaning anything on the host -- exactly KEP-127 Story 1. Two corrections to the working assumptions: (1) the 'nested user namespace via unshare' path is gated by seccomp, not by capabilities -- the default RuntimeDefault seccomp profile (kubelet seccompDefault / pod securityContext.seccompProfile) blocks unshare with CLONE_NEWUSER for unprivileged processes, so bubblewrap-style sandboxing inside a userns pod requires either dropping to seccompProfile: Unconfined (or a custom Localhost profile allowing unshare/clone) or granting CAP_SYS_ADMIN, and VICE must decide which explicitly; (2) the hostNetwork incompatibility is no longer absolute -- it is enforced by API validation by default, but the alpha gate UserNamespacesHostNetworkSupport (v1.35+, KEP-5607) removes it if a cluster admin enables it; hostPID and hostIPC remain unconditionally forbidden with hostUsers: false. Verify the actual cluster and node versions before assuming the feature is on.

### [confirmed] Under containerd's default (RuntimeDefault) seccomp profile, bubblewrap cannot run even if CAP_SYS_ADMIN is added: without CAP_SYS_ADMIN, clone is only allowed when none of CLONE_NEWNS|CLONE_NEWUSER|CLONE_NEWPID|CLONE_NEWNET|... are set, clone3 returns ENOSYS, and unshare, mount, umount2, setns, mount_setattr, open_tree are only allowlisted when CAP_SYS_ADMIN is present; pivot_root is not in the allowlist in either case. bubblewrap's source calls clone with CLONE_NEWUSER (when --unshare-user), pivot_root, and mounts a fresh /proc.

**Evidence.** Every element checked against primary sources fetched 2026-09-06.

**Implication for VICE.** The claim holds as of 2026-09 (containerd v2.3.5, bubblewrap v0.12.0): bwrap cannot start in a VICE pod under seccompProfile.type: RuntimeDefault, and adding SYS_ADMIN does not fix it because pivot_root is never allowlisted. Three corrections to the proposed remedy: (1) The custom Localhost seccomp profile must allow clone with CLONE_NEWNS (bwrap always sets it) in addition to CLONE_NEWUSER/CLONE_NEWPID/CLONE_NEWNET, plus unshare, setns, mount, umount2, pivot_root, and (for newer mount API use) mount_setattr/open_tree/move_mount; clone3 handling is irrelevant to bwrap since it calls __NR_clone directly. (2) A seccomp profile alone is NOT sufficient on AppArmor-enabled nodes (e.g. Ubuntu): containerd's CRI applies its default AppArmor profile 'cri-containerd.apparmor.d' when the pod specifies none (apparmor_linux.go: 'default apparmor profile should be applied for when apparmor is not specified', kubernetes#51746), and that template contains 'deny mount,' (template.go line 81), which is exactly the 'Failed to make / slave: Permission denied' failure the Codex PR hit. VICE must also set securityContext.appArmorProfile.type: Unconfined (or a Localhost AppArmor profile permitting mount/pivot_root) — the appArmorProfile field is stable since Kubernetes 1.31. (3) Even with both relaxed, bwrap --proc /proc will still fail inside a pod because the container's /proc has masked paths; users need bwrap without --proc, or the pod needs procMount: Unmasked, which requires hostUsers: false (both ProcMountType and UserNamespacesSupport are Stable since Kubernetes 1.36, beta-on since 1.33), which in turn depends on the cluster's node/kubelet/containerd/idmapped-mount support. Alternatively, running the pod with hostUsers: false gives the agent a user namespace where bwrap's CLONE_NEWUSER need is partly moot, but the seccomp allowlist still blocks clone/pivot_root, so the Localhost seccomp + AppArmor changes remain necessary. Unconfined seccomp is the fallback the Codex project itself chose, at the cost of losing the outer-sandbox syscall filter for the whole VICE container.

### [partially_true] Two more layers block bubblewrap in pods: (a) containerd's default AppArmor template contains `deny mount,` (Codex's devcontainer PR reports 'Failed to make / slave: Permission denied' from the default AppArmor profile, fixed with apparmor=unconfined); (b) on Ubuntu 23.10+/24.04 nodes, `kernel.apparmor_restrict_unprivileged_userns=1` blocks unconfined binaries such as bwrap/unshare from creating user namespaces unless an AppArmor profile grants `userns`; Claude Code docs ship a `profile bwrap /usr/bin/bwrap flags=(unconfined) { userns, }` profile or the sysctl can be set to 0.

**Corrected claim.** (a) Confirmed with attribution fix: containerd's contrib/apparmor/template.go (copied from moby's profiles/apparmor, last touched 2026-09-02) contains `deny mount,` and pins `abi <abi/3.0>`; the resulting pod profile is named `cri-containerd.apparmor.d`. Codex PR #17547 (merged 2026-04-12) attributes 'Failed to make / slave: Permission denied' to DOCKER's default AppArmor profile, not containerd's — equivalent text, but the PR also needed `seccomp=unconfined`, `--cap-add=SYS_ADMIN/SYS_CHROOT/SETUID/SETGID/SYS_PTRACE` and a setuid bwrap, so AppArmor was not the sole blocker in that fix. (b) The userns restriction shipped in Ubuntu 23.10 but was NOT enabled by default there; it is enabled by default (sysctl=1) from Ubuntu 24.04. It applies to unprivileged, UNCONFINED processes; the Claude Code docs profile text is verbatim correct (`abi <abi/4.0>`, `include <tunables/global>`, `profile bwrap /usr/bin/bwrap flags=(unconfined) { userns, include if exists <local/bwrap> }`), and Ubuntu documents `kernel.apparmor_restrict_unprivileged_userns=0` in /etc/sysctl.d as the alternative. Caveat for pods: a container under the RuntimeDefault profile is confined (not unconfined), and containerd compiles the profile against abi/3.0, which per Ubuntu's own design note lacks the userns feature and therefore silently grants userns — so in a RuntimeDefault pod the likely blocker is `deny mount,`, while the userns sysctl bites when the pod runs AppArmor-Unconfined. The quoted Ubuntu sentence ('will be blocked unless they have an AppArmor profile explicitly granting the userns permission') was not found verbatim in the cited discourse post or the 24.04 release notes.

**Evidence.** containerd template.go (fetched 2026-09-06, last commit 3c10e5f 2026-09-02): line 81 `deny mount,`; header comment 'This code is copied from <github.com/docker/docker/profiles/apparmor>'; profile flags `attach_disconnected,mediate_deleted`; `const abi = "abi/3.0"` used when /etc/apparmor.d/abi/3.0 exists; no `userns` rule anywhere. ## Findings

### Kubernetes user namespaces (`pod.spec.hostUsers: false`) reached GA in Kubernetes v1.36 (April 2026); they were enabled by default (beta) in v1.33 (April 2025). Requirements: Linux kernel >= 6.3 (idmap mounts incl. tmpfs), containerd >= 2.0 or CRI-O >= 1.25, runc >= 1.2 or crun >= 1.9 (1.13+ recommended); the filesystem under /var/lib/kubelet/pods must support idmap mounts; a `kubelet` system user and `getsubids` (shadow-utils) on the node.

- Confidence: high (load-bearing); source: <https://kubernetes.io/blog/2026/04/23/kubernetes-v1-36-userns-ga/> (2026-04-23 (blog); docs page marked v1.36+)
- Evidence: Blog: 'User Namespaces support reached General Availability (GA) in Kubernetes v1.36 with the hostUsers: false field'. Docs: 'stable feature since Kubernetes v1.36', 'Minimum Linux version: 6.3', 'containerd: version 2.0 (and later)', 'CRI-O: version 1.25 (and later)', 'crun version 1.9 or greater', 'runc version 1.2 or greater'.
- Relevance to VICE: Sets the minimum node stack (kernel 6.3+, containerd 2.0+) for VICE's next iteration; userns is the foundation that makes in-pod agent sandboxes and FUSE mounts safe without host privileges.

### With `hostUsers: false`, capabilities granted to the pod (e.g. CAP_SYS_ADMIN, CAP_NET_ADMIN) are scoped to the pod's user namespace and are not valid on the host; KEP-127 explicitly lists 'CAP_SYS_ADMIN to mount a FUSE filesystem' as a target user story. The KEP also warns that a userns pod without any seccomp profile 'has access to the unshare syscall, allowing a user to create a user namespace in the pod, and gain the full set of capabilities within a user namespace'. hostNetwork: true is incompatible with hostUsers: false.

- Confidence: high (load-bearing); source: <https://github.com/kubernetes/enhancements/blob/master/keps/sig-node/127-user-namespaces/README.md> (KEP updated for GA (2026); docs v1.36)
- Evidence: Docs: 'Capabilities granted to a pod are also limited to the pod user namespace' ; KEP-127: 'Allow pods to have capabilities (e.g. CAP_SYS_ADMIN) that are only valid in the pod' and 'As a cluster admin, I want run some pods with privileged capabilities ... (e.g. CAP_SYS_ADMIN to mount a FUSE filesystem'. Docs: 'if you set hostUsers: false then you are not allowed to set: hostNetwork: true'.
- Relevance to VICE: Means VICE can grant CAP_SYS_ADMIN inside a userns pod for FUSE/bwrap without giving host root; and that seccomp is what actually gates nested user namespaces (bubblewrap).

### Under containerd's default (`RuntimeDefault`) seccomp profile, bubblewrap cannot run even if CAP_SYS_ADMIN is added: without CAP_SYS_ADMIN, `clone` is only allowed when none of CLONE_NEWNS|CLONE_NEWUSER|CLONE_NEWPID|CLONE_NEWNET|... are set, `clone3` returns ENOSYS, and `unshare`, `mount`, `umount2`, `setns`, `mount_setattr`, `open_tree` are only added to the allowlist when CAP_SYS_ADMIN is present; `pivot_root` is not in the allowlist in either case. bubblewrap's source calls clone with CLONE_NEWUSER (when --unshare-user), `pivot_root`, and mounts a fresh /proc.

- Confidence: high (load-bearing); source: <https://github.com/containerd/containerd/blob/main/contrib/seccomp/seccomp_default.go> (containerd main branch, fetched 2026-09-06; Codex PR 2026)
- Evidence: containerd seccomp_default.go: `case "CAP_SYS_ADMIN": ... Names: "bpf","clone","clone3",...,"mount","mount_setattr",...,"setns",...,"umount2","unshare"`; non-admin rule: `"clone"` allowed with Args mask `CLONE_NEWNS|CLONE_NEWUTS|CLONE_NEWIPC|CLONE_NEWUSER|CLONE_NEWPID|CLONE_NEWNET|CLONE_NEWCGROUP`, `ValueTwo: 0`, `Op: OpMaskedEqual`; comment 'clone3 is explicitly requested to give ENOSYS instead of the default EPERM, when CAP_SYS_ADMIN is unset'. grep for "pivot_root" in the profile returns nothing. bubblewrap.c: `if (opt_unshare_user) clone_flags |= CLONE_NEWUSER;` ... `if (pivot_root (base_path, "oldroot")) die_with_error ("pivot_root");` and `die_with_mount_error ("Can't mount proc on %s", op->dest)`. Corroborated by OpenAI Codex PR #17547: Docker's default seccomp 'blocks bubblewrap with pivot_root: Operation not permitted even when CAP_SYS_ADMIN is present'.
- Relevance to VICE: This is the concrete answer to 'can bubblewrap run in a non-privileged pod': not under RuntimeDefault. VICE must deploy a custom Localhost seccomp profile (allowing clone/unshare with CLONE_NEWUSER, mount, umount2, pivot_root, setns, mount_setattr) or, less safely, seccomp Unconfined.

### Two more layers block bubblewrap in pods: (a) containerd's default AppArmor template contains `deny mount,` (Codex's devcontainer PR reports 'Failed to make / slave: Permission denied' from the default AppArmor profile, fixed with apparmor=unconfined); (b) on Ubuntu 23.10+/24.04 nodes, `kernel.apparmor_restrict_unprivileged_userns=1` blocks unconfined binaries such as bwrap/unshare from creating user namespaces unless an AppArmor profile grants `userns`; Claude Code docs ship a `profile bwrap /usr/bin/bwrap flags=(unconfined) { userns, }` profile or the sysctl can be set to 0.

- Confidence: high (load-bearing); source: <https://github.com/containerd/containerd/blob/main/contrib/apparmor/template.go> (containerd main; Ubuntu spec 2023; Claude Code docs fetched 2026-09-06)
- Evidence: containerd contrib/apparmor/template.go line 81: `deny mount,`. Ubuntu discourse: applications 'that depend on unprivileged user namespaces will be blocked unless they have an AppArmor profile explicitly granting the userns permission'. Claude Code docs: 'On Ubuntu 24.04 and later, the default AppArmor policy prevents bubblewrap from creating the user namespaces it needs'.
- Relevance to VICE: VICE nodes on Ubuntu 24.04 need node-level prep (sysctl or bwrap AppArmor profile) plus a pod AppArmor `Localhost` profile allowing mount/userns (PSS baseline/restricted forbid `Unconfined` AppArmor); otherwise every agent CLI sandbox silently degrades.

### Pod Security Standards `restricted` requires allowPrivilegeEscalation=false, capabilities drop ALL (only NET_BIND_SERVICE may be added), runAsNonRoot, seccompProfile RuntimeDefault or Localhost (Unconfined forbidden), AppArmor RuntimeDefault or Localhost, no hostPath, procMount Default only. `Localhost` seccomp profiles must live under `/var/lib/kubelet/seccomp` on the node and are OCI JSON (`defaultAction`, `syscalls[].names/action`).

- Confidence: high (load-bearing); source: <https://kubernetes.io/docs/concepts/security/pod-security-standards/> (kubernetes.io current (v1.36))
- Evidence: PSS: 'seccompProfile.type: RuntimeDefault or Localhost (required)', 'capabilities.add: [NET_BIND_SERVICE] (only allowed capability)', 'hostPath - FORBIDDEN', 'ProcMount: Default only'. Seccomp doc: 'Profile must be available on the node disk at: /var/lib/kubelet/seccomp'; 'It is not possible to apply a seccomp profile to a Pod or container running with privileged: true'.
- Relevance to VICE: A bubblewrap-capable pod cannot be fully PSS-restricted if it needs CAP_SYS_ADMIN (even namespaced); VICE should define its own 'AI sandbox' policy = baseline + userns + Localhost seccomp/AppArmor + no hostPath, and enforce it via admission rather than the stock restricted profile.

### gVisor supports NVIDIA GPUs via `runsc --nvproxy`, a passthrough ioctl driver with 'negligible performance impact' for GPU-bound work, supporting 'most CUDA workloads, including PyTorch and various generative models like LLMs' plus Vulkan and NVENC/NVDEC (driver caps `compute,utility,graphics,video`, default compute+utility). - Evidence: Issue #13303: 'Failed to create pod sandbox: can't set spec.hostUsers: false, RuntimeClass handler "runsc" does not support user namespaces' with Kubernetes 1.35.2, containerd 2.2.2, runsc release-20260520.0. GKE doc: incompatible with 'Hostpath storage', 'privileged mode', 'Linux kernel security modules such as Seccomp, Apparmor, or Selinux'.
- Relevance to VICE: VICE's security levels must be modeled as alternative tiers, not a stack: a gVisor tier (Sentry isolation, pod seccomp ignored) versus a runc+userns tier (Localhost seccomp/AppArmor). Do not plan on hostUsers:false + gVisor together.

### Running bubblewrap (and thus Claude Code/Codex/srt sandboxes) inside gVisor is partially broken as of mid-2026: `bwrap --unshare-net` fails with 'loopback: Failed RTM_NEWADDR' (issue #13438, 2026-06-13, fix PR #13532 pending), bubblewrap 0.12's openat2(RESOLVE_IN_ROOT) returns ENOSYS in gVisor (issue #14451, 2026-08-27), gVisor does not implement Landlock syscalls so Codex's legacy Landlock mode and tools like nono cannot apply policy (issue #13439, 2026-06-13), and a nested-userns overlay rename EPERM bug exists (#14033). gVisor's syscall table lists `unshare` as partial (time/cgroup namespaces unsupported), `seccomp` full, `clone3` partial, `io_uring_register` unimplemented.

- Confidence: high (load-bearing); source: <https://github.com/google/gvisor/issues/13438> (2026-06 to 2026-08)

- Relevance to VICE: If VICE puts agents in gVisor pods, the agent CLIs will need `enableWeakerNestedSandbox`/no inner sandbox (treat gVisor as the boundary) until these issues close; pin bubblewrap < 0.12 or build without assume_kernel.

### FUSE under gVisor is supported in two modes: (1) a FUSE daemon inside the sandbox talking to the Sentry via `/dev/fuse`; (2) an external (host-side) FUSE server passed in via `runsc --pass-fd=HOST_FD:GUEST_FD` and mounted with `mount -t fuse ... -o fd=<n>` — the external server must speak the raw FUSE kernel protocol (FUSE_INIT, FUSE_GETATTR, FUSE_LOOKUP, FUSE_OPEN, FUSE_READ, FUSE_RELEASE, FUSE_ACCESS) and 'higher-level FUSE libraries (e.g., libfuse) ... may not work directly over a socketpair'. A gVisor issue also notes FUSE mounted on the host can be exported into the sandbox as a regular host filesystem (with drawbacks). gVisor's `mount`/`umount2` are fully supported syscalls.

- Confidence: high (load-bearing); source: <https://gvisor.dev/docs/user_guide/fuse/> (gvisor.dev current (fetched 2026-09-06))
- Evidence: gvisor.dev FUSE page: 'A FUSE daemon runs inside the sandbox and communicates with the gVisor kernel via /dev/fuse'; '--pass-fd=HOST_FD:GUEST_FD'; 'Higher-level FUSE libraries (e.g., libfuse) typically expect /dev/fuse and may not work directly over a socketpair without adaptation'. Issue #12396: 'FUSE can be mounted on the host and exported to gVisor as a regular host filesystem, but it has drawbacks'.
- Relevance to VICE: s3fs/irods-fuse can run inside a gVisor pod (in-sandbox mode) but with Sentry-mediated I/O overhead; the cleaner design is to mount OSN S3 / iRODS on the node via CSI and bind it in, which requires a driver rather than hostPath.

### In ordinary (runc) pods, mounting FUSE (s3fs) requires `/dev/fuse` exposure plus `CAP_SYS_ADMIN` and (on AppArmor nodes) an unconfined/permissive AppArmor profile (kubernetes/kubernetes #79265); the Preferred Networks meta-fuse-csi-plugin (Apache-2.0) avoids pod privileges by having a privileged DaemonSet perform open('/dev/fuse') and mount() and pass the fd over a Unix socket to an unprivileged sidecar, supporting s3fs, goofys, mountpoint-s3, gcsfuse, sshfs (Kubernetes >= 1.30 sidecar containers recommended). Device plugins for /dev/fuse are another option.

- Confidence: high (load-bearing); source: <https://github.com/pfnet-research/meta-fuse-csi-plugin/blob/main/README.md> (README (tested K8s 1.27.3; project active))
- Evidence: meta-fuse-csi-plugin README: 'CSI driver Pods are deployed by cluster operators on each node as DaemonSet. They process privileged operations (open("/dev/fuse") and mount("fuse", ...)) on behalf of FUSE implementations'; supported: 'mountpoint-s3, goofys, s3fs, ros3fs, gcsfuse, sshfs'. Issue #79265: needs 'SYS_ADMIN capability, /dev/fuse device access, AppArmor set to unconfined'.
- Relevance to VICE: Gives VICE two viable FUSE paths on the runc+userns tier: (1) userns pod + CAP_SYS_ADMIN (namespaced) + /dev/fuse via device plugin + AppArmor Localhost profile; (2) fd-passing CSI so the interactive pod stays capability-free. An iRODS FUSE client would need the fuse-starter/fusermount3-proxy pattern.

### gVisor's default platform is systrap (seccomp SECCOMP_RET_TRAP based; ptrace deprecated mid-2023); KVM platform is fastest on bare metal but needs /dev/kvm and suffers under nested virtualization. Performance guidance: raw disk I/O has minimal overhead but VFS-heavy workloads with many small file operations (Python/Node imports, builds) pay measurable overhead; Directfs (default) made stat() >2x faster than the gofer model. GKE warns that workloads generating 'a large volume of low-overhead system calls' may need more resources. - Confidence: medium; source: <https://gvisor.dev/docs/architecture_guide/platforms/> (gvisor.dev current; Directfs blog 2023-06-27)
- Evidence: Platforms guide: 'systrap ... Became the default platform in mid-2023'; 'KVM ... Requires /dev/kvm support and encounters overhead with nested virtualization'. Performance guide: 'VFS operations introduce measurable costs in scenarios involving many small file accesses'.
- Relevance to VICE: RStudio (R package loading), JupyterLab (Python imports) and node-based agents are exactly the small-file-heavy workloads that feel gVisor overhead; expect noticeable but not prohibitive slowdown. No primary source documents KasmVNC/Xvnc under gVisor; DRM is unsupported so GPU-accelerated desktops are out.

### Kata Containers GPU support is VFIO passthrough with the NVIDIA driver built and loaded in the guest kernel (host needs CONFIG_VFIO*, IOMMU on; guest needs CONFIG_HOTPLUG_PCI_PCIE, CONFIG_MODULES, CONFIG_PCI_MMCONFIG). NVIDIA GPU Operator's Kata integration (RuntimeClass `kata-qemu-nvidia-gpu`, resources like `nvidia.com/GA102GL_A10`, Helm `sandboxWorkloads.enabled=true`, `kataManager.enabled=true`; components NVIDIA Kata Manager, Sandbox Device Plugin, VFIO Manager) is 'Technology Preview', containerd-only, single-GPU passthrough only: 'Multi-GPU passthrough and vGPU are not supported', MIG not supported, and 'Support is limited to initial installation and configuration only'. Confidential Containers + GPU follows the same vm-passthrough model with the same multi-GPU/vGPU limits.

- Confidence: high (load-bearing); source: <https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/gpu-operator-kata.html> (NVIDIA GPU Operator docs v25.10.0; Kata docs main)
- Evidence: Kata doc: '/nvidia-installer -k 5.15.23-nvidia-gpu' against the guest kernel; NVIDIA doc: 'Multi-GPU passthrough and vGPU are not supported', 'Technology Preview status - not for production environments', RuntimeClass 'kata-qemu-nvidia-gpu'.
- Relevance to VICE: A Kata tier can host vLLM/Ollama with a whole dedicated GPU per pod (no MIG/time-slicing), which fits ad-hoc self-hosted inference but wastes GPUs for many small users; operational support is preview-grade.

### Kata does not support Kubernetes user namespaces (issue #8170 'support user namespace', open since 2023-10-08); documented limitations include no HostNetwork, no `volumeMounts.subPath`, `checkpoint`/`restore` unavailable, and different privileged semantics. The Kata guest kernel config enables CONFIG_FUSE_FS, CONFIG_VIRTIO_FS and OverlayFS ('Docker in Docker support requires overlay'), and ships landlock.conf and seccomp.conf kernel fragments, so in-guest FUSE, nested containers, Landlock and seccomp are available inside the VM. Kata with the Firecracker VMM requires the devmapper snapshotter and block-backed storage and documents no VFIO/GPU path; Firecracker's own FAQ lists only virtio-net, virtio-balloon, virtio-block, virtio-vsock, serial console and a minimal keyboard controller as devices.

- Confidence: high (load-bearing); source: <https://github.com/kata-containers/kata-containers/issues/8170> (issue 2023-10-08 (open 2026-09); docs main)
- Evidence: Kata issue #8170: 'Now it is time for kata to be in the party and integrate with containerd to handle idmapped mount and user namespace'. Limitations.md: 'Host network ... is not supported'; 'checkpoint and restore commands are unavailable'. fs.conf: 'CONFIG_OVERLAY_FS=y ... CONFIG_VIRTIO_FS=y CONFIG_FUSE_FS=y'. Firecracker FAQ device list.
- Relevance to VICE: Kata is the tier where bubblewrap/Landlock-based agent sandboxes and Docker/systemd work unmodified (guest kernel is a normal Linux), FUSE works in-guest, and no userns interaction issues arise; but Firecracker-backed Kata cannot do GPUs, so GPU Kata means QEMU or Cloud Hypervisor.

### Sysbox (Community Edition, Apache-2.0; Docker is 'main sponsor' with best-effort support; Enterprise Edition deprecated) runs pods with `runtimeClassName: sysbox-runc` plus `hostUsers: false` (K8s >= 1.30 with containerd 2.0+, but 2.0.1–2.0.4 are broken with userns pods; otherwise the installer deploys CRI-O) and supports Kubernetes v1.32–v1.35 on Ubuntu nodes (5.4+ kernel), enabling systemd, Docker, buildx and K8s inside unprivileged pods. Kasm's documentation states that under Sysbox 'NVIDIA GPU support via the NVIDIA Container Runtime is unavailable' (DRI3 with open-source drivers works), and Sysbox issue #901 (2025) tracks multi-GPU failures.

- Confidence: high; source: <https://github.com/nestybox/sysbox/blob/master/docs/user-guide/install-k8s.md> (Sysbox docs current (repo pushed 2026-09-03); Kasm 1.17 docs)
- Evidence: install-k8s.md: 'Sysbox supports Kubernetes v1.32, v1.33, v1.34, and v1.35'; 'versions 2.0.1 through 2.0.4 have compatibility issues with user-namespace pods'; Kasm docs: 'NVIDIA GPU support via the NVIDIA Container Runtime is unavailable; however, DRI3 using open source drivers will still function'.
- Relevance to VICE: Sysbox is the lowest-friction way to give the KasmVNC Ubuntu desktop image systemd + Docker + real sudo inside a rootless pod, but it forfeits NVIDIA GPU access, so it should not be the GPU tier.

### Landlock is an unprivileged, inheritable kernel sandbox: enforcement requires `PR_SET_NO_NEW_PRIVS` (or the LANDLOCK_RESTRICT_SELF_NO_NEW_PRIVS flag in ABI v11+) unless the caller has CAP_SYS_ADMIN; ABI v4 adds TCP bind/connect restriction, v6 signal/abstract-socket scoping, v10 UDP; it must be enabled in the boot `lsm=` list. containerd's RuntimeDefault seccomp allowlist includes `landlock_add_rule`, `landlock_create_ruleset`, `landlock_restrict_self`, so Landlock works in normal pods without any custom profile; gVisor does not implement it.

- Confidence: high; source: <https://docs.kernel.org/userspace-api/landlock.html> (kernel docs current)
- Evidence: kernel docs: 'Landlock empowers any process, including unprivileged ones, to securely restrict themselves'; ABI v4 'LANDLOCK_ACCESS_NET_BIND_TCP, LANDLOCK_ACCESS_NET_CONNECT_TCP'. containerd profile lines 196-198 list the three landlock syscalls.
- Relevance to VICE: Landlock-based filesystem restriction (e.g., Codex `use_legacy_landlock`) is the one agent sandbox mechanism that works under a stock PSS-restricted pod with zero node changes — useful as a fallback tier, but only on runc/Kata, not gVisor.

### Egress allowlisting options: native Kubernetes NetworkPolicy has no FQDN selectors; Cilium's CiliumNetworkPolicy supports DNS/FQDN-based egress (`toFQDNs` with `matchName`/`matchPattern`) by proxying DNS to learn IPs, plus L7 HTTP rules via its embedded Envoy; Squid supports `dstdomain` ACLs for plain HTTP and `ssl::server_name` ACLs that match CONNECT URIs / TLS SNI for HTTPS allowlisting without decryption. Both Claude Code's and srt's proxies decide on the client-supplied hostname without TLS termination unless `network.tlsTerminate` is set, and Claude Code warns of domain fronting.

- Confidence: medium; source: <http://www.squid-cache.org/Doc/config/acl/> (squid-cache.org current; Cilium blog 2026-03-13; Claude Code docs 2026)
- Evidence: Squid docs: ssl::server_name 'matches server name obtained from various sources' including 'CONNECT request URIs, TLS client SNI'. Cilium blog/docs (secondary): 'FQDN-based policies let you write rules like allow traffic to *.s3.amazonaws.com on port 443'. Claude Code docs: 'the proxy makes its allow decision from the client-supplied hostname without inspecting TLS'.
- Relevance to VICE: VICE should enforce the domain allowlist (llm-api.cyverse.ai, api.anthropic.com, github.com, PyPI/CRAN mirrors, data.cyverse.org) at the CNI/proxy layer per pod, so an agent that disables its own sandbox proxy still cannot exfiltrate ~/.irods/.irodsA.

### kubernetes-sigs/agent-sandbox (Apache-2.0, SIG Apps, ~3.75k stars, latest release v1.0.1 on 2026-09-03) provides a `Sandbox` CRD (v1beta1) for long-running, stateful, singleton workloads with stable identity and persistent storage, with `SandboxTemplate`, `SandboxClaim` and `SandboxWarmPool` extensions and a Python SDK; it delegates isolation to RuntimeClass (gVisor or Kata+QEMU) rather than being a runtime. Google's Agent Substrate (agent-substrate/substrate, Apache-2.0, 'not an officially supported Google product', release v0.0.0 2026-05-19) multiplexes suspended 'actors' onto 'WorkerPool' pods using gVisor (default) or Cloud Hypervisor microVMs, checkpointing to Google Cloud Storage, and states 'currently in early development. It is not ready for production use' and 'Much of this architecture is aspirational'. kagent (CNCF sandbox, Apache-2.0) defines Agent/ModelConfig/ToolServer/RemoteMCPServer CRDs for cloud-native operations agents and has no sandboxing/isolation feature.

- Confidence: high; source: <https://github.com/kubernetes-sigs/agent-sandbox/blob/main/README.md> (2026-09 (agent-sandbox v1.0.1); Substrate May–Sept 2026)
- Evidence: agent-sandbox README: 'delegates to secure Sandbox Runtimes (like gVisor or Kata Containers) via RuntimeClass'; GitHub releases API: v1.0.1 2026-09-03. Substrate README: 'It is not ready for production use, and the APIs are almost guaranteed to change'; architecture.md: 'Much of this architecture is aspirational, and is not yet implemented!'. kagent README: no references to gVisor/Kata/sandboxing.
- Relevance to VICE: For the 'AI Sandboxes' iteration, agent-sandbox is the vendor-neutral, K8s-native orchestration layer VICE's app-exposer could target; Agent Substrate should be watched, not adopted; kagent addresses a different problem (ops agents) than runtime isolation.

### Other sandbox platforms: OpenSandbox (opensandbox-group/OpenSandbox, Apache-2.0, ~15k stars, active Sept 2026) offers multi-language SDKs, Docker and Kubernetes runtimes, gVisor/Kata/Firecracker backends and VNC desktop examples; microsandbox (superradcompany/microsandbox, Apache-2.0, ~8.1k stars, beta) is a libkrun microVM runtime needing KVM/Apple HVF with no Kubernetes story; E2B's infra (Apache-2.0) self-hosts only on GCP/AWS via Terraform + Nomad/Consul with Firecracker ('requires bare metal or nested virtualization'), not Kubernetes; Daytona moved its production codebase closed-source on 2026-06-11 and its public repo is unmaintained.

- Confidence: high; source: <https://github.com/alibaba/OpenSandbox/blob/main/README.md> (Sept 2026 repo state; Daytona post 2026-06-11)
- Evidence: OpenSandbox README: 'Docker/Kubernetes runtimes ... gVisor, Kata Containers, and Firecracker microVMs'; E2B self-host.md: 'Firecracker requires bare metal or nested virtualization support', Nomad/Consul; Daytona post: production codebase now proprietary, existing repo 'stays public but unmaintained'; GitHub API licenses/stars.
- Relevance to VICE: Of the packaged sandbox platforms, only OpenSandbox runs inside an existing Kubernetes cluster with pluggable RuntimeClasses; E2B/microsandbox require their own VM hosts; Daytona is no longer an open-source candidate.

### Goose exposes four permission modes — auto, approve, smart_approve (LLM 'PermissionJudge' classifier), chat — selectable with `GOOSE_MODE` (auto|approve|smart|chat) or `/mode`; OpenCode's `opencode.json` `permission` block supports keys read, edit, glob, grep, bash, task, skill, lsp, question, webfetch, websearch, external_directory, doom_loop with values allow|ask|deny, pattern rules where the last match wins, per-agent overrides, `.env` denied by default, and `opencode run --auto` for non-interactive approval. Neither documents any OS-level (namespace/seccomp/Landlock) sandbox.

- Confidence: medium; source: <https://opencode.ai/docs/permissions/> (opencode.ai docs current; Goose issue #4097 (2025))
- Evidence: OpenCode docs: 'Each rule resolves to one of three actions: allow, ask, deny'; 'opencode run --auto command automatically approves permissions except those explicitly denied'; 'The documentation contains no mention of OS-level sandboxing mechanisms'. Goose docs mirror/issue #4097: modes 'auto|approve|smart|chat'.
- Relevance to VICE: OpenCode and Goose rely purely on policy prompts, so for these agents VICE must supply the OS boundary itself (wrap them with srt, or run them in a gVisor/Kata pod); their permission files should be shipped read-only by the image.

### NVIDIA's OpenShell project (an agent-cluster system running k3s with sandbox pods hardened by Landlock and seccomp) evaluated gVisor vs Firecracker microVMs vs cluster-in-VM in Feb 2026 and recommended gVisor as the starting point ('Lightweight, fast startup ... Works with existing Kubernetes RuntimeClass infrastructure'), noting Firecracker needs /dev/kvm and custom containerd binaries.

- Confidence: medium; source: <https://github.com/NVIDIA/OpenShell/issues/4> (2026-02-27)
- Evidence: Issue #4: gVisor 'Recommended'; Firecracker 'Provides strongest isolation model but requires /dev/kvm access'.
- Relevance to VICE: Independent corroboration that a K8s-native agent platform lands on gVisor-by-RuntimeClass as the default sandbox tier, with microVMs reserved for higher assurance.

## Recommendations

- Define three VICE security levels as alternative RuntimeClasses, not a stack: L1 'hardened container' = runc/crun + `hostUsers: false` + Localhost seccomp + Localhost AppArmor (for human-interactive JupyterLab/RStudio/VS Code/KasmVNC/ttyd pods); L2 'sandboxed agent' = gVisor RuntimeClass (`handler: runsc`, systrap on VMs / KVM on bare metal, `--nvproxy` on GPU nodes) for headless autonomous agent pods; L3 'VM' = Kata (QEMU or Cloud Hypervisor, `kata-qemu-nvidia-gpu` for whole-GPU passthrough) for Docker-in-pod, systemd, or sensitive-data jobs. Document that L2 cannot use hostUsers:false and ignores pod seccomp/AppArmor (gVisor issue #13303, GKE docs).
- Raise the node baseline before anything else: kernel >= 6.3, containerd >= 2.0.5 (skip 2.0.1–2.0.4 if Sysbox is used), Kubernetes >= 1.36 for GA user namespaces; on Ubuntu 24.04 nodes either set `kernel.apparmor_restrict_unprivileged_userns=0` or load an AppArmor profile for /usr/bin/bwrap with `userns,`; keep NVIDIA drivers inside gVisor's `runsc nvproxy list-supported-drivers` window.
- Ship a VICE-specific seccomp profile (OCI JSON under /var/lib/kubelet/seccomp, referenced as `seccompProfile.type: Localhost`) that starts from containerd's RuntimeDefault and additionally allows `unshare`, `clone`/`clone3` with CLONE_NEWUSER|CLONE_NEWNS|CLONE_NEWPID|CLONE_NEWNET|CLONE_NEWIPC|CLONE_NEWUTS, `mount`, `umount2`, `mount_setattr`, `open_tree`, `move_mount`, `pivot_root`, `setns`; and an AppArmor Localhost profile that permits `mount` and `userns` inside the pod. Verify with `bwrap --ro-bind / / --unshare-all --proc /proc true` in CI. Only with this can Claude Code (`sandbox.enabled`, `allowUnsandboxedCommands:false`, `failIfUnavailable`), Codex (`sandbox_mode = workspace-write`) and srt run their real sandboxes instead of `enableWeakerNestedSandbox`.
- Split human and agent processes: keep the human session in the L1 pod and launch autonomous agents as separate kubernetes-sigs/agent-sandbox `Sandbox` objects (v1.0.1) using the L2/L3 RuntimeClass, mounting the same RWX PVC/iRODS-backed volume; expose the agent's ttyd/log stream back into the DE UI. This gives uninterrupted long runs (`codex exec`, `claude -p`, `opencode run --auto`, `GOOSE_MODE=auto`) without sharing the human's shell, TTY, or Unix identity, and lets the human pod be stopped/restarted independently.
- Even inside one pod, never run agents as the human's UID with passwordless sudo: create a dedicated `agent` UID/GID (no sudoers entry), make ~/.irods, ~/.aws, ~/.ssh, ~/.config/gh, ~/.claude/.credentials.json and each agent's token dirs mode 0700 to the human user, and mount per-agent credential material (OpenBao-issued short-lived tokens) into the agent's own home. Layer Claude Code managed settings on top: `sandbox.credentials.files` deny for ~/.irods/.irodsA, ~/.aws/credentials, ~/.ssh; `credentials.envVars` mask with `injectHosts` for the AI Verde key (llm-api.cyverse.ai) and Anthropic/OpenAI keys, `network.tlsTerminate` for mask, `strictAllowlist` and `allowManagedDomainsOnly`; set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` for MCP subprocesses.
- Enforce egress at the cluster, not in the agent: default-deny NetworkPolicy per VICE namespace plus either Cilium `toFQDNs` policies or a transparent Squid egress gateway with `ssl::server_name` SNI allowlists (llm-api.cyverse.ai, api.anthropic.com, api.openai.com, github.com, PyPI/CRAN/conda mirrors, CyVerse Data Store/DE API endpoints). Treat the Claude Code/srt/Codex proxies as defense in depth only, since `excludedCommands` and `HTTP_PROXY`-ignoring binaries bypass them.
- FUSE strategy: on L1 pods, mount OSN S3 and iRODS via node-side CSI drivers (or the meta-fuse-csi-plugin fd-passing pattern for s3fs/goofys/mountpoint-s3) so the user pod needs no CAP_SYS_ADMIN or /dev/fuse; if in-pod s3fs must remain, require `hostUsers: false` + `CAP_SYS_ADMIN` (namespaced) + a /dev/fuse device plugin + the AppArmor profile above. On L2 (gVisor) run the FUSE daemon inside the sandbox via /dev/fuse and benchmark before offering it; do not plan on host-side libfuse servers over `--pass-fd`. On L3 (Kata) FUSE works in-guest (CONFIG_FUSE_FS=y).
- GPU strategy: self-hosted vLLM/Ollama for agents belongs on gVisor GPU nodes (`--nvproxy`, CUDA only, supported T4/L4/A100/H100, no MIG, no time-slicing) or on Kata with single-GPU VFIO passthrough for VM-grade isolation; keep GPU-accelerated KasmVNC desktops on L1 (gVisor lacks /dev/nvidia-drm) and do not use Sysbox on GPU nodes (NVIDIA container runtime unavailable). Consider a shared, cluster-level vLLM service behind AI Verde instead of per-pod GPUs so agent pods stay CPU-only and cheaply sandboxable.
- Run a two-week spike with measurable exit criteria before committing: (1) KasmVNC desktop and RStudio Server under `runtimeClassName: gvisor` on systrap (login, X shared-memory, package install timings vs runc); (2) bubblewrap/srt inside gVisor with bubblewrap < 0.12 and `--unshare-net` (tracking gVisor issues #13438/#14451); (3) vLLM in a gVisor pod on the actual VICE GPU driver version; (4) s3fs in-sandbox under gVisor vs CSI on runc. Record results in the VICE design doc as the basis for which apps get which level.
- Do not adopt kagent or Agent Substrate as the VICE runtime substrate: kagent is an ops-agent CRD framework with no isolation features, and Agent Substrate is self-described as early/aspirational with GCS checkpointing. Target kubernetes-sigs/agent-sandbox for orchestration and revisit Substrate in 2027; keep OpenSandbox on the watch list if VICE wants a unified sandbox SDK/API for MESA and CARC users.
- Deliver the isolation policy as admission rules (a VICE 'ai-sandbox' policy = PSS baseline + `hostUsers: false` required + no hostPath + seccomp/AppArmor Localhost required + capability allowlist limited to SYS_ADMIN only for FUSE-enabled apps) and lock agent config files (opencode.json, ~/.codex/config.toml, Claude managed settings) read-only in the image so users and agents cannot widen them; run Claude Code as a non-root user (its `--dangerously-skip-permissions` is refused as root).

## Open questions

- Does KasmVNC (Xvnc + shared-memory pipelines) and RStudio Server actually start and perform acceptably under gVisor systrap? No primary source documents either; needs a VICE spike (gVisor supports shmget without SHM_HUGETLB and Unix sockets, but DRM is unsupported).
- When will gVisor's user-namespace/idmap gap (issue #13303) and the bubblewrap-in-gVisor bugs (#13438 RTM_NEWADDR, #14451 openat2) be fixed, and will containerd start introspecting non-runc runtimes' features?
- Will gVisor add Landlock (issue #13439), which would let Codex's `use_legacy_landlock` and other Landlock-based agent sandboxes work inside gVisor pods?
- Which exact NVIDIA driver versions are installed on CyVerse VICE GPU nodes, and are they inside gVisor's rolling supported-driver window (`runsc nvproxy list-supported-drivers`)? If not, is `--nvproxy-allow-unsupported-driver` acceptable?
- Is there an iRODS FUSE client compatible with libfuse3 fd passing (fuse-starter / fusermount3-proxy) so it can use the meta-fuse-csi-plugin pattern, or must iRODS access go through a CSI driver / the mesa-mcp and formation-mcp APIs instead?
- Are VICE worker nodes bare metal (KVM available for gVisor KVM platform and Kata/Firecracker) or VMs without nested virtualization (systrap only, no Kata)?
- Which CNI does the DE cluster run today, and is a Cilium migration acceptable, or must egress control be a Squid/Envoy gateway with transparent redirection?
- How should hostUsers:false interact with existing VICE PVC/NFS volumes (idmap mount support on the node filesystem and any NFS/CephFS backends) and with the DE's current runAsUser/fsGroup conventions?
- What is the Pod Security Admission integration for user-namespace pods (the K8s docs reference a userns/PSA integration section that was not fetched) — can a userns pod be admitted as 'restricted' with capabilities such as SYS_ADMIN in a future release?
- How will long-running agent sandboxes be billed/quota'd in the DE (the existing VICE time limits vs agent-sandbox warm pools), and how does the human re-attach to a running agent pod's ttyd session across DE restarts?
