# GPUs and self-hosted LLMs (DRA, MIG/MPS, vLLM, Ollama, nvproxy)

Dimension key: `gpu-local-llm`. Date: 2026-09-06.

## Summary

Kubernetes GPU plumbing has matured enough in 2025-2026 that VICE can plan on it: Dynamic Resource Allocation went GA in v1.34 (resource.k8s.io/v1, on by default), Partitionable Devices and Consumable Capacity are beta-on-by-default since v1.36, Device Taints and Extended Resource mapping are GA in v1.37 (Sept 2026), and OCI Image Volumes (spec.volumes[].image) went Stable in v1.36 — so read-only model weights can be shipped as OCI artifacts and mounted without a PVC. NVIDIA's DRA driver moved to kubernetes-sigs/dra-driver-nvidia-gpu (v0.5.0, Aug 2026, needs K8s 1.32+) and documents full-GPU, MIG, time-slicing, MPS and consumable-capacity guides, but its README still labels GPU allocation experimental and its consumable-capacity "memory" mode explicitly does not cap a process's CUDA memory — DRA is a scheduler-side promise tracker; runtime isolation still comes only from MIG (hardware) or MPS/HAMi-style interposition. That matters because the GPUs in play mostly cannot MIG: CyVerse VICE offers NVIDIA A16 (4 x 16 GB Ampere GPUs per board, no MIG, no FP8) and UNM CARC's Easley has 36 L40S (48 GB, MIG: No) plus 8 H100 and Hopper's 37 A100 (both MIG up to 7). Time-slicing gives zero memory/fault isolation ("if one workload crashes, they all do"), so per-user agent pods sharing a GPU is a weak isolation story; a shared, namespace-level vLLM service behind LiteLLM (topology B) is the safer default, with an in-pod Ollama sidecar (topology A) reserved for whole-GPU A16/L40S allocations and small Q4 models. Every agent CLI the team ships can be pointed at such a service without user-held keys: vLLM and Ollama both expose the Anthropic /v1/messages API for Claude Code (ANTHROPIC_BASE_URL plus dummy ANTHROPIC_AUTH_TOKEN and ANTHROPIC_DEFAULT_*_MODEL), OpenCode uses @ai-sdk/openai-compatible with options.baseURL, Goose uses OPENAI_HOST/OPENAI_BASE_PATH or a LITELLM_HOST provider, and Codex has reserved ollama/lmstudio providers plus custom [model_providers] (but wire_api is "responses"-only, an open question for vLLM). Sandboxing GPU pods is possible but constrained: gVisor nvproxy requires an exact driver-version match from a short list (535.x, 570.124-172, 580.65-173, 590.48.01, 615.15) and passes driver ioctls through to the host kernel, and Kata/GPU-Operator supports only single-GPU VFIO passthrough with no vGPU. Memory rule of thumb from Ollama's own tag sizes: Llama 3.3 70B is 141 GB fp16 / 75 GB q8_0 / 43 GB q4_K_M; Qwen3-Coder 30B-A3B is 61/32/19 GB — so a 16 GB A16 slice only fits ~7B-14B Q4 models, one L40S fits 30B-Q4 or 70B-Q4 barely, and 70B fp16 needs two 80 GB cards (vLLM --gpu-memory-utilization default 0.92).

### [partially_true] Kubernetes DRA graduated to GA in v1.34: the resource.k8s.io API group is v1 and DRA is enabled by default.

**Implication for VICE.** The claim's implications for VICE hold, with two practical caveats. ### [confirmed] DRA consumable capacity for NVIDIA GPUs only reserves scheduler-visible memory; it does not enforce CUDA memory limits at runtime. Requires K8s 1.34+ (gate manual on 1.34-1.35, default on 1.36+); driver gate ConsumableShares is Alpha.

**Evidence.** Every specific in the claim was verified against the primary source plus independent upstream sources, all current as of 2026-09.

1. Runtime non-enforcement (primary source, NVIDIA DRA driver docs, "Last modified July 23, 2026"): the consumable-capacity guide states verbatim "A memory value reserves scheduler-visible capacity but does not limit a process's CUDA memory use." Modes documented: memory ("in 1 MiB increments"), unlimited ("Consumes zero memory capacity by default"), and a fixed positive-integer share count. Helm values named in the doc: `--set featureGates.ConsumableShares=true`, `--set consumableShares=memory|unlimited|<int>|disabled`, `--set gpuResourcesEnabledOverride=true`.

2. Independent corroboration of non-enforcement: KEP-5075 (kubernetes/enhancements) describes scheduler-side capacity accounting only and delegates any enforcement to drivers; the CNCF blog "Does Kubernetes DRA Replace HAMi?" (Mesut Oezdil, 2026-08-07) says verbatim "DRA, consumable capacity included, is a promise tracker. It guarantees the scheduler never promises more than a device has." and "It does nothing about a container that breaks the promise at runtime". The same post describes HAMi-core's libvgpu.so as a preloaded C library that "intercepts CUDA and NVIDIA Management Library (NVML) calls and applies the granted limits from user space" and reports a CUDA OOM at exactly the 8,000 MiB grant boundary. HAMi-core README confirms it intercepts CUDA calls to enforce per-container memory (CUDA_DEVICE_MEMORY_LIMIT) and SM (CUDA_DEVICE_SM_LIMIT) limits via LD_PRELOAD of libvgpu.so. HAMi README shows `nvidia.com/gpumem` as the resource name; `nvidia.com/gpucores` appears in charts/hami/README.md.

3. Kubernetes versions/gate: kubernetes.io feature-gates page (documenting v1.37) lists `DRAConsumableCapacity`: Alpha, default false, 1.34–1.35; Beta, default true, 1.36–. KEP-5075 kep.yaml: alpha v1.34, beta v1.36, stable targeted v1.38, latest-milestone v1.37 — i.e., Beta, not GA, today. NVIDIA doc matches: "Use Kubernetes v1.34 or later. On Kubernetes v1.34 and v1.35, enable the upstream DRAConsumableCapacity feature gate on the kube-apiserver, kube-controller-manager, kube-scheduler, and kubelet. Kubernetes v1.36 and later enables that gate by default."

4. Driver gate: NVIDIA/k8s-dra-driver-gpu pkg/featuregates/featuregates.go defines `ConsumableShares` with `PreRelease: featuregate.Alpha, Default: false, Version: 0.5`; the v0.5.0 release (published 2026-08-19, latest release) notes list `ConsumableShares | Alpha | false`. The doc string adds "MPS sharing is not supported when consumable shares is enabled", and the guide says "MPS is not supported while the driver's consumable-capacity mode is active. The driver rejects an MPS-configured claim in this configuration."

5. Licenses: NVIDIA/k8s-dra-driver-gpu is Apache-2.0 (GitHub API); Project-HAMi/HAMi is Apache-2.0 and is a CNCF Incubating project (README; CNCF blog 2026-07-15). Caveat: the Project-HAMi/HAMi-core repo reports no license via the GitHub API and has no LICENSE file in its root listing, so HAMi-core's license could not be verified from source.

**Implication for VICE.** The claim stands: on non-MIG GPUs (A16, L40S), NVIDIA's DRA consumable-capacity mode only prevents the scheduler from over-committing GPU memory; a VICE pod running an AI agent or notebook can still allocate past its claimed MiB and OOM a neighbor. For hard per-user GPU memory quotas VICE needs a runtime enforcer (HAMi's libvgpu.so interposer, Apache-2.0 HAMi, CNCF Incubating), NVIDIA MPS with per-client memory limits, MIG where hardware supports it, or whole-GPU allocation. Two constraints to plan around: (a) DRA consumable shares and MPS are mutually exclusive in the NVIDIA driver (the driver rejects MPS-configured claims when consumable-capacity mode is active), so "DRA + MPS" is not a valid combination — pick one; (b) the stack is pre-GA: DRAConsumableCapacity is Beta (default on) only from K8s 1.36 with GA targeted at 1.38, and the driver's ConsumableShares gate is Alpha/off-by-default in v0.5.0 (2026-08-19), so it is not production-grade for a multi-tenant research platform yet. Also note HAMi-core's repository carries no detectable license file, which is worth confirming before adopting it.

## Recommendations

- Adopt topology B as the default: run one namespace-level vLLM service per model tier (e.g., a 30B-class coder in AWQ/GPTQ on an L40S or A100, a 7B-14B model on an A16 sub-GPU) behind LiteLLM, and have app-exposer inject ANTHROPIC_BASE_URL/ANTHROPIC_AUTH_TOKEN/ANTHROPIC_DEFAULT_*_MODEL, OPENAI_HOST/OPENAI_BASE_PATH, and an opencode.json/Codex config.toml at launch; issue a LiteLLM virtual key scoped to the analysis lifetime so no user-held LLM key exists in the pod.
- Reserve topology A (Ollama sidecar container in the VICE pod) for whole-GPU allocations only (one A16 sub-GPU or one L40S per analysis), never on time-sliced GPUs; bake OLLAMA_HOST=127.0.0.1:11434, OLLAMA_CONTEXT_LENGTH>=32768, OLLAMA_KEEP_ALIVE=-1, and OLLAMA_MODELS pointing at a read-only mounted model volume; expose it to agents via 'ollama launch claude'-style env rather than a shared network endpoint.
- Do not use time-slicing for multi-user agent pods on A16/L40S unless failRequestsGreaterThanOne=true and renameByDefault=true are set and users are told there is no memory/fault isolation; where per-user memory caps are required on non-MIG GPUs, evaluate MPS (device plugin or DRA v0.5.0 multi-user MPS) and HAMi-core runtime enforcement, and use MIG (nvidia.com/mig-1g.10gb-style resources) only on CARC's A100/H100.
- Pin the cluster upgrade path to Kubernetes >=1.36 before the 'AI Sandboxes' iteration: it delivers Stable Image Volumes for OCI model artifacts, default-on DRA Partitionable Devices/Consumable Capacity, and (in 1.37) GA Device Taints and extended-resource mapping; then pilot kubernetes-sigs/dra-driver-nvidia-gpu v0.5.x with the gpu-kubelet-plugin enabled on a single GPU node pool while production keeps the device plugin.
- Package approved model weights as OCI artifacts (KitOps/ModelPack, or ORAS) in harbor.cyverse.org and mount them with spec.volumes[].image (ImageVolume) read-only into both vLLM and Ollama containers; keep a per-user writable Ollama/HF cache on the analysis's own PVC only for user-pulled models, and never share a writable model cache across users' agent pods.
- Define VICE security levels with explicit GPU consequences: 'standard' = runc + device plugin; 'sandboxed' = RuntimeClass gvisor with --nvproxy (compute+utility only; add graphics only for KasmVNC GPU desktops) which requires pinning node drivers to an nvproxy-supported version (580.x/590.48.01/615.15 at time of writing) and running 'runsc nvproxy list-supported-drivers' in CI; 'isolated' = Kata kata-qemu-nvidia-gpu with one whole GPU per pod and no sharing. Document that gVisor does not protect against NVIDIA driver vulnerabilities.
- Isolate GPU capacity with a dedicated node pool labeled via NFD (e.g., nvidia.com/gpu.product) and tainted NoSchedule; have app-exposer add the toleration and nodeAffinity only for GPU-requesting apps, and use DRA DeviceTaintRule (GA in 1.37) later to drain a GPU from agent pods without draining the node.
- Size by measured artifact sizes, not folklore: for VICE's 16 GB A16 sub-GPUs offer 7B-14B Q4/Q8 models; for a 48 GB L40S offer Qwen3-Coder-30B (19 GB q4_K_M / 32 GB q8_0) or Llama-3.3-70B q4_K_M (43 GB, minimal KV headroom); for 70B fp16 or long-context agent runs use two 80 GB H100/A100 with vLLM tensor parallelism; use FP8 weights/KV cache only on L40S/H100 (Ada/Hopper), and --gpu-memory-utilization <0.92 when co-tenanting.
- Track vLLM's Anthropic Messages implementation as a first-class dependency: pin a vLLM release that includes PR #44283 (Claude Code >=2.1.154 roles), set CLAUDE_CODE_ATTRIBUTION_HEADER=0 for prefix caching on older versions, and add a CI smoke test that runs Claude Code, Codex (--oss / custom provider, responses wire API), OpenCode and Goose against the shared endpoint after every image or vLLM bump.
- For MESA/CARC collaboration, stand up the shared vLLM tier on Easley (L40S/H100) and expose it to VICE as an external OpenAI/Anthropic-compatible endpoint fronted by LiteLLM with OpenBao-issued short-lived keys; K40s on Xena are pre-Volta and cannot run vLLM quantized paths, and llm-d/KServe are only worth adopting if that tier grows to multi-node H100 scale.
- Cut idle energy: prefer one shared L40S (350 W) running vLLM continuous batching over N per-pod sidecars each pinning a GPU; where sidecars are used, enforce OLLAMA_KEEP_ALIVE and stop the sidecar container when the analysis is idle, and report GPU-hours per analysis via the kubelet DRA/pod-resources metrics.
