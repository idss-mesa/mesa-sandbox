# MESA and UNM CARC context

Dimension key: `mesa-carc`. Date: 2026-09-06.

## Summary

MESA (NSF IDSS "Multidisciplinary Environment for Scientific Advancement", led by UNM with UNC and UArizona) is not a single deployment: its user-facing images (mesa-cli, mesa-jupyterlab, vscode, rstudio, kasm) are CyVerse VICE apps on harbor.cyverse.org; its hosted mesa-mcp runs on a Jetstream2 VM behind nginx + CyVerse Keycloak OIDC; its portal runs on a k3s cluster at gpu07.cyverse.org; and its most sensitive workload (mesa-nmdid, decedent CT imaging) runs on two NVIDIA DGX Sparks at UNM CARC (sparky-1.hpc.unm.edu, sparky-2) that are shared LDAP hosts with a LiteLLM->vLLM gateway on loopback, explicitly outside CARC's Slurm clusters. The team's own next-iteration design (idss-mesa/js2-substrate, written 2026-09-02, "designed, not built") is exactly the VICE candidate stack: kagent AgentHarness on Agent Substrate (gVisor actors, checkpoint/restore to rustfs/S3) on k3s on Jetstream2 VMs, reaching CARC's vLLM only through an outbound SSH tunnel, with default-deny NetworkPolicies and pods holding only a LiteLLM master key. MESA's credential model today is file-based and inherited by every agent: ~/.irods/irods_environment.json + scrambled ~/.irods/.irodsA (written by VICE's launcher or cyverse-login), ~/.aws and ~/.ssh copied from the user's iRODS home at container start, an AI Verde key in ~/.config/aiverde/env (0600) exported as OPENAI_API_KEY/ANTHROPIC_API_KEY, and Formation/AI-client configs that the MESA docs admit "land in plaintext in each client's config file"; the mesa-cli Dockerfile grants jovyan NOPASSWD sudo and mounts S3 with s3fs allow_other. MESA's existing security mechanisms are application-layer, not sandbox-layer: mesa-mcp's assert_allowed path allowlist backed by iRODS ACLs, the hosted mcp.cyverse.ai/mcp OAuth endpoint (client mcp-client) so Claude Code needs no iRODS password, per-project mesa.policy.<name> AVUs, and (in mesa-nmdid) Claude Code .claude/settings.json deny lists for seven ticket/ACL/rule tools plus DuckDB lockdown. UNM CARC's HPC (Easley: 36 L40S + 8 H100; Hopper: 37 A100) is Slurm + Singularity/Apptainer with CARC-specific accounts, no Kubernetes, no LLM service documented, and a Good Neighbor policy that bans HIPAA/PHI/PCI/FERPA/CUI data and passwords stored unencrypted on CARC filesystems; UNM AI guidance permits only P-Class (public) data in AI tools without Data Steward approval. A VICE AI-sandbox design that keeps secrets out of the agent's filesystem, offers a hosted-OAuth path for iRODS/DE access, isolates long-running agents in substrate actors, and treats an external OpenAI-compatible gateway (AI Verde or CARC LiteLLM) as the only model endpoint would fit both CyVerse and the UNM/CARC constraints without changing what runs on CARC.

## Recommendations

- Replace the entry.sh 'copy ~/.aws, ~/.ssh, .gitconfig from /data-store/iplant/home/$IPLANT_USER' step and the launcher-dropped ~/.irods/.irodsA with a per-pod credential broker: keep the CSI Data Store mount, and expose iRODS/DE/S3 access to agents only through hosted OAuth MCP endpoints (mcp.cyverse.ai/mcp with the mcp-client Keycloak client, de.cyverse.org/formation/mcp) or a local proxy that holds the secret; this preserves MESA's zero-config path for Claude Code and removes the .irodsA/plaintext-config exposure for all five agent CLIs.
- Add a first-class OAuth/PKCE login helper for OpenCode, Codex, Antigravity and Goose (the MESA README documents that only Claude Code completes the irods-auth login), or run a pod-local mcp-remote bridge that mints short-lived Keycloak tokens (the pattern mesa-mcp's OIDC doc describes for 'stdio-only Claude clients') so no agent needs ~/.irods.
- Drop 'jovyan ALL=(ALL) NOPASSWD: ALL' and s3fs allow_other from the VICE AI-sandbox image tier; mount OSN buckets via a CSI/sidecar using a Kubernetes Secret that the agent process cannot read, matching CyVerse's own guidance that VICE apps 'will not have root privileges'.
- Define VICE sandbox security levels that map to UNM data classes (P/C/E) and CARC's Good Neighbor rules: Level 0 = hosted models + public data (P-class); Level 1 = self-hosted gateway only (AI Verde on-prem models or a CARC LiteLLM tunnel), default-deny egress with allowlists (reuse js2-substrate's 00-90 NetworkPolicy set), no snapshots off-campus; Level 2 = no external egress, no ticket/ACL/rule MCP tools. Enforce MCP tool deny lists (ds_create_ticket, ds_modify_ticket, ds_use_ticket, ds_modify_access, ds_modify_access_inheritance, ds_execute_rule, mesa_policy_enable, as mesa-nmdid does) at the MCP gateway/proxy layer, not in per-agent settings files.
- Adopt Agent Substrate + kagent for headless long-running agents in a separate WorkerPool/namespace from the human's interactive VICE pod, and resolve MESA's open question first (does the kagent controller merge or overwrite ~/.openclaw/openclaw.json?) with the experiment in js2-substrate/kagent/OPEN-QUESTION-mcp-in-harness.md before committing to baked MCP configs; keep the interactive JupyterLab/RStudio pod as-is and let it hand tasks to the actor.
- Treat snapshot storage as a credential and data store: encrypt rustfs/S3 snapshot buckets at rest, expire them, and give each security level a snapshot-location constraint (MESA's data-governance.md refuses off-campus snapshots for agents holding ticket text or credentials).
- Make 'external OpenAI-compatible gateway' the primary GPU/LLM integration for VICE sandboxes (ModelConfig pointing at AI Verde or a tunnelled CARC LiteLLM), with in-cluster vLLM/Ollama as an optional backend; for MESA at UNM the only model endpoint is http://127.0.0.1:8000/v1 on the Sparks reachable via outbound SSH tunnel, so the design should include a per-user tunnel/relay sidecar pattern like js2-substrate's carc-vm-forward.
- Provide an injected, non-agent-readable Postgres DSN secret (MESA_MCP_DUCKLAKE__CATALOG_DSN) or route mesa-mcp through the hosted Mode A service so DuckLake provenance is recorded in VICE sessions instead of silently skipped.
- Publish an Apptainer-compatible, sudo-free variant of the MESA agent image (no ttyd daemon requirement, no FUSE allow_other, credentials via env from Slurm --export or a CARC-approved secret file with 0600) so MESA users on Easley/Hopper OOD sessions can run the same agents and MCP servers under CARC's Good Neighbor constraints.
- Coordinate with CyVerse IAM early to register VICE-specific Keycloak clients (confidential for the broker, public PKCE for agent logins), since mesa-mcp's docs show client registration is ticket-only and the mesa-mcp-public client was still pending.
